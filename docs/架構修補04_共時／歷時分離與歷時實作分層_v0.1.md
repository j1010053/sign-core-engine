# 修正目的

本修補正式區分：

* 共時（Synchronic）
* 歷時（Diachronic）

兩套系統的責任，並建立歷時引擎的分層架構。

修補完成後：

* 共時引擎負責描述「語言現在如何運作」。
* 歷時引擎負責描述「語言如何改變」。
* Compile 僅存在於共時側。
* 歷時系統永遠操作 Grammar Source，而非 Compiled Grammar。

---

# 一、共時架構

共時系統採宣告式（Declarative）。

目的為描述語言目前的狀態，而非描述修改流程。

共時 Grammar Source 包含：

* Global
* Trait
* Sign

Compile 後產生：

* Compiled Sign
* Compiled Grammar

Engine 僅讀取：

* Compiled Sign
* Compiled Grammar

不得讀取：

* Trait
* Compile Metadata
* Annotation
* Example

---

## 共時流程

```text
Grammar Source
(Global / Trait / Sign)

        │

     Compile

        │

 ├─ Trait Expansion
 ├─ Name Resolution
 ├─ Type Check
 ├─ Priority Resolution
 ├─ Rule Order Preservation
 ├─ Index Generation

        ▼

Compiled Sign
Compiled Grammar

        ▼

Grammar Engine

        ▼

Deep → Surface
```

---

# 二、歷時架構

歷時系統採腳本式（Imperative）。

目的不是描述語言，而是修改 Grammar Source。

歷時引擎不得直接修改：

* Compiled Grammar
* Compiled Sign

所有修改皆作用於：

* Global
* Trait
* Sign

修改完成後重新 Compile。

流程如下：

```text
ChangeSet

        │

Interpreter

        │

Grammar Source

        │

Compile

        ▼

Compiled Grammar

        ▼

Grammar Engine
```

因此：

Compiled Grammar 永遠是編譯產物。

不得成為歷時演化的操作對象。

---

# 三、歷時實作分層

歷時系統分為四層。

---

## 第一層：Primitive Edit

最底層 AST 操作。

不包含任何語言學知識。

例如：

* insert
* delete
* replace
* rename
* move
* set
* unset

此層直接修改 Grammar Source。

---

## 第二層：Atomic Rewrite

原子化語言學操作。

每個 Rewrite 僅負責一種語言學變化，可自由組合。

例如：

* reanalyze
* bleach
* shift_category
* lexicalize
* fossilize
* generalize
* specialize
* morphologize
* cliticize
* fuse
* split
* merge
* semantic_extension
* semantic_narrowing

Atomic Rewrite 由 Primitive Edit 組成。

---

## 第三層：Evolution Recipe

Evolution Recipe 為可重複使用的演化流程。

一個 Recipe 定義：

> 如何透過 Atomic Rewrite 完成某種演化路徑。

例如：

Future by GO

可能包含：

* reanalyze
* semantic bleaching
* morphologize
* phonological reduction

另一個：

Future by Word Order

則可能包含：

* reorder
* reanalyze

Recipe 為固定流程。

若修改其中步驟，應建立新的 Recipe，而非修改既有 Recipe。

Recipe 構成自動演化系統的主要知識庫。

---

## 第四層：Evolution Goal

Goal 描述希望演化出的語言功能。

例如：

* Future
* Perfect
* Progressive
* Topic
* Focus
* Case Marker
* Classifier
* Article
* Honorific
* Evidential
* Negation

Goal 不描述演化方法。

Goal 僅決定：

> 應搜尋哪些 Recipe。

例如：

Future

可能對應：

* GO Recipe
* WANT Recipe
* COME Recipe
* Auxiliary Recipe
* Word Order Recipe
* User-defined Recipe

Goal 與 Recipe 完全分離。

---

# 四、自動演化資料庫

自動演化主要維護：

* Evolution Goal Database
* Evolution Recipe Database

其中：

Goal Database

負責：

* Goal 與 Recipe 的對應
* 各 Recipe 的選擇權重

Recipe Database

負責：

* Rewrite Sequence
* 適用條件
* 偏好條件
* 語言學來源
* 使用統計

MVP 階段：

Recipe 權重預設以自然語言分布作為抽樣機率。

未來可替換為其他演化模型。

---

# 五、使用者干涉層級

本架構不區分「自動」與「手動」。

而採用不同抽象層級的介入。

使用者可於任一層停止自動化。

例如：

**Goal 層**

指定：

> 發展完成時。

Recipe 由系統選擇。

Rewrite 自動展開。

---

**Recipe 層**

指定：

> 採用 GO Recipe。

系統直接執行對應 Rewrite。

---

**Atomic Rewrite 層**

使用者自行組合：

* reanalyze
* bleach
* lexicalize
* generalize

系統負責展開 Primitive。

---

**Primitive 層**

完全自行編輯 Grammar Source。

不經任何語言學封裝。

---

此外，使用者亦可直接修改：

* Goal Database
* Recipe Database

以建立符合特定世界觀或語言家族的演化模型，而不需修改底層 Rewrite 或 Primitive。

---

# 六、設計原則
0. 將共時檔案名稱改為Language
1. 共時描述語言狀態；歷時描述語言修改。
2. Compile 僅存在於共時系統。
3. Compiled Grammar 永遠為執行表示，不屬於語言知識。
4. 歷時引擎永遠修改 Language。
5. Primitive 不包含語言學知識。
6. Atomic Rewrite 提供自由組合的語言學操作。
7. Recipe 封裝常見演化路徑。
8. Goal 描述語言功能，不描述演化方式。
9. Goal 與 Recipe 解耦，使自動演化與手動演化可共享相同底層架構。

# 七、補充：未來功能佔位接口
### State

State 用於描述**語言演化發生時的外部狀態**，而非語言知識本身。

State 不參與共時 Grammar、Compile 或 Grammar Engine，也不屬於 Language。它提供歷時演化所需的環境資訊，使相同的 ChangeSet 能在不同環境下產生不同的演化結果。

State 的內容包括但不限於：

* 年代（Time）
* 地理與區域（Region）
* 社會環境（如階級、群體）
* 語言接觸（Language Contact）
* 其他影響語言演化的外部條件

#### MVP

MVP 階段，State 僅作為專案資料與 UI 顯示使用，不參與任何演化運算，其定位接近 Annotation，但具有明確的資料結構，供未來系統使用。

#### 未來規劃

未來 State 將作為自動演化與 Multi-Agent 系統的共享環境。

Evolution Recipe 可根據 State 調整候選路徑與權重；Multi-Agent 則透過修改 State（如人口、地區、社會結構、語言接觸等）間接影響語言演化，而非直接修改 Language 或 ChangeSet。
