# 邏輯分層架構(v0.1)— docs/12

補 docs/01 架構書 §3 未曾精確化的分層設計。本檔定義**每一層的職責、讀寫權限、資料流方向**,解決「UI 要跟誰要資料」「引擎層是幾個子層」「哪些東西不屬於 UI 卻被我們一路說成 UI 的事」等懸案。

> 梯次:【M】MVP /【M+】後 /【N】v-next。
> 本檔不重複定義各層的內部資料結構,引用各自的規範文件。

---

## 0. 分層總覽

```
┌─────────────────────────────────────────────────────────┐
│  展示層(Presentation)                                    │
│  Tauri shell / WASM 前端                                 │
└──────────────────────┬──────────────────────────────────┘
                       │ Command / Query
┌──────────────────────▼──────────────────────────────────┐
│  應用層(Application)                                     │
│  Command API · Query/Projection API · Undo/Redo · 專案管理│
└──────────────────────┬──────────────────────────────────┘
                       │ 操作(Action) / 快照(Snapshot)
┌──────────────────────▼──────────────────────────────────┐
│  引擎層(Engine)                                          │
│  ┌───────────────────────┐ ┌───────────────────────────┐ │
│  │ 即時子層(Interactive) │ │ 批次演化子層(Evolution)   │ │
│  │ DSL 即時執行          │ │ ChangeSet Replay          │ │
│  │ Sign 生成引擎         │ │ B 原語批次執行            │ │
│  └───────────────────────┘ │ E 批次抽樣(自動模式)      │ │
│                             └───────────────────────────┘ │
└──────────────────────┬──────────────────────────────────┘
                       │ 讀/寫
┌──────────────────────▼──────────────────────────────────┐
│  資料層(Data)                                            │
│  D 節點樹 · C Sign Store · E1 先驗庫 · 專案設定檔        │
└─────────────────────────────────────────────────────────┘
```

**資料流方向:單向下行**。展示→應用→引擎→資料。反向只有「快照/視圖」回傳(唯讀引用),不是資料改動。

## 1. 資料層(Data Layer)

**唯一變更理由**:語言知識與專案設定的持久儲存。

### 1.1 引擎資料(由引擎層寫;規範見 docs/06–10)
- **D**:LanguageNode 樹、ChangeSet(ChangeEntry = L1∪L2 op + macro 回指)、nativization、parents。
- **C**:Sign Store(稀疏四維 sign、五連接關係、覆寫層、旁註層)。
- **E1**:類型學先驗庫(唯讀,隨軟體打包,永不被引擎寫)。

### 1.2 專案設定檔(由應用層寫;引擎唯讀或不讀)
- **View Config**:閾值、著色方案、篩選條件、顯示偏好。與 ChangeSet 同一 SQLite 不同表——同一專案檔、語意完全隔離。
- **Classification Override**:使用者對語言/方言界線的手動裁決(強制合併/分割/自訂標籤/說明文字)。
  - 理由:語言/方言界線本質是社會政治判斷,不是語言距離能回答的(馬其頓語 vs 保加利亞語;塞爾維亞語 vs 克羅埃西亞語)。資料層永遠只存連續的差異向量(語言學事實);Override 是「詮釋層」,存在設定檔而非 ChangeSet。
  - 操作:強制合併(兩節點同語言)/ 強制分割 / 自訂標籤(語言/方言/口音/社會變體)/ 附說明(進旁註層)。
  - 可多套並存:「從語言學看」一套閾值、「從政治認可看」一套 Override,同一棵樹多個視角切換,不改底層資料。

### 1.3 讀寫權限總結
| 誰 | 讀 | 寫 |
|---|---|---|
| 展示層 | 禁止直接讀 | 禁止 |
| 應用層 | Sign Store 快照(唯讀引用) | View Config / Override |
| 引擎層(即時) | C / D / E1 | C(透過 Builder commit) |
| 引擎層(批次) | C / D / E1 | C / D(透過 lifecycle commit) |
| E1 | — | 永遠唯讀 |

## 2. 引擎層(Engine Layer):兩個性質不同的子層

**切分依據:操作的時間性質**——不是「操作什麼」,而是「操作的節奏與觸發方式」。

### 2.1 即時子層(Interactive Engine)【M】

**回應時間:毫秒**。操作特性:增量、使用者觸發、每次影響少量單位、必須即時回應、支援 undo。

```
DSL 即時執行(docs/02–04,M0 的 core crate)= 共時導出(預覽;《架構修補01》):
  lifecycle / primitives / verbs / strategy / locality / scan / spellout / diag
  使用場景:使用者測試一條規則、看它對某詞(臨時韻律域)的即時導出效果;
           逐步追蹤規則套用的中間形。表層形為預覽產物,不回寫儲存。

Sign 生成引擎(docs/09):
  Need → Generator(唯讀)→ Builder(唯一寫入點)
  使用場景:造詞、組合、借詞的互動流程;
           使用者挑選候選、採納後固化進 Store。
```

兩個**平行**子系統:都是「使用者下指令、引擎即時回應、影響少量單位」。DSL 直譯器 core crate 在此以**單詞/選定範圍**的粒度運作。

### 2.2 批次演化子層(Evolution Engine)【M+】

**回應時間:秒到分鐘**。操作特性:批次、規則驅動、影響整個 Store 或節點樹、可非同步、有進度回報。

```
ChangeSet Replay(docs/06 §5):
  對整個 Sign Store 依序展開 ChangeEntry 序列 → 產生後代節點。
  SoundChange 條目 = Grammar Store/UR 的編輯(《架構修補01》P2),
  編輯後對受影響 sign 重導出——同一個 DSL core crate,批次模式呼叫。

B 原語批次執行(docs/08 B1):
  展開 L3 宏 → L1/L2 原語序列 → 對 Store 批次施加語意/句法/結構變化。
  語法化路徑在此被「跑完」,而非逐步互動。

E 批次抽樣(docs/10,僅自動演化模式):
  大量候選生成 + 類型學路徑選擇 + 類型學合理性驗證。
  ⚠️ 只有干涉光譜設為「自動」時才觸發。
```

三個**協作**子系統:都是大批次、共用同一個「跑完再回報結果」的排程語意。

### 2.3 關鍵結論:DSL 核心跨兩子層

**同一個 DSL core crate 被兩個子層以不同方式使用**——這就是「音變引擎既像 sign 生成(即時互動)又像演化子系統(批次 replay)」的原因:它不偏屬任何一邊,是兩層共用的底層能力。

工程含義:
- 即時子層要低延遲、可 undo、同步回應。
- 批次演化子層可非同步、有進度條、跑很久沒問題。
- **並行化在批次子層的殼層做,core crate 維持單執行緒**——符合 CLAUDE.md §4 可移植性規範。

## 3. 應用層(Application Layer)

**目前設計最空白的一層**——我們把大量「不是 UI 也不是引擎」的邏輯說成「UI 的事」,其實都屬於此層。

**唯一變更理由**:協調使用者意圖與引擎操作、維護視圖一致性。

### 3.1 Command API【M+】
接收使用者意圖 → 分解為引擎操作序列 → 下發給對應子層:
```
command::apply_rule(rule, scope) → 即時子層 DSL
command::adopt_proposal(proposal_id) → 即時子層 Builder
command::run_evolution(node_id, changeset) → 批次子層 Replay
command::set_view_config(config) → 寫 View Config
command::set_override(override) → 寫 Classification Override
```
Command API 是**展示層唯一的寫入管道**。展示層不直接呼叫引擎。

### 3.2 Query / Projection API【M+】
計算視圖、回答查詢;接收 View Config + Override 作為參數(無狀態純函數):
```
query::lexicon(filter, sort, config) → 辭典視圖(已固化 sign 投影)
query::semantic_coverage(map_ref, config) → 語意場/覆蓋率
query::derivation_family(sign_id) → 派生 DAG(origin+derivation 邊遍歷)
query::diff_vector(node_a, node_b) → 分層差異向量(需 replay 兩節點)
query::intelligibility(a, b, override) → 互通度(含 Override 參數)
query::dialect_groups(root, threshold, override) → 方言群組
query::search(query_str, kind) → 全文/IPA/語意場搜尋
query::phoneme_stats(node_id) → 統計投影(呼叫 E)
```
**增量失效**:演化後哪些投影需重算——應用層維護失效表,避免重複計算昂貴的 diff/replay。

### 3.3 Undo/Redo 協調【M+】
Command 執行前後各取快照(即時子層的 commit 天然產生快照);批次演化為粗粒度 undo(整個 ChangeSet 執行前快照)。

### 3.4 專案管理【M】
讀寫 SQLite 專案檔;序列化/反序列化 D/C;管理 View Config / Override 的存取。

## 4. 展示層(Presentation Layer)

**UI 的精確定義**:展示層對引擎資料是**唯讀的**——它不直接改 sign store 或 ChangeSet。但它有**自己的狀態**,且能透過 Command API 觸發引擎操作。

### 4.1 展示層自己的狀態
| 種類 | 描述 | 生命週期 |
|---|---|---|
| Session State | 目前選中節點/sign/Proposal、追蹤視圖進度 | ephemeral(關視窗即消) |
| View Config | 閾值/著色/篩選(存專案設定檔) | 隨專案持久 |
| Classification Override | 政治/社會切分判斷(存專案設定檔) | 隨專案持久 |

### 4.2 UI 負責的渲染工作
UI 只渲染 Query API 回傳的視圖,無語言學邏輯:

| 畫面 | 資料來源 | UI 做什麼 |
|---|---|---|
| 演化樹視圖 | D 節點+邊 | 渲染家族樹 + 規則清單 |
| 詞源回放 | DSL replay 快照序列 | 逐 commit 動畫 |
| 辭典表格 | `query::lexicon` | 可篩選排序表格 |
| 語意場覆蓋 | `query::semantic_coverage` | 填空進度視覺化 |
| 候選詞面板 | Generator 的 Proposal 列表 | 10–20 候選挑選 |
| 統計面板 | `query::phoneme_stats` | 頻率圖表 |
| 派生家族 | `query::derivation_family` | DAG 渲染 |
| 旁註層 | Annotation Layer | 附著在對象旁顯示 |
| 方言群組 | `query::dialect_groups(threshold, override)` | 依閾值+Override 著色 |
| 追蹤視圖 | trace 快照 / resolved-later 警告 | 逐步視覺化;resolved-later 淡化 |

### 4.3 UI 有邏輯的地方(不是純渲染)
- 閾值調整介面:讓使用者設定 `threshold` 傳入 Query API。
- Classification Override 編輯:強制合併/分割/標籤/說明文字 → 存 Override → 觸發相關查詢重算。
- 候選詞排序/過濾 UI:讀 Proposal 的評分欄位排序(評分由 Generator 給,UI 只顯示)。
- 類型學合理性提示:自動模式下,Query API 回傳的產物超出 Grambank/WALS 分佈時,UI 顯示警告標記。

## 5. 跨層資料流實例(三個具體路徑)

**路徑 A:使用者造一個詞(即時)**
```
展示層:使用者填 Need(只給 sem「河」)
  → Command API: adopt_proposal 後選中候選
  → 即時子層 Builder: assign SignId + validate + write Store
  → C Sign Store: 新 sign 固化
  → Query API 觸發 lexicon 失效 → 辭典視圖更新
  → 展示層渲染新詞條
```

**路徑 B:節點演化(批次)**
```
展示層:使用者點「執行演化」
  → Command API: run_evolution(node, changeset)
  → 批次子層 ChangeSet Replay: 展開 L1/L2 op → DSL core 批次執行 → B 原語執行
  → C/D: 後代節點寫入
  → Query API 觸發 diff_vector / dialect_groups 失效
  → 展示層更新演化樹視圖
```

**路徑 C:使用者調整方言界線(純視圖)**
```
展示層:使用者設閾值 0.4 + 強制合併節點 A/B(Override)
  → Command API: set_view_config(threshold=0.4) + set_override(merge A,B)
  → 應用層寫 View Config / Override 進設定檔
  → Query API: dialect_groups(root, 0.4, override) 重算
  → 展示層用新分組重新著色演化樹
  (C / D 完全不動——底層差異向量沒有改變)
```

## 6. 實現順序

| 梯次 | 項目 |
|---|---|
| 【M】 | 資料層結構(已含 docs/06–10);即時子層核心(M0 實作);專案管理骨架(讀寫 SQLite) |
| 【M+】 | 批次演化子層(ChangeSet Replay + B 原語);Query/Projection API 骨架;Command API;Undo/Redo;View Config / Override 介面 |
| 【N】 | 批次子層的非同步排程與進度回報;Classification Override 多套並存視角;類型學合理性警告系統 |

**下一個設計空白**:應用層(Command API + Query API)目前是本文件的骨架宣告,尚無欄位級規格——這是 M3/M4 動工前需補齊的。Sign 引擎(docs/09)和 DSL 引擎(docs/02–04)動工前無需此層,但 UI 動工前必須有。
