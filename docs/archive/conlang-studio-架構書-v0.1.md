# Conlang Studio 初步架構書(v0.1)

> 一款可自由調節「人為干涉程度」的人造語言設計桌面軟體。
> 第一階段:純規則 + 統計引擎,完全離線、結果可重現。
> 核心重點:**音系與音變演化**、**造詞與詞典管理**。

---

## 1. 專案目標

讓使用者能在「全手動精雕」與「一鍵生成」之間自由滑動:

- 演化語言時,只需撰寫**關鍵音變規則**,系統依自然語言演變規律自動補齊次要演變。
- 造詞時,系統依音位配列與音型分佈**自動生成候選詞**,使用者挑選、微調或重骰。
- 所有自動生成內容皆可追溯、鎖定、覆寫——軟體是助手,不是黑箱。

### 非目標(第一階段)

- LLM / 線上 AI 輔助(列為 Phase 2)
- 文字系統(字符)設計器(列為 Phase 2+)
- 完整句法樹分析、語料庫工具

---

## 2. 核心設計原則

### 2.1 干涉光譜(Intervention Spectrum)

每個模組獨立設定三檔模式,而非全域開關:

| 模式 | 行為 |
|------|------|
| 手動 | 使用者定義一切,系統只做驗證(如檢查詞是否違反音位配列) |
| 輔助 | 使用者設定約束與關鍵規則,系統填補其餘並標示為「建議」 |
| 自動 | 系統依類型學統計分佈生成,使用者事後修改 |

### 2.2 來源標記(Provenance)

每個資料物件(音素、規則、詞條)攜帶 metadata:

```
origin: manual | assisted | generated
locked: bool        # 鎖定後重新生成時不會被覆蓋
seed_ref: string    # 生成時使用的亂數種子引用
```

### 2.3 可重現性(Reproducibility)

- 所有隨機生成基於**顯式 seed**(專案層 + 操作層)。
- 同一專案檔 + 同一 seed → 完全相同的輸出。方便分享、回溯、除錯。

### 2.4 非破壞式演化

音變不修改原詞條,而是產生新的「語言階段(stage)」。祖語永遠保留,演化樹可任意分支。

## 3. 系統架構總覽

```
┌─────────────────────────────────────────────┐
│                  UI 層(桌面)                │
│  專案儀表板 / 音系編輯器 / 規則編輯器(音變)  │
│  造詞工作台 / 詞典瀏覽器 / 演化樹視圖         │
├─────────────────────────────────────────────┤
│                應用邏輯層                     │
│  專案管理 / 干涉模式控制 / 撤銷重做 /         │
│  匯入匯出 / 驗證與衝突偵測                    │
├─────────────────────────────────────────────┤
│                核心引擎層(純函式、無 UI 依賴)│
│  ① 音系引擎   ② 音變引擎(SCE)              │
│  ③ 造詞引擎   ④ 統計/類型學資料層            │
├─────────────────────────────────────────────┤
│                資料層                         │
│  專案檔(SQLite 或 JSON bundle)              │
│  內建資料集:IPA 特徵表 / 音變自然度庫 /      │
│  類型學共現統計(WALS 派生)/ Swadesh 語意庫  │
└─────────────────────────────────────────────┘
```

核心引擎層與 UI 完全解耦,可獨立測試,未來可抽成 CLI 或函式庫。

## 4. 核心模組詳述

### 4.1 音系模組(Phonology)

**資料模型**

- `Phoneme`:IPA 符號 + 區別特徵(distinctive features:[±voice]、[±nasal]、調音部位/方式等)。特徵系統是音變引擎的基礎。
- `SyllableTemplate`:如 `(C)(G)V(C)`,各槽位可綁定音素類別(class)。
- `PhonemeClass`:使用者自訂類別,如 `C = 全部輔音`、`P = {p, t, k}`。
- 超音段:重音規則(固定/重量敏感)、聲調(Phase 1 支援簡單聲調欄位)。

**輔助模式行為**

- 使用者選定部分音素後,系統依**共現統計**建議補齊(例:有 /b d/ 而無 /g/ 的系統罕見 → 建議加入 /g/ 或標示為刻意空缺)。
- 音素庫完成後自動計算:音素數量落點、對稱性分析、與自然語言分佈的相似度報告。

### 4.2 音變引擎(Sound Change Engine, SCE)——第一優先

**規則語法**(對標 Lexurgy / SCA²,但整合特徵系統):

```
# 基本形式:目標 > 結果 / 環境
k > tʃ / _ [+front]          # k 在前元音前顎化
[+stop -voice] > [+voice] / V_V   # 元音間清塞音濁化
V > ∅ / _ #  (unstressed)     # 詞尾非重音元音脫落
```

- 支援特徵運算(`[+stop]`)、類別引用(`P > B / V_V`)、通配、詞界 `#`、可選環境。
- 規則**有序套用**(feeding / bleeding 順序可視化)。
- 每條規則可附註解與「自然度標籤」。

**輔助模式:自動補充演變(本軟體的招牌功能)**

1. 使用者撰寫 N 條關鍵音變(如「元音大推移」「詞尾輔音脫落」)。
2. 系統依**音變自然度資料庫**(內建常見演變路徑:lenition 鏈 `p→b→β→v→∅`、顎化、元音弱化、同化等,各附機率權重與前提條件)抽樣補充次要演變。
3. 補充規則以「建議」形式插入時間軸,使用者可接受/拒絕/調整順序。
4. 系統檢查衝突(規則互相抵銷、產生違反音位配列的輸出)並警告。

**輸出**

- 每個詞條的完整**衍生鏈(derivation)**:`*kʷetwores → kʷettor → tʃettor → tʃetor`,逐規則可展開檢視。
- 階段(stage)快照:演化後產生新語言階段,自動繼承詞典並記錄詞源鏈。

### 4.3 造詞引擎與詞典(Lexicon)——第一優先

**造詞器(Word Generator)**

- 依音節模板 + 音位配列限制生成合法詞形。
- **加權模型**:音素頻率(可手動調或依 Zipf 類分佈)、音節數分佈、位置偏好(某音素偏好詞首)、雙音素轉移機率(bigram)——讓生成詞有一致的「語感」。
- **候選預選流程**:輸入語意概念 → 系統生成 10–20 個候選 → 使用者挑選/編輯/重骰 → 入庫。
- 避撞檢查:同音詞警告、與既有詞的編輯距離過近警告(可設閾值)。

**詞典管理**

- 詞條 schema:詞形(音位/表層)、詞類、語意(可多義項)、語意場標籤、詞源(來源詞 + 經過的音變鏈 + 語意漂移註記)、例句、備註。
- 語意覆蓋工具:內建 Swadesh 100/207、Leipzig-Jakarta 等概念清單,顯示覆蓋進度。
- 派生關係:複合詞、詞綴派生的連結圖。
- 搜尋:依詞形(支援音素類別搜尋,如「找所有 /P/ 開頭的詞」)、語意、標籤。

### 4.4 次要模組(第一階段從簡)

- **型態模組**:詞綴定義 + 範式自動展開(定義規則後生成完整變化表),音變引擎可作用於整個範式。不做複雜的非串接型態。
- **句法模組**:僅存基本類型設定(語序、對齊)供文件化,不做分析器。

## 5. 自動化引擎設計

### 5.1 規則層(確定性)

音位配列驗證、範式展開、音變套用。純函式、可單元測試。

### 5.2 統計層(加權隨機)

- **類型學共現資料**:音素庫建議、音節結構常見度(源自 WALS / PHOIBLE 派生的靜態資料集,隨軟體內建,離線可用)。
- **音變自然度庫**:人工整理的常見演變路徑 + 權重 + 觸發條件。這是需要投入內容工程的部分,建議做成**可編輯的資料檔(如 TOML/JSON)**,社群可貢獻擴充。
- 所有抽樣走 seeded PRNG。

### 5.3 Phase 2 擴充點(預留介面)

引擎層定義 `SuggestionProvider` 介面,Phase 1 由統計層實作;Phase 2 可掛 LLM 實作(語意漂移建議、例句生成),不動核心架構。

---

## 6. 資料模型與專案檔

- **專案檔**:單一 SQLite 檔(`.conlang`),優點:交易性、增量儲存、大詞典查詢快。另支援匯出為人類可讀的 JSON bundle(利於版本控制與分享)。
- 主要資料表:`languages(stages)`、`phonemes`、`classes`、`syllable_templates`、`sound_changes`、`lexemes`、`senses`、`etymologies`、`affixes`、`paradigms`、`project_meta(seeds)`。
- **演化樹**:`language_stage` 節點 + `derived_from` 邊,天然形成語言家族樹。
- 匯出:詞典 → CSV / Markdown / LaTeX;衍生鏈 → 文字報告。

## 7. 技術選型建議

| 項目 | 建議 | 理由 |
|------|------|------|
| 桌面框架 | **Tauri**(備選 Electron) | 體積小、記憶體省;前端生態完整 |
| 核心引擎 | **Rust**(Tauri 原生)或 TypeScript | 音變批次套用上萬詞條需效能;Rust 可編譯成 CLI/WASM 復用 |
| 前端 | React + TypeScript | 規則編輯器、衍生鏈視圖等複雜 UI |
| 儲存 | SQLite(bundled) | 離線、單檔、可靠 |
| IPA 支援 | 內建 IPA 鍵盤面板 + X-SAMPA 輸入轉換 | 降低輸入門檻 |

若你偏好單一語言棧,Electron + TypeScript 全棧亦完全可行;效能瓶頸(批次音變)可後續以 WASM 優化。

## 8. 開發階段規劃

**Phase 1a — MVP(核心閉環)**
音系編輯器(手動模式)→ 音位配列 → 造詞器(含候選預選)→ 基本詞典 → 音變引擎(手動規則)+ 衍生鏈檢視 → 專案存讀。

**Phase 1b — 輔助模式**
音素庫建議、音變自動補充、造詞加權模型調校 UI、衝突偵測、演化樹多階段管理。

**Phase 1c — 打磨**
範式展開、匯出格式、Swadesh 覆蓋工具、撤銷重做完善、seed 管理 UI。

**Phase 2 — AI 擴充**
LLM SuggestionProvider(語意漂移、例句、自然語言描述→規則草稿)、文字系統設計器。

---

## 9. 風險與開放問題

1. **音變規則語法的學習曲線**:需在表達力(Lexurgy 級)與易用性間取捨。建議提供「規則精靈」表單模式與純文字模式雙軌。
2. **音變自然度庫的內容工程**:這是差異化功能但需大量語言學整理,建議先覆蓋 20–30 種最常見演變,格式開放讓社群擴充。
3. **特徵系統的選擇**:採用哪套區別特徵(SPE 式?)影響規則語法設計,需早期定案。
4. **聲調與超音段**:第一階段支援到什麼深度?(建議:聲調作為音節屬性可參與音變,但不做聲調變調沙盒。)
5. **詞典規模**:目標支援單語言 1 萬詞條以上流暢操作,影響索引與 UI 虛擬化設計。
