# 套件內容雜湊的正規化(裁定)

> **狀態:已裁定(擁有者 2026-08-09),已實作。**
> 起因:2026-08-07 CI 在 windows-latest 掛在
> `CHANGESET_LIBRARY_LOCK_MISMATCH`,ubuntu-latest 全過。
>
> 承 P26(replay 逐位元可重現)、P29(package code/data/config 三層 + export
> 穩定契約)、P50(可重現性靠 library lock)、P21(canonical printer)、
> R9-a(package 可由 host 注入)。

---

## 0. 症狀與直接原因

`library lock digest = sha256(package_lock_content(package))`,而
`package_lock_content` 組的是**工作樹上的原始位元組**:

```rust
content.push_str(&package.code);        // include_str! 讀進來的
content.push_str(&package.data);
```

`include_str!` 在**編譯期直接讀工作樹**。GitHub Actions 的 windows-latest
預設 `core.autocrlf=true`,故未被 `.gitattributes` 覆蓋的檔案以 CRLF 檢出
→ 內容不同 → digest 不同 → 簽入的 golden `.chg` resolve 不過。

**直接原因已修**(`.gitattributes` 補上 `*.conf`、`*.tsv`),但那是**症狀**:
下一個加進套件的副檔名還會踩到,而 R9-a 的注入式套件(host 從使用者磁碟讀)
根本不受 `.gitattributes` 保護。

---

## 1. 其他生態系怎麼做

| | 作法 | 例子 |
|---|---|---|
| **A** | **雜湊發布產物**,不雜湊工作樹 | npm 的 `integrity`(對 `.tgz`)、Cargo registry 的 `checksum`(對 `.crate`)、pip 的 `--hash` |
| **B** | **自家原始碼不雜湊**,用版控身分 | **Cargo 的 path 依賴沒有 checksum 欄位**;git 依賴記 commit rev |
| **C** | **先正規化再雜湊** | Nix 的 **NAR**(丟掉時間戳、排序目錄項、只留檔案/目錄/符號連結與可執行位元)、Go `go.sum` 的 `h1:`(對**排序過的**(檔名, 雜湊)清單) |

A 的關鍵在:tarball 在發布那刻凍結,**根本不存在「檢出變異」** —— 因為從不對
檢出取雜湊。

C 的關鍵在:承認檔案系統狀態帶有**與內容無關的變異**,故先定義一個正規形。

## 2. 本專案落在哪裡

**三者都不是。** 現行是「對工作樹的原始位元組取雜湊」——正是 A/B/C 都在避開的那件事。

### 2.1 一個沒串起來的觀察

R3 落地時判斷「`packages.lock.json` 現在不必做」,理由記在
`演化專案結構與套件載入_v0.1.md`:

> 鎖只在套件來自二進位之外時才有工作做。目前所有套件都是 `include_str!` 內嵌,
> 解析結果完全由引擎版本決定。

**同一個論證也適用於 `.chg` 的 library lock。** 內嵌套件的 digest 本質上是
「引擎版本」的函數——它沒有比「你用哪一版引擎」多說什麼,卻多了一整類脆弱性。
那正是 Cargo 對 path 依賴的判斷(作法 B)。

### 2.2 它是本 repo 唯一繞過 canonical form 的地方

repo 已有正規化紀律:

- `Language` 有 canonical printer(P21),dump 確定性;
- `.chg` 有 canonical dump;
- 節點 id 對 **canonical source** 取雜湊(不是對檔案原文)。

**唯獨套件 digest 對原始位元組取雜湊。** 它不是缺一個新觀念,是既有紀律漏了一處。

## 3. 三條路

| | 作法 | 對應 | 代價 |
|---|---|---|---|
| **甲** | 計算 digest 前**正規化** | Nix / Go | 改變**所有**既有 digest(golden churn);要定義正規形的範圍 |
| **乙** | 內嵌套件改記「引擎版本 + 套件版本」,不用內容雜湊 | Cargo path deps | 改 `.chg` prelude 格式(觸及 P26/P50);外部注入的套件仍需雜湊 ⇒ **兩套規則** |
| **丙** | 維持現狀,靠 `.gitattributes` | —— | 已做;但新副檔名會再踩,且**對 R9-a 的外部套件無效** |

### 3.1 若走甲,正規形的範圍要定

- **只統一換行符**(`\r\n` → `\n`):最小,解掉目前這一類;
- **加上尾端空白 / 檔尾換行**:再擋一類編輯器差異;
- **連檔案順序也納入**(如 Go 的排序 dirhash):徹底,但那等於為套件定一個
  canonical 序列化格式,範圍最大。

值得注意:`package_lock_content` 目前已經**部分**在做正規化——它把 config
解析成欄位再組字串(而不是雜湊 `package.conf` 原文),`requires`/`exports`
也是逐項重組。**只有 `code`/`functions`/`data` 是原文直通。**
所以甲的最小版可能只需要動那三處。

## 4. 裁定

### H-a:走甲(雜湊前正規化)

與 repo 既有的 canonical 紀律一致,也是唯一同時解掉「新副檔名」與
「R9-a 外部套件」兩個場景的作法。乙在外部套件到來後會分裂成兩套規則;
丙已被證明會漏。

### H-b:正規形 = `\r\n` → `\n`,一分不多

判準不是品味,是:**正規化的範圍 = 引擎解析時本來就看不見的差異。**
digest 該是「引擎讀到什麼」的函數,而不是「磁碟上躺著什麼」的函數。

| 差異 | 引擎看得見? | 裁定 |
|---|---|---|
| `\r\n` vs `\n` | **看不見**。`str::lines()` 切 `\n` 並丟掉行尾 `\r`,每行再 `.trim()`。實證:同一份 `.lang` 的 LF 版與 CRLF 版 canonical dump 完全相同 | **正規化** |
| 落單的 `\r` | **看得見**。`lines()` 不把它當換行,行中的 `\r` 活過 `.trim()` | 不動 |
| 尾端空白 | **未經證實不可見**。不是每個消費端都 trim,`data` 更是原文保存 | 不動 |
| 檔案順序 | P50 ③ **明文要求**路徑與檔案邊界進 digest,正是為了偵測重排 | 不動(正規化它會抵觸既有決策) |

不對稱是刻意的:**讓兩份真的不同的內容撞同一個 digest,比 golden churn
嚴重得多**——後者只是雜訊,前者是 P26 的破口。存疑時一律不正規化。

### H-c:不必 bump schema——**因為沒有任何既有 digest 改變**

實作後 `cargo test --workspace` 891 綠、**golden `.chg` 一個字元都沒動**。

這不是巧合,是這個修法的核心性質:repo 的工作樹本來就是 LF(`.gitattributes`
釘著),於是 `lock_normalized` 在正規樹上**就是恆等函數**。它只在工作樹偏離
正規形時才有作用——也就是它本來要解的那個場景。

既然沒有既有 `.chg` 改變值或失效,schema 版本沒有要辨識的東西。

### 附帶:`.gitattributes` 要不要留

**留。** 它現在對 digest 是多餘的,但仍讓 diff 與編輯器行為維持乾淨。
它從「正確性的依賴」降級成「衛生措施」——這正是想要的方向:
正確性不該再靠一份要記得同步維護的副檔名清單。

## 5. 實作

`crates/changeset/src/lib.rs` 的 `lock_normalized()`,施於
`code` / `functions` / `function_sources[].source` / `data` /
`data_sources[].source`。其餘欄位(id、version、路徑、exports)是**解析後**
的值,載入時已逐行 `.trim()`,不需要也不該再處理。

測試:`crates/changeset/tests/lock_digest_normalisation.rs`。每一條「應相同」
都配一條「應不同」的反例,並經突變測試——四個突變(不正規化 / 移除所有 `\r` /
連尾端空白一起吃 / 回傳空字串)各被預期的那條測試殺掉。
