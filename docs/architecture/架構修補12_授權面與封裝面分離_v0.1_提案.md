## 0. 修正目的

`.chg` 的 prelude 目前把**三種變更理由不同、作用域不同**的東西寫在同一份文字裡:

```
changeset evo:n1:
    schema = conlang.changeset/v1
    base_source     = sha256:e3b0c44…      ← ② 疊在哪個 base 上
    base_identities = sha256:b60d365…      ← ②
    library std:core@0.1.0 sha256:7cef96…  ← ③ 環境有哪些套件
    library std:cxg@0.1.0 sha256:337375…   ← ③
    library std:grambank@… sha256:9f8a01…  ← ③
    library std:grammaticalization@… sha…  ← ③

    #0:
        update sign("x").def[syn.category].value = verb   ← ① 這份變更做什麼
```

| | 內容 | 誰決定 | 作用域 |
|---|---|---|---|
| ① | 這份變更**做什麼** | 作者 | 這一份 |
| ② | 疊在**哪個 base** | commit 時的 parent | 這一份 |
| ③ | **環境**有哪些套件 | 安裝了什麼 | **整個專案** |

三者混在一份文字裡,產生三個**已經觀測到**的後果。

### 0.1 後果一:`.chg` 不能手寫

②③ 是 64 字元的雜湊,人無法計算也無法記憶。目前唯一的產生方式是
`change_set_prelude()`,即**每一份 `.chg` 都必須由程式產生**。

### 0.2 後果二:產生物裡的雜湊會過期(**已發生**)

commit `55cb27f` 在同一次提交裡

- 重組了 `std:grammaticalization` 套件(刪 `code/paths.chg`,加 `goals.chg`/`recipes.chg`/`data/weights.tsv`),
- 並加入 `tutorials/en-standard-reconstruction/restore.chg`。

`restore.chg` 內嵌的 ③ 是**套件改動前**算的,於是 `main` 紅燈,由 `e9d0ef6` 以
「更新那一行摘要」修復。差異範圍恰為**一行**。

> 這不是誰疏忽——**把導出值抄進被 diff 的檔案裡,過期是必然**。

### 0.3 後果三:rebase 必須改寫文字

《修補11》§11.1 記錄:rebase 的實作是「**重寫 prelude 的兩行 base digest**」,
且「只放寬不重寫的話新節點過不了 fsck」。

亦即:**同一份 changeset 疊到另一個 base 上,它的文字必須改**——而 rebase 的本質
恰恰是「同一份變更、換一個基底」。文字被迫改動,是因為基底寫在文字裡。

## 1. 觀察:② 在圖裡**本來就推得出來**

P56 之下:

- 邊記著 `from`(parent 的 `NodeId`),
- 節點記著 `snapshot`。

故「這份 changeset 疊在什麼上面」**圖自己知道**。prelude 裡的 ② 是**冗餘**的,
它唯一多出來的作用是 P59 的第一項——`.chg` **單獨**拿到別處時的防掉包。

## 2. digest 移到邊上【P65】

```
Edge {                          Edge {
    from:      NodeId,              from:               NodeId,
    changeset: Option<String>,      changeset:          Option<String>,
}                       ──►         base_digest:        Option<BaseDigest>,
                                    environment_digest: Option<String>,
                                }

BaseDigest { source: String, identities: String }
```

**digest 由「changeset 文字的內容」變成「這條邊的中繼資料」。**

理由:digest 描述的是**這次套用**(疊在哪、環境如何),不是**這份變更做什麼**。
把它放在 changeset 文字裡,等於讓「做什麼」的單一資訊源承載「套用在哪」的資訊。

### 2.1 直接後果:rebase 不再改寫文字

rebase 變成「換邊上的 `base_digest`」,`.chg` **一個字都不動**。

《修補11》§11.1 記錄的「保留 changeset 原文(只換兩行)、不採解析後重新 dump」
這條特別考量隨之消失——因為根本沒有兩行要換。

### 2.2 為什麼 `base_identities` 不能省

`NodeId` 雜湊的是 `snapshot.source()`,**不含身分清單**(故 `add_root` 需要
`RootIdentityConflict` 那道額外檢查)。而 `.chg` 以**穩定 id** 定址,
兩份文字相同、id 不同的文件對它是兩回事。故 `base_digest` 必須是**兩個**,
不能用 `from` 的 `NodeId` 取代。

## 3. 環境鎖分離,但綁定仍在每條邊【P66】

③ 是**專案級**的(你裝了哪些套件),不該在每份 `.chg` 重述。

### 3.1 環境鎖是**物件庫裡的一個物件**,不是設定檔

`crates/persistence` 的 `GraphStore::load` 帶著一句直接相關的約束:

> `libraries` is **deliberately injected by the host**. Library locks inside `.chg`
> remain the authority for replay compatibility; **no state-changing dependency is
> smuggled through hash-external P64 config**.

即:**會改變語言狀態的依賴,不得從雜湊外的 config 溜進來**——那正是 P64 的判準。
故環境鎖**不能**是一個 dotfile 設定;它必須落在雜湊內的一側。

既有機制已經夠用:

```
objects/
    a3f2…   sign「water」
    7b91…   trait「Verb」
    c04d…   **environment lock**        ← 一個普通物件
nodes/<id>/
    edges → { from, changeset, base_digest, environment: c04d… }
```

| | |
|---|---|
| 不新增檔名/位置 | 物件庫(P60)已經在 |
| 自動去重 | 兩份 changeset 同環境 → **共用同一個物件** |
| 綁定精確 | 邊上記雜湊,環境變動前後分得出來 |
| 雜湊內 | 符合 P64 判準,不違反上引註解 |

**授權時**編輯一份人類可讀的工作檔(名稱不影響語意),`seal` 時將其存為物件、
把雜湊寫進邊——與 `.chg` 是**同一個模式**:工作檔不是權威,物件才是。

### 3.2 共用檔案不等於共用綁定

兩份 changeset 可能寫於環境變動前後。故清單內容可共用一個物件,但「當時用的是哪一版」
必須記在**每條邊**上。

| | 存哪 | 為何 |
|---|---|---|
| 套件清單與各自摘要 | `objects/` 裡的一個物件 | 內容相同即自動共用 |
| **當時用的是哪一版** | **邊上的 `environment_digest`** | 每次套用各自綁定 |

### 3.3 刻意不做:把 N 行收成一個「環境雜湊」

曾考慮把四行 library 鎖收成單一 `environment = sha256:…`。**否決**:
對不上時說不出**是哪個套件變了**,而 §0.2 的實例正是單一套件過期。
逐套件的清單是診斷力,不換版面。

(注意:環境鎖**物件本身**仍是逐套件的清單;邊上那一個雜湊只是指向它,
不是把清單壓成一個值。兩者不同。)

## 4. 授權形與封裝形【P67】

```
授權形(人寫)                封裝形(可執行)
──────────────             ─────────────────────────
changeset evo:n1:           .chg 文字   ← **完全相同**
    schema = v1        +    邊上的 base_digest
    #0:                     邊上的 environment_digest
        update …
```

**`seal` 是「算出邊上的兩個欄位」,不是「改寫文字」。** 兩形的 `.chg` 文字逐字相同。

### 4.1 鐵律:未封裝不得執行

`resolve`/`commit` 遇到沒有 `base_digest` 的邊**硬錯**,訊息指向 `seal`。

否則會出現「**有時檢查、有時不檢查**」——比完全不檢查更糟,因為你不知道手上這份
到底驗過沒有。

### 4.2 這才是 §0.2 的解法

digest 改為**按需算出**(seal 時),而非抄寫在被 diff 的檔案裡。套件改版後重新
封裝即可,不會有「檔案裡的摘要對不上實際內容」的中間狀態。

> **注意**:單純把雜湊「搬去另一個檔」**不解決過期**——只是搬到 lock 檔裡過期。
> 解決過期的是「按需重算」,兩件事要分開看。

### 4.3 先例

P49 的**定義文件模式**已經是「一份**沒有 base digest** 的 `.chg`」(`package` 頭、
只收 function)。故「`.chg` 可以沒有 base digest」在解析層**已經成立**;
授權形沿用同一個機制,以 `changeset` / `package` 頭區分,**不新增標記**。

## 5. P59「跨系統流通」的職責移轉【P68】

P59 定 digest 的兩個用途:

| 用途 | 本提案之後 |
|---|---|
| rebase 判定的入口 | **不變**——只是讀邊上的欄位而非文字裡的行 |
| **`.chg` 單獨拿到別處時防掉包** | **改由 bundle 承擔**(見下) |

digest 移到邊上之後,單獨的一份 `.chg` 文字**不再自帶**基底宣告。這是對 P59 的
**明確覆寫**,不得默默發生。取代方案:

```
bundle = .chg 文字  +  邊(含 base_digest / environment_digest)  +  引用到的物件
                                                                    (含環境鎖物件)
```

物件是內容定址的(P60),故打包時只裝對方沒有的——同 `git bundle`。

**流通的單位由「一份 `.chg`」改為「一個 bundle」。** 一份裸 `.chg` 從此只是
授權輸入,不是可流通的成品——與「未封裝不得執行」是同一條線。

## 6. P 系列決策(提案)

| # | 決策 |
|---|---|
| **P65** | **`base_source`/`base_identities` 由 changeset 文字移至邊**:`Edge` 增 `base_digest: Option<BaseDigest>`。digest 描述「這次套用」而非「這份變更做什麼」,故屬邊的中繼資料。**推論:rebase 不再改寫 `.chg` 文字**,《修補11》§11.1 的「保留原文只換兩行」考量隨之消失。`base_identities` **不可**由 `from` 的 `NodeId` 取代——後者只雜湊 `snapshot.source()`,不含身分清單 |
| **P66** | **library 鎖移出 `.chg`,以物件形式存於 `objects/`,綁定記在每條邊**(`environment_digest`)。**不新增檔名或位置**——P60 物件庫已在,且內容相同即自動共用。**不得放雜湊外的 config**:`persistence` 明文「no state-changing dependency is smuggled through hash-external P64 config」,而環境會改變語言狀態,故必須落在雜湊內。共用物件不等於共用綁定:兩份 changeset 可能寫於環境變動前後,故每條邊各記其雜湊。**否決**把 N 行收成單一環境雜湊——對不上時說不出是哪個套件變了,而那正是已發生的失效樣態(物件內部仍是逐套件清單) |
| **P67** | **授權形／封裝形二分**:`.chg` 文字兩形**逐字相同**,`seal` 只算出邊上的欄位。**未封裝不得執行**(硬錯,訊息指向 seal)——「有時檢查有時不檢查」比不檢查更糟。沿用 P49 定義文件模式的既有機制以 header 區分,**不新增標記** |
| **P68** | **P59 第一項用途移轉**:「`.chg` 單獨拿到別處防掉包」改由 **bundle**(`.chg` + 邊 + lock + 物件,物件走 P60 內容定址)承擔。流通單位由「一份 `.chg`」改為「一個 bundle」;裸 `.chg` 只是授權輸入 |

## 7. 遷移成本(據實估計)

| 面 | 影響 |
|---|---|
| `change_set_prelude` | 不再產生 ②③ 行 |

| `rebase_prelude`(修補11) | **整個移除** |

**這是一次大遷移。** 建議若核准,分刀進行並以「既有 628 綠不得變紅」為每刀出口。

## 8. 界線 / 待裁

1. ~~`environment.lock` 的位置與檔名~~ → **已定形(§3.1)**:環境鎖以**物件**存於
   `objects/`,邊上記其雜湊。授權時的工作檔名稱**不影響語意**(非權威),
   可暫定 `environment.lock`。
2. **bundle 的容器格式**——目錄、tar、或 `GraphStore` 的匯出?
   `crates/persistence` 已提供內容定址的 `objects/` 與 `nodes/<id>/`,
   bundle 應是其**子集匯出**(只裝對方沒有的物件),而非另一種格式。細節待裁。
3. **可選的 `base = @<node-id>` 意圖宣告**:寫了則 seal 驗證「我打算疊在節點 X 上」
   與實際 parent 相符,防「疊錯地方」。**不取代** `base_digest`(理由見 §2.2)。
   建議允許但可選。
4. **授權形能否進版本控制而不封裝**?若可,repo 裡會同時存在兩種狀態的 `.chg`,
   需定「什麼時候必須是封裝形」。
5. 本提案**未觸及** Step 17 缺口 3/4、模組 A/E、應用層。

## 9. 附:通讀 `crates/persistence` 的一項發現(不屬本提案,但影響 P60 的估計)

P60 曾註記 identity manifest「因位址位置式(`Signs(n)`)而不易共享……最簡作法是
**逐節點整份存**,或改用非位置式定址」。落地採了前者:

```rust
let identities = self.put_object(document.manifest_json()?.as_bytes())?;   // 整份一個物件
```

後果可精確描述:

| | 每代新增的儲存量 |
|---|---|
| sign / trait 物件 | **O(改動量)** ✅ |
| identity manifest | **O(語言大小)** —— 位址一位移,整份即新物件 |

故 P60 宣稱的「空間由『節點數 × 語言大小』降為『節點數 × 每代改動量』」
**只兌現了一半**。現階段不痛(`en-standard` 僅 30 個 sign、16 KB),
但在數千 sign × 數十代時 manifest 會主導。

**候選解**(P60「另議」的另一支):**位址不存,id 跟著 sign 物件走**。
清單的四個欄位中,位址／kind／parent 都能由正規文字走一遍算出,
**只有 id 非存不可**;把 id 序列併入 sign 物件後,位址位移的問題整個消失,
且不變的 sign 因文字與 id 皆未變而**仍然共用**。重建由
`from_edit_parts` 的既有驗證把關(它已在驗「清單與 `.lang` 逐位址相符」)。

此項**與本提案正交**,列此僅為記錄;是否採行另案裁定。
