## 1. 問題陳述

`$self` / `$slot.` 的解析原本**沒有單一實作**。八個位置各自以 `strip_prefix`
比對,接受的子集互不相同:

| 位置 | 接受的形 | 維度 | 路徑長度 |
|---|---|---|---|
| 維度規則 RHS / guard | `$self.<dim>.<path>` / `$slot.<n>.<dim>.<path>` | 四維 | 任意 |
| `slot_features:` 值 | 只 `$slot.<n>.syn.<f>` | 鎖死 syn | 恰 1 段 |
| `constraints:` 欄位運算元 | `$slot.` **可省** | 鎖死 syn | 恰 1 段 |
| `constraints:` 順序運算元 | **完全不解析**,整串當 slot 名 | — | — |
| case scrutinee | `$self.` **可省**,省略後首段被當 slot | `.phon` 重載(見後果 4) | 恰 2 段 |
| `token_scalar` | `$self.` **可省** | 四維 | 恰 2 段 |
| application 實參 | `{$self}` / `{$slot.n}` / `{n}` | — | — |
| phon 模板 / sem role | **只有** `{n}` 裸名 | — | — |

三個後果:

1. **同一件事多種拼法。** `stem.syn.number` 與 `$slot.stem.syn.number` 在
   constraint 位置等價;`{stem}` 與 `{$slot.stem}` 在實參位置等價,但在 phon
   模板位置只有前者合法。
2. **首段猜測。** 裸形之下,`stem.phon`(讀 slot)與 `syn.number`(讀自己)
   只能靠「首段是不是維度關鍵字」決定主體——一個**名為 `syn` 的 slot 會被
   靜默讀成自己的 syn 維**。
3. **正確性靠記憶力維持。** rename 需要三個重寫器(裸形 / `$slot.` / `{…}`),
   而「哪個 `SignItem` 該套哪幾個」是一張人工維護的對應表。實測其中一格是錯的:
   constraint 運算元寫成顯式 `$slot.` 形時 **rename 完全不會改到它**,留下懸空引用。
4. **`.phon` 被重載成兩種運算。** 同一個 `<主體>.<維度>` 記法,`$slot.N.phon`
   **有**欄位時比欄位值、**沒有**欄位時改比本體樹成員關係。兩種語意靠「有沒有
   欄位」這個難以察覺的差異區分,而範疇比對在全庫早有自己的記法(`[Trait]`)。
   同時 `$slot.N.<非 phon 維>.<欄位>` 靜默永不匹配——不是規格如此,是實作債:
   規格中唯一相關的出現是一行**範例**,而 `FillerSnapshot` 一直帶著四維欄位。

`{…}` 的處理另外散在七處,其中三處是幾乎相同的字元迴圈,只差命中後做什麼。

## 2. 裁定的語法

```text
Reference     := Subject ( '.' Dim ( '.' Path )? )?
Subject       := '$self' | '$slot' '.' Name
Interpolation := '{' Subject '}'
Dim           := 'phon' | 'syn' | 'sem' | 'prag'
Path          := Name ( '.' Name )*     (承 P22 / 修補05 §3.5,經 ⑨ 縮減)
```

**兩個記號是正交算子,不是競爭的拼法:**

- **`$` 只建立引用,不求值。** `$slot.stem.syn.number` 是一個指名——「slot `stem`
  的填充者的 syn.number 這個欄位」。規則拿它去比對或寫入。
- **`{…}` 要求求值後把結果嵌在這裡。** `/{$slot.stem}+s/` 是「把 `stem` 的填充者
  算出來,結果放這個位置」。

兩者可以疊:**括號內永遠是一個引用**。`{$self}` 因此不是特例,而是這條規則的
一般情形;`{stem}` 才是漏掉 `$` 的那個。

括號內只寫主體、不帶維度與路徑——**嵌入什麼型別由括號所在的位置決定**
(phon 模板要 surface、sem role 要語意節點),不由引用自己宣告。

## 3. 決策點

### ① 主體一律顯式,裸寫法不相容

**選擇**:`$` 不可省略,`{…}` 內也一樣。舊的四種裸寫法一律拒絕:

| 舊 | 新 |
|---|---|
| `before(subject, object)` | `before($slot.subject, $slot.object)` |
| `equal(a.syn.number, b.syn.number)` | `equal($slot.a.syn.number, $slot.b.syn.number)` |
| `case stem.phon:` | `case $slot.stem.phon:` |
| `case syn.number:` | `case $self.syn.number:` |
| `/{stem}/`、`agent = {subject}`、`f({stem})` | `/{$slot.stem}/`、`agent = {$slot.subject}`、`f({$slot.stem})` |

**理由**:裸形是「首段猜測」的唯一成因(見 ②),也是三個 rewriter 的唯一成因
(見 ③)。保留相容等於保留那兩個問題。

**代價**:`base_source` 與套件 digest 全數改變,既有 `.chg` 需 rebase。
**可逆性**:低。回退需再一次全庫遷移與 re-bless。

### ② 移除首段猜測

**選擇**:刪除「首段是維度關鍵字 → `$self`,否則 → 同名 slot」這條消歧規則。

**理由**:它使 slot 命名空間與維度關鍵字相撞。一個名為 `syn`/`phon`/`sem`/`prag`
的 slot 在裸形下不可定址,且失敗方式是**靜默讀到別的東西**而非報錯。

**證據**:`reference_surface.rs::a_slot_named_after_a_dimension_is_addressable`
——`$slot.syn.phon` 現在確實指向名為 `syn` 的 slot。

### ③ rename 收斂為單一掃描

**選擇**:刪除 `rewrite_slot_operand` / `rewrite_slot_accesses` /
`rewrite_slot_template` 三個重寫器與其呼叫點對應表,改為單一
`reference::rename_slot`。

**理由**:主體顯式之後引用只有 `$slot.<name>` 一種可掃形狀,而 `{$slot.<name>}`
也是同一形狀——整串運算元、內嵌於本文、模板插值三者可共用同一次掃描。

**附帶修正**:constraint 運算元的顯式 `$slot.` 形先前不被 rename,已修;
迴歸測試 `primitive_edits.rs::slot_rename_rewrites_an_explicitly_sigilled_constraint_operand`
已驗證在舊行為下會紅。

### ④ 括號內容不帶維度與路徑(擁有者已通過)

**選擇**:`{…}` 內只允許 `$self` 或 `$slot.<name>`,不允許 `{$slot.x.syn.f}`。

**理由**:`{}` 的語意是「求值並嵌入」,而嵌入什麼型別是**位置決定**的。
若允許括號內帶維度,同一個位置就會有兩個型別來源(位置與引用),必須再定
優先序。

**未決**:`{$self}` 寫在 phon 模板裡(會遞迴)目前落到 unknown-slot 診斷,
而非專屬錯誤碼。見 §5。

### ⑤ `{…}` 掃描收斂為單一實作

**選擇**:`scan_interpolations` / `substitute_interpolations` /
`render_interpolation` 三個函數取代原本散在七處的括號處理(其中三處是同型
字元迴圈)。

**保留的分工**:括號**良構性**(未閉合、巢狀、空)仍由 `template_references`
檢查,括號**內容**的良構性交給 reference。兩者是不同的錯誤類別。

### ⑥ 呼叫點宣告子集,不自行比對

**選擇**:每個位置宣告一份 `RefSpec`(允許哪種主體、維度政策、路徑政策),
由單一 `reference::parse` 執行。目前五份公開 spec:
`SLOT_SYN_FEATURE` / `CONSTRAINT_OPERAND` / `CONSTRAINT_SLOT` / `SCRUTINEE` /
`SUBJECT_ONLY`。

**理由**:接受/拒絕的集合成為可讀的宣告,而非散落的 `strip_prefix` 串接。
新增一個位置時,「它接受什麼」是一次宣告而不是一次重新實作。

### ⑦ 兩處行為收緊,一處技術債移除,一處記法去重

**收緊(兩處)**:

- **非法 scrutinee 是 compile 錯誤**(新增 `CASE_INVALID_SCRUTINEE`)。先前
  `case head.phon:` 能通過 compile,只在求值時靜默不匹配。
- **constraint 運算元解析失敗不再退回「把整串當 slot 名」**。該 fallback 會讓
  裸寫法靜默續存,使 ① 的遷移落空。

**移除技術債(一處)**:case scrutinee 先前只處理 `$slot.NAME.phon`,
`$slot.NAME.<其他維>.<欄位>` 靜默永不匹配。查證後:**沒有任何規格規定
scrutinee 只收 `.phon`**——規格中唯一相關的出現是
`共時lang_FP_expression_typed_case_constraint_v2.md` 的一行**範例**,不是規則。
而 `FillerSnapshot` 一直帶著四維的純量欄位,只是 scrutinee 沒去讀。
現已補上:`$slot.NAME.<dim>.<field>` 讀填充者的純量欄位,與
`$self.<dim>.<field>` 對稱。

**記法去重(一處;擁有者裁定,推翻本檔 v0.1 初稿)**:
`$slot.NAME.phon`(無欄位)先前**兼差**當範疇比對——同一個 `<主體>.<維度>`
記法,有欄位時比欄位值、沒欄位時比本體樹成員關係。已移除。

理由:範疇比對在全庫早有記法,就是 `[Trait]`——slot 約束 `head [RefEntity]`、
function 參數 `verb [Verb]`、guard `$self == [Trait]`、`$slot.NAME == [Trait]`
(`synchronic::Guard::SlotIsA`,早已實作)皆然。讓 `.phon` 再兼一個,等於同一
件事有兩種寫法,且第二種靠「有沒有欄位」這個難以察覺的差異來區分。

**現在的分工**:

| 要比什麼 | 寫法 |
|---|---|
| 欄位的**值** | `case $slot.NAME.<dim>.<field>:` + `== VALUE:` |
| 本體樹的**範疇** | `case:` + `$slot.NAME == [Trait]:` |

`SCRUTINEE` spec 的路徑政策因此改為**必填**——`$slot.head.phon` 缺欄位,在
**compile 期**就被擋下,而不是通過編譯後在求值時才炸。連帶移除已無適用情形的
`CASE_UNKNOWN_CATEGORY` 診斷(equals 分支不再拿 trait 名當期望值)。

出口:`reference_surface.rs` 的
`a_dimension_without_a_field_is_not_a_category_test` /
`a_category_test_uses_the_bracket_guard_form` /
`a_slot_scrutinee_may_read_a_scalar_field_not_only_phon`,
以及 `reference.rs::a_scrutinee_without_a_field_is_rejected_by_the_spec`。

### ⑧ 暫不納入 `.chg` function 層(理由已修正)

**選擇**:`.chg` function 的 guard 主體(`x.syn.category`)本次不動。

**「function 參數」是什麼**(查證結果,`crates/changeset/src/function.rs`):

- 宣告是 `FunctionParam { name, constraint: Option<String> }`,寫成
  `function F(verb [Verb], tense, delta):`——約束語法與 slot 的 `[Trait]` 相同。
- 綁定是 `BTreeMap<String, String>`:**參數值是字串**。實參可以是 sign selector
  (`sign("go")`),也可以是純量字面值(`FUTURE`、`Aux`、`0.2`)。這是與 slot 的
  第一個實質差別——**slot 一定是 sign**。
- 求值時 `rewrite_guard` 把主體識別字**代換成 `$self`**,再交給
  `conlang_language::synchronic::guard_matches_sign`——**`.lang` 的同一個求值器**。

**故先前寫的「主體命名空間不同」是錯的。** function 層根本沒有自己的主體語意,
它已經借用 `.lang` 的 `$self`;差別只在**表面拼法**(`x` vs `$self`),由一次
文字代換抹平。

**這個代換帶來一個可觀察的限制**:因為 `$self` 是單數,一句 guard 只能有一個
主體——`FunctionError::GuardMultiSubject` 明確拒絕跨參數的 guard。若參數改以
一級引用拼寫(如 `$arg.verb.syn.category`),多主體 guard 就有機會表達。

**真正的未決問題**因此不是「參數與 slot 是不是同一種東西」(不是——參數可綁
純量、生命期只在一次求值內),而是:**參數引用要不要有自己的 sigil**,
以及那是否應同時解除單主體限制。這需要 P49/P52 的擁有者一起看,故本次不動。

**代價**:`.chg` 側仍有一套無 `$` 的主體記法,與 `.lang` 側不一致。

### 6.1 語料庫實際用到的形狀

全庫(`.lang` / `.chg` / Rust fixture / md)共 **201 個 `$` 引用**:

| 面向 | 分佈 |
|---|---|

### 6.2 查找端怎麼用這條路徑

`read_self` 是 `sign.project(dim).get(&"<dim>.<path>")`,`read_slot` 是
`FillerSnapshot::scalar(dim, path)`——**兩者都以整條路徑當字串鍵查表**。

量測(`measure_what_the_path_segment_actually_supports`):

| 情形 | 結果 |
|---|---|
| 宣告 `a`,引用 `$self.syn.a` | 讀到 |
| 宣告 `a.b`,引用 `$self.syn.a.b` | 讀到 |
| 宣告 `a[k]`,引用 `$self.syn.a[k]` | 讀到 |
| 宣告 `t~tone`,引用 `$self.syn.t~tone` | 讀到 |
| 宣告 `a`,引用 `$self.syn.a[0]` | **讀不到**(Unmatched) |
| 宣告 `a.b`,引用 `$self.syn.a` | **讀不到** |
| 宣告 `a`,引用 `$self.syn.a.b` | **讀不到** |

**結論:`Path` 段在查找端是不透明字串鍵。** 逐字相同就命中,否則不命中;
`.` / `[k]` / `~tier` 只是鍵名裡的字元,沒有索引、沒有上行、沒有下行。
`[k]` 與 `~tier` 因此**不是**「支援索引與 tier 導覽」,只是允許這些字元出現在
鍵名裡。

### 6.3 什麼形狀的路徑能合法存在

`$slot.` 側走完整 compile(`measure_the_slot_side_and_the_closed_list`),
故受 P71 封閉清單約束:

| 路徑 | 結果 |
|---|---|
| `syn.alignment.a` / `sem.aspect.a` / `prag.evidence.a` | 讀到(三個非 phon 維對稱) |
| `syn.alignment.a.b`(三段) | 讀到 |
| `syn.alignment.a[k]` / `syn.alignment.t~tone` | 讀到 |
| `syn.made-up.a`(不在清單上) | **compile 擋下** |

而封閉清單之外的自造欄位一律走 `feature:`,其名稱是**單一識別字**。
`phon:` 區塊根本不收 `field = value`(承 P71 增修 C)。

**綜合**:多段路徑現實中的唯一來源是**套件座標前綴**
(`syn.alignment.…`、`sem.aspect.…`、`prag.evidence.…` 等 30 條);
`[鍵]` 與 `~tier` 雖可通過驗證,卻**沒有任何生產者**——`feature:` 產不出、
封閉清單的座標也不用它們。

### 6.4 `parse_path` 驗證買到什麼

`PathPolicy::RequiredValidated` 對引用的路徑跑 `parse_path`。既然查找端只做
字串比對,這道驗證的作用**不是**保證可解析,而是把「畸形路徑」從**靜默永不
匹配**變成**明確錯誤**——例如 `$self.syn.a..b` 現在報 `BadPath`,而沒有驗證時
它只會是一個永遠查不到的鍵。這與 ⑦ 的兩處收緊同一性質。

### 6.5 由量測導出的決策點

**⑨ `Path` 段縮減為點分名段。已採納 (b)(擁有者裁定)。**

裁定前的現況是文法允許三種段(`.名` / `[鍵]` / `~tier`)、任意段數,而:

- 語料庫 191/191 只用單段純識別字,Def lhs 側同樣零使用;
- `[鍵]` 與 `~tier` 零生產者——`feature:` 產不出(名稱是單一識別字),
  封閉清單的套件座標也不用;
- 查找端不解讀結構,故三種段的表達力**完全相同**(都只是鍵名字元);
- Step 13 的欄位定址(`identity.rs`)本來就只收 `Name` 段,其餘段是死分支。

曾考慮但未採納的兩案:**(a) 維持現狀**——成本是文法承諾了查找端沒兌現的
能力,讀 `'[' Key ']'` 會合理預期有索引語意;**(c) 保留文法並補上結構語意**
——那是加功能不是修語法,需要使用案例,目前零。

**落地**:

```text
Path := Name ( '.' Name )*
```

`PathSeg` 只剩 `Name` 一個 variant;`identity.rs` 的死分支移除;
