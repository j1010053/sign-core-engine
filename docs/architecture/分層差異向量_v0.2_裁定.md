## 0. 問題

> 本節記的是**裁定當下(2026-08-07)的狀態**。§6 第 1–2 步落地後,下表兩列
> 都已不再全零——留著是為了保存病灶的原貌與量測數字。

當時的 `diff_vector` **只走 `signs`**(`traits` 出現 0 次),故:

| 改動 | 現行 diff |
|---|---|
| 一條音變規則(`global trait Core` 底下) | **全零** |
| `trait Noun` 加一行 `belongs Animate` | **全零** |

第二個尤其嚴重:實測 `sign A: belongs MyNoun` 在 `MyNoun` 加了 `belongs Animate`
之後,閉包由

```
["MyNoun", "Nominal", "AgreementBearer", "Entity", "Semantic"]
```

變成

```
["MyNoun", "Nominal", "AgreementBearer", "Entity", "Semantic", "Animate", "Physical"]
```

——所有 `belongs MyNoun` 的詞,role 約束、slot 授權、語意型別統統跟著變,而 diff 是 0。

連帶後果(實測):**一次音變之後兩節點的互通度是 `1.0`**,方言分群完全看不見它。

### 與規格的落差

§6.1 原文:

> 音系距離、詞彙距離、型態距離、句法距離各一分量(貢獻不同:詞彙差異最傷互通,
> **規則性音變其次**)
>
> 差異 = 兩點到共同祖先的 **ChangeSet 距離**的分層投影(**差異是果,ChangeSet 是因**)

「對齊鍵:兩狀態的 sign 以 `SignId` 對齊」那句只規定 **sign 怎麼對齊**,
沒有說「只算 sign」。故現行實作**未達規格**,§6.1 又標【M】(MVP 範圍)。

## 1. 裁定 ①:階層向量,外層仍是四維

**外層維持 phon / syn / sem / prag 四維**(§6.1 的「各一分量」不變),
每一維**內部**再分子節點。

```
DiffVector
  ├─ phon   ├─ signs      詞的音韻投影
  │         └─ rules      phon 規則
  ├─ syn    ├─ signs
  │         ├─ rules
  │         └─ slots      (二級分類,見下)
  ├─ sem    ├─ signs
  │         ├─ rules
  │         └─ senses
  ├─ prag   └─ …
  └─ structural           跨維者(belongs / trait 引用 / 無維 Def)
```

**為什麼不是「另立 `rules` 分量」**:那會讓「音系距離」散在兩個欄位,
§6.1 的「音系距離**一個**分量」就不成立。階層化保住外層語意,又不把兩種東西
壓進同一個整數。

**為什麼不併進單一整數**:`phon: 3` 若同時含「3 個詞變了」與「3 條規則變了」,
那個數字就說不出自己是什麼。

二級分類(slots / senses / …)**按需長出**,不預先造滿——依《共時lang語法與
資料貼合度》「不先造無消費者語法」。

### 1.1 落地補充:子節點的軸是**宣告處**(2026-08-11)

上圖把子節點畫成按**項目種類**分(signs / rules / slots / senses),但 §3 要補的
`traits` 容器有一塊圖上沒有位置:**trait 攜帶的非規則內容**(Def、slot、義項)。
第 2 步實作因此把每一維的子節點定為三個,軸是**這段內容宣告在哪裡**:

| leaf | 收什麼 | 對齊鍵 |
|---|---|---|
| `signs` | sign 上宣告的該維內容(**含 sign 自帶的規則**) | `SignId` |
| `trait_content` | trait 上宣告的該維內容(**不含規則**) | trait 名 |
| `trait_rules` | trait 上宣告的該維規則 | `RuleId`(P25) |

`structural` 同樣分 `signs` / `trait_content`,但**沒有** `trait_rules`
——`Rule::dim` 是 `Dim` 不是 `Option<Dim>`,跨維的規則不存在,擺一個恆為零的
欄位會被下游當成「這裡沒事發生」而加總。

**為什麼不照圖上的種類分。** 種類分會把 trait 的 slot 與 sign 的 slot 併進同一
個數字,而這兩件事的**範圍差三個數量級**:改一個 trait 上的 slot 經 `belongs`
閉包影響一整片詞,改一個 sign 只動那一個詞。§6.1 明說詞彙差異與規則性音變的
權重不同——分不開就沒得加權。裁定 ① 拒絕把詞與規則壓進同一個整數,是同一條
理由;這裡只是把它推到 trait 上。

**命名要防的誤讀:`syn.trait_content` 不是「syn 的 trait」。** 按 P38 v0.2,
分類樹是**單一且維度中立**的,`TraitDef` 沒有維度欄位,沒有 syn trait 或
sem trait 這種東西。維度一律來自**項目自己**(與 sign 共用同一個
`item_dimension`)——sign 同樣不是 syn 或 sem,`signs` leaf 做的是一模一樣的
投影動作。**trait 作為分類節點的本體住在 `structural.trait_content`**:
`belongs` 邊沒有維度,所以它在跨維那一格。

## 2. 裁定 ②:不硬找分母,發原始計數

**引擎不做正規化。** 理由:

- 「以 `aligned` 為分母」這個框架**本來就對生滅無效**——新增的詞不跟任何東西
  對齊,現行實作也是把 `born`/`died` 另計;
- §6.4 已裁定**引擎不定義評分合成公式**。挑一個分母就是挑一個公式。

每個葉節點發**四個原始數**:

| 欄位 | 意思 |
|---|---|
| `both` | 兩邊都有(依 id 對齊) |
| `changed` | `both` 之中內容不同的 |
| `only_before` | 只在前者(滅) |
| `only_after` | 只在後者(生) |

呼叫端要什麼比例自己算:

```
比例式   = changed / both
Jaccard  = (changed + only_before + only_after)
           / (both + only_before + only_after)
總數     = both + only_before(前) / both + only_after(後)
```

Jaccard 是**呼叫端的選擇**,不是引擎的裁定——引擎給的四個數足以算它,
也足以算別的。

## 3. 裁定 ③:補整個 `traits` 容器

不只補規則。`trait` 的 `belongs`、Def、slot 一併納入——理由見 §0 的第二個例子:
改一行 `belongs` 影響數百個詞的投影,只補規則的話那個例子仍然隱形。

`trait` 與 `sign` 以**名字**對齊(`TraitDef` 無 `SignId` 等價物;
名字在 catalog 層已強制唯一,`ONTOLOGY_DUPLICATE_TRAIT`)。
規則另有穩定 `RuleId`(P25),故規則層可精確對齊。

### 3.1 裁定:trait 的規則傳播到 sign **不重複算**(丙)

**問題**:`trait Noun` 有一條規則,100 個 sign `belongs Noun`。改那條規則,
差異該記 **1**(改在宣告處)還是 **100**(影響到的詞數)?

| | 作法 | 得到什麼 | 失去什麼 |
|---|---|---|---|
| **甲** | 只算宣告處 | 一次編輯 = 一個計數,不膨脹 | 看不出影響範圍——改一個沒人用的 trait 與改 `std:core` 的根 trait,數字一樣 |
| **乙** | 算投影(逐 sign) | 反映實際衝擊 | 一次編輯灌出 100 個計數,淹掉其他所有變動;且 trait 改動與 sign 改動再也分不開 |
| **丙** | 宣告處算 1,**另記影響到幾個 sign** | 兩件事都在,且分得開 | 多一個欄位 |

**裁定丙(擁有者 2026-08-09)。** 宣告處算 1,**另記影響到幾個 sign**。

它與裁定 ① 的階層形狀天然相合(外層是「改了什麼」,內層附「波及多廣」),
而閉包本來就要算,取得影響數幾乎零成本。

「改了幾處」與「影響多廣」是**兩個問題**,壓成一個數字必然有一邊說謊——
這與裁定 ① 拒絕把詞與規則壓進同一個整數是同一條理由。

#### 落地細節

`traits` 底下的每個葉節點,除了 §2 的四個原始計數,再加整體與逐事件兩層
**影響範圍**:

| 欄位 | 意思 |
|---|---|
| `reach_before` | 前狀態下 `belongs` 閉包涵蓋到此 trait 的 sign 數 |
| `reach_after` | 後狀態下同上 |
| `event_reaches.changed` | 每個 changed 事件各自的 `{ before, after }` |
| `event_reaches.only_before` | 每個刪除事件各自的 `{ before, after: 0 }` |
| `event_reaches.only_after` | 每個新增事件各自的 `{ before: 0, after }` |

**為什麼是兩個數而不是一個。** 「改一條 `belongs` 邊」本身就會移動閉包,
前後的波及面不同;只發一個數就得先挑「用哪一邊」,那又是一次隱形的
合成選擇(§6.4 已裁定引擎不做那件事)。發兩個,呼叫端要 max、要 union
大小、要平均,自己決定。

`reach_before/reach_after` 仍是整個 leaf 的**受影響 sign 聯集大小**;它適合顯示
「這批改動總共碰到多少詞」。`event_reaches` 則保留每個事件自己的波及面,供
measure 加總。兩者不能互換:九個各碰一詞的事件,聯集是 9,逐事件總和也是 9;
若誤算成「9 個事件 × 聯集 9」就會膨脹成 81。

**`reach` 不是差異分量。** 它是**旁註**,不參與 §2 的 `both`/`changed`/
`only_*` 四元組,也不該被下游當成第五個計數加總——否則就退化成乙,
一次編輯照樣灌出上百個計數。這一點在型別上要看得出來
(獨立欄位,不與四元組同層)。

**零波及不等於沒改。** 沒有任何 sign `belongs` 某 trait 時 `reach` 是 0,
但 `changed` 仍是 1——「改了一個沒人用的 trait」與「沒改」必須分得開。
這是丙相對於乙的全部意義,測試要守住它。

#### 落地時補的四個判斷(2026-08-11,第 3 步)

§3.1 沒說死的地方,實作時各挑了一個並在此記下:

1. **leaf 層級的 reach = 聯集大小,不是逐 trait 相加。** 一個詞同時 `belongs`
   兩個被改的 trait 時它是**一個**受影響的詞;相加會說成兩個,那正是裁定乙
   的膨脹病換一個地方發作。
2. **只有「這個 leaf 記到事件的 trait」進 reach。** 兩邊都沒動的 trait 有多少
   詞 `belongs` 它,跟這次差異無關。推論:`counts.is_identical()` 時 reach 恆為
   `(0, 0)`,故 reach 不影響 `is_identical`——它是旁註,不是分量。
3. **生滅的 trait 依內容所在的維歸戶,並一律進 `structural`。** `both` /
   `only_before` / `only_after` 是 trait **集合**的性質,五個 leaf 必然相同
   (同 `signs` leaf);若 reach 也跟著五份都算,一個只帶 phon 內容的 trait
   被刪掉時連 sem 的波及面都會記上一筆。分類節點的生滅本身是分類樹的改變,
   所以無論帶不帶內容都進 `structural`。
4. **`global trait` 的 reach = 全部的詞。** global trait 是**自動引用**的
   phon-rule macro(P6),沒有任何詞需要 `belongs` 它。只數 `belongs` 閉包會
   讓一條全語言音變——§0 的第一個例子、最該被看見的那種改動——報出 0 的
   波及面。一個結構上永遠是 0 的波及面比沒有這個數字更糟。

閉包本身走 `OntologyRegistry`(菱形去重、循環安全已在那裡解決過一次),
不另寫一套,否則兩邊對「涵蓋」的定義會慢慢分岔。

#### 規則搬家與換維

trait 規則仍以 `RuleId` 對齊。相同維度下,規則內容或 `declared_in` 改變都算
一個 `changed`;逐事件 reach 的 before/after 分別取舊、新 trait 的波及面。
若同一 `RuleId` 換維,它在舊維是 `only_before`,在新維是 `only_after`,不會把
新增誤記回舊 leaf。整體 touched 集合也分 before/after 維護,所以搬家不會把
另一狀態不存在的波及面混進聯集。

## 4. 裁定 ④:先忠實計數,權重之後再說

引擎的責任到「**數出來**」為止;「一條規則值多少」是 measure 的事(§6.4)。

實作完成後 `ExploratoryHeuristicV1::suggested()` 的係數要重新校準——
目前那組是在「規則變動恆為 0」的前提下訂的。校準時要留意一個實際約束:
**若加一條音變就讓互通度掉到預設閾值以下,則每演化一步就分裂一次方言群,
分群功能等於報廢。**

### 4.1 校準結果(2026-08-11,第 4 步)

`DimensionWeights` 多兩個係數,語意是「**這種間接改動,對它波及到的每個詞
造成多少傷害**」,以「那個詞整個換掉」為 1.0:

| 係數 | 值 | 理由 |
|---|---|---|
| `trait_rule` | 0.25 | §6.1「規則性音變**其次**」的量化。音變改的是怎麼唸 |
| `trait_content` | 0.5 | 改分類/slot/義項,改的是那些詞**是什麼**,比音變重 |

間接傷害 = `係數 × Σ max(event.before, event.after)`(逐事件取前後 max——
§3.1 說了合成方式由呼叫端決定,measure 就是呼叫端)。**逐事件乘 reach 是關鍵**:
否則一條作用於全語言的
音變與一條只碰三個詞的音變會得到同一個數字,而互通度問的正是「有多少詞聽不懂」。
同時也不能先取 leaf 聯集再乘事件數,否則互不相交的局部事件會形成 Cartesian
product,把九個各碰一詞的改動錯算成九個各碰九詞。

代進 §4 的約束(N 個詞、一條波及全部的音變):

```
相異度 = w_phon × 0.25 × N / ((Σw + w_bd) × N) = 2 × 0.25 / 10.5 = 0.0476
互通度 = 0.952        預設閾值 0.6
```

餘裕:同一個 changeset 裡 **8 條音變仍同群、第 9 條才切開**。一步一條音變的
演化鏈永遠不會自己裂開(§4 的約束成立),而一次九條的躍進被判成方言分化是
合理的。這個邊界由 `query/tests/grouping.rs` 的
`the_calibration_margin_sits_between_eight_and_nine_sound_changes` 釘住——
係數被調重時先崩的是它。

**兩個已知的粗糙處**,都記在 `ExploratoryHeuristicV1::suggested` 的文件裡:

1. **傷害以規則節點為單位。** 一個 P46 結構化 block(`rules:`/`Then:`/`Else:`)
   不論裝幾條語句都是一個 `Rule` 節點,算一個事件——十二條語句塞進同一個
   block,傷害與一條相同。這是葉節點粒度決定的(裁定 ① 的階層到 `rules`
   為止,不下探規則內部),換係數補不了。
2. **trait 的生滅只從 `structural` 算一次。** `trait_content` 的 `only_*` 是
   trait **集合**的性質、五個 leaf 數字相同,逐維相加會讓「新增一個 trait」的
   傷害取決於它碰巧寫了幾個維度的內容。四維因此只取各自的 `changed`。

## 6. 實作順序建議

1. ✅ **已落地** —— `diff.rs`:階層結構 + 四個原始計數,**先只補 sign 層**
   (形狀改完、既有語意不變);
2. ✅ **已落地** —— 補 `traits` 容器(規則 + belongs + Def + slot):
   `DimensionDiff.trait_content`(依 **trait 名**對齊,不含規則)、
   `DimensionDiff.trait_rules`(依 **`RuleId`** 對齊,只收 trait 宣告的規則)、
   `StructuralDiff.trait_content`(trait 間的 `belongs` 與
   `global` / `marker` / `type_params` 標頭)。
   子節點的軸與命名理由見 **§1.1**;
3. ✅ **已落地** —— 補 §3.1 的 `reach_before` / `reach_after`(裁定丙),並加入
   `event_reaches`:trait 那側的 leaf 型別改為
   `TraitDiff { counts, reach_before, reach_after, event_reaches }`
   ——reach 與四元組**同層並列而非塞進 `DiffCounts`**,型別上就看得出它不是
   第五、第六個計數。落地時補的四個判斷見 §3.1;
4. ✅ **已落地** —— 重新校準 `ExploratoryHeuristicV1`:新增兩個係數
   `trait_rule = 0.25`、`trait_content = 0.5`(「其次」的量化,故 < 1.0),
   規則與 trait 內容的傷害 = **逐事件 Σ max(before, after) × 係數**(見下);
   §4 的硬約束由測試釘住;
5. ⏸ wire 與前端 v2 延後;本次保留既有 `UI_SCHEMA_V1`。

1 與 2 之間所有既有測試應維持綠(形狀變、數字不變),那是切分的用意。
**實測如此**:第 1 步只有出境轉換處(`app/src/wire.rs` 的 `DiffSummaryV1::from`)
需要跟著改——它把 leaf 的 `changed` 攤平回舊欄位,送出去的數字一個都沒變,

### 6.1 第 2 步的落地筆記

**`trait` 的項目住在 `Block` 裡,不直接掛在 `TraitDef` 上**(`TraitDef.blocks`,
P27 的 `==` 分塊)。故 `.chg` 要對 trait 加一行 `belongs`,位址得寫到塊:

```
insert into trait("LocalNoun").block[0] at end:      ✅
insert into trait("LocalNoun") at end:               ❌ EditError::ParentKind
```

這與 `sign`(`SignDef.items` 是平的,可直接 insert)不對稱,但那是資料模型
的既有事實,不是 diff 這一刀造成的。

**P46 結構化 phon 規則的 `body` 是空的。** `rules:` / `Then:` / `Else:` 那種
寫法會把內容放進 `Rule.phon_block`,`Rule.body` 留空(見 `Rule.phon_block`
的註解)。改一條這種規則要走 leaf 位址:

```
update trait("Core").block[0].rule[0].leaf[0].body = a => b / #_    ✅
update trait("Core").block[0].rule[0].body = a => b / #_            ⚠ 見下
```

⚠ 後者**目前不報錯也不生效**(寫進一個 printer 不看的欄位,canonical
round-trip 後消失)。這是編輯層的洞,不是 diff 的——diff 忠實地報告
「文件沒變」。已另記,待修。
