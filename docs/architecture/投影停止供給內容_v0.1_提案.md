## 0. 現況與問題

第 1、2 步已落地:警告就位、std 的 103 個 `belongs` 補上了顯式引用。
第 3 步要把**投影的內容那一半**關掉,讓 trait 內容只從展開來。

**實測:把 `effective_sign` 改成原樣回傳,`cargo test --workspace` 從 115 綠掉到 54 綠。**

倒掉的不是零星測試,是 app 的 cache/ipc/prestep22/project/session/wire、changeset 幾乎
全部、query、command。追下去發現三個阻塞,**沒有一個是「測試沒跟上」**。

---

## 1. 三個阻塞

### 1.1 `X[n]` 引用不到套件的 trait

實測四種寫法:

| 寫法 | 現況 |
|---|---|
| `belongs Noun`(std 的 trait) | ✅ 通過,範疇 5 個 |
| `belongs Noun` + `Noun[0]` | ❌ `UnknownTrait { sign: "x", name: "Noun" }` |
| `Noun[0]`(無 belongs) | ❌ `UnknownTrait` |
| `belongs Local` + `Local[0]`(本地 trait) | ✅ 通過 |

`expand_traits` 只查 `src.traits`——**使用者語言自己的 trait**。而投影用的 registry 是
`OntologyRegistry::build(&[&std, &user])` 建的,兩份都在。

於是:**顯式引用只對同一份文件裡宣告的 trait 有效**,而真實文件的 `belongs` 大多指向 std。
這是既有限制,不是兩階段造成的——但兩階段把它從「少用的路不能走」變成「主幹道不通」。

std 那 103 行遷得動,是因為它們引用的是**同一個套件內**的 trait。

### 1.2 `effective_sign` 被當成兩件事在用

```
"ControllerTargetAgreement": branch 0: unknown slot reference "controller"
```

`ControllerTargetAgreement` 自己就宣告了 `controller` slot,之所以「找不到」,是因為
驗證器要檢查 **trait 上的規則**時,會造一個合成 sign:

```rust
SignDef { name: format!("{}#rule-validation", trait_def.name),
          items: vec![belongs(trait_def.name)] }   // 再 effective_sign 把內容拉出來
```

兩種用途共用同一個函式:

| 用途 | 站點數 | 兩階段之後 |
|---|---|---|
| ①「這個 sign 繼承到什麼」 | 約 20 | **該被展開取代**——要關的是這一半 |
| ②「給我一個 trait 的 sign 樣視圖」(驗規則、slot 引用、guard 白名單) | **6**(system.rs ×4、ontology.rs、changeset/lib.rs) | **仍然需要**,與內容通道無關 |

把 `effective_sign` 整個關掉,等於連 ② 一起砍。trait 不是 sign,要驗它的規則就得先把它
看成 sign——那個需求不會因為內容通道換了而消失。

### 1.3 `.chg` 的編輯驗證走 ① Source

`check_document` / `check_document_with_packages` 是 **changeset 每次原語編輯**都會呼叫的
(`crates/changeset/src/lib.rs:355,367`),它驗的是 `effective_source`——**① Source**,
內容還沒展開,只能靠投影。

也就是說,關掉投影會讓**每一次 `.chg` 編輯**的驗證看不到繼承內容。

## 2. 行為預期(做完之後)

### 2.1 內容從哪裡來

規則只有一條,**與 trait 住在本地還是套件無關**:

> **有展開點時,內容由展開點供給,宣告不展開;沒有展開點時,宣告就地展開全部塊。
> 兩者互斥,永不重複。**

| 情境 | 今天 | 第 3 步之後 |
|---|---|---|
| `belongs Local`(無展開點) | 投影供給 | 在**宣告處**展開全部塊 |
| `belongs Local` + `Local[0]` | 投影供給(與展開重複,靠名字疊掉) | 只由**展開點**供給 |
| `belongs Std`(無展開點) | 投影供給 | 在**宣告處**展開全部塊 |
| `belongs Std` + `Std[0]` | **`UnknownTrait` 錯誤** | 只由**展開點**供給 |
| `Std[0]` 無 `belongs` | `UnknownTrait` | `TRAIT_USE_WITHOUT_BELONGS` |
| `belongs Marker` | 無內容可給 | 不展開,無診斷 |

**本地與套件的 trait 在「之後」那一欄行為完全相同**——內容都從展開來、分類都由 registry
回答、優先順序規則相同。今天那個差別(套件的引用不到)純粹是阻塞 1.1 的實作缺口,
**不是設計上的分別**;修掉 1.1 之後這兩列就合而為一。

### 2.2 分類不變

`sign_categories` / `category_is_a` / `categories_satisfy` / `closure` /
`missing_name_hint` 全部**照舊由 `belongs` 閉包回答**。那是 `belongs` 的本職(P40),
與內容通道無關。菱形去重、循環安全也留在那一側。

### 2.3 診斷

| 代碼 | 級別 | 意思 |
|---|---|---|
| `BELONGS_DEFAULT_PLACEMENT` | **Info** | 宣告沒有顯式展開點,內容落在宣告處;要控制位置請寫 `X[n]` |
| `TRAIT_USE_WITHOUT_BELONGS` | Warning → **Error**(合併後可升) | 展開點沒有對應的宣告 |
| `BLOCK_EMPTY_WITHOUT_PASS` | Warning | 不變 |
| `TRAIT_MARKER_HAS_CONTENT` | Error | 不變 |

### 2.4 不變的東西

- `.chg` 定址:`belongs["X"]` 與 `trait_use["X"]` 兩種 `NodeKind` 維持(合併的是儲存,不是定址)
- canonical 形式:`belongs X` 與 `X[n]` 兩行照舊,round-trip 逐位元穩定
- `global trait`:P6 自動引用,**不經 belongs 也不經展開**(擁有者已裁,保持自動)
- 既有 `.lang` 文件:**零改動**——沒寫展開點的一律走預設落點

## 3. 實作順序

1. **給展開一個外部 trait 來源**(解 1.1)。`expand_traits(src)` → 需要能查 std/套件的
   trait。影響 `codegen::compile_full` 與 `compile()` 的簽名。
   *出口*:`belongs Std` + `Std[0]` 通過,且內容進得了 CompiledSign。
2. **拆開 `effective_sign` 的兩個用途**(解 1.2)。② 改成從 trait 自己的 blocks 直接造
   視圖(展開後那些 blocks 已含祖先內容),不走 belongs 閉包。
   *出口*:6 個合成視圖站點改用新入口,行為不變(115 綠)。
3. **編輯驗證改看展開後的視圖**(解 1.3),或明確裁定「`.chg` 的驗證只驗 Source 能驗的
   部分」。
   *出口*:`check_document` 路徑在關掉投影後仍綠。
4. **預設落點 + 關掉投影的內容那一半**(本步的正題)。
   *出口*:115 綠,且 `effective_sign` 只回 sign 自己的項目。

前三步各自**獨立可驗、可單獨提交**;第 4 步是它們的合流。

## 4. 未決與風險

- **第 3 步的代價未量**:讓編輯驗證看展開後的視圖,等於每次原語編輯都要跑一次展開。
  有 lazy compile 快取(步驟 14),但**成本沒有量過**。若太貴,替代方案是裁定「Source
  級驗證看不到繼承內容」——那會讓一批既有診斷在編輯當下失效、延到 commit 時才報。
- **菱形**:預設落點讓 `belongs` 也展開,於是 D→B,C→A 會把 A 展開兩份。擁有者已裁
  「不禁重複、按既有規則合併」,但 Slot 的同名合一規則([C])**尚未實作**。
- 這份提案**沒有**涵蓋 P76 參數化與 rename/別名機制——那兩件接在本步之後。
