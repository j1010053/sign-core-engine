# 架構修補13 — 跨界表層回傳與唯讀範圍(v0.1 提案)

> **性質**:提案,**未裁定**。兩項合為一組,不建議分開落地(理由見 §6)。
> **緣起**:2026-08-17/18 釐清 `realization:` 本體時的副產物。原問題是
> 「`.phon.ret` 能不能沿著順序依序展開,再把跑完 `.qy` 的東西丟回引用方」。
> **上位依賴**:`sem_roles_self_phon_realization_v1.md` §4/§4.1(realization 與 `+` 接縫)、
> 《修補08》(具名可定址節點)、P71-B3(不預先造無消費者語法)。
> **範圍**:只回答「跨界回傳跑完音變的東西」需要什麼。不改 realization 的既有語意。

---

## 1. 起點:`.phon.ret` 回的是材料,不是唸出來的樣子

`/{Callee(...).phon.ret}/` 今天的行為是:套用該 application → 要求飽和 →
遞迴 `realize_phon` → 取回 `RealizedPhonInput`。

那是**進 Tshiatūn 之前**的輸入字串。真正跑音變在更外層
(`build_phrase` → `run_program` → `surface_phrase`,見 `system.rs` `derive_with_context`)。

所以「內層先唸出來,外層拿去當材料」——**今天做不到**。

---

## 2. 但大部分需求已經被既有機制覆蓋

提案前先劃掉不需要提案的部分。Tshiatūn 已有三層執行域:

```rust
/// 規則的執行域:逐 stem、逐 prosodic word,或整個 phonological phrase。
pub enum Stage { Stem, Word, Phrase }
```

`stage_domains`(`tshiatun/crates/dsl/src/exec.rs`)把每一級映到它跑的片段:

| `stage:` | 跑在哪些片段上 | 片段從哪來 |
|---|---|---|
| `stem` | **逐 stem bracket** | template 裡的 `+`(§4.1) |
| `word` | 逐韻律詞 | template 裡的空白 |
| `phrase` | 整句 | — |

**這已經是層級音韻,而且一趟跑完。** 「內層先音變、外層再音變」用
`+` 標詞幹域 + 規則標 `stage: stem` 就做得到,不需要跨界兩次。

> **由此抬高 `+` 的份量**:它不只讓規則環境引用得到邊界(§4.1 原有的理由),
> 它同時**決定 `stage: stem` 的規則跑在哪些片段上、跑幾次**。
> 漏寫 `+` 不是少一個可引用的環境,是**整個 stem 層級失效**——全詞被當成一個域。
> 這一點應回填 `sem_roles_self_phon_realization_v1.md` §4.1。

**結論:單趟 + 三層 stage(以下稱「方案 A」)是預設做法,零改動、今天可用。**

---

## 3. 方案 A 的天花板

`+` 給出的是**平的**詞幹域序列,`MorphUnit` 只有 `Root` / `Stem` / `Word` 三級。
所以多層嵌套的循環會被壓成一層:

```
[[condition]al]ity        ← 兩次外加,每次都該重跑重音指派
```

英語 level-ordering(`-ity` 觸發重音移動、`-ness` 不觸發)這類**真正的多輪循環**
是方案 A 的上限。多數語言用不到;要用到就得跨界不只一次。

---

## 4. 提案:兩項一組

### 4.1 新投影 `.phon.surface`

| 投影 | 回什麼 | 對應本體 |
|---|---|---|
| `.phon.ret`(**不動**) | 音變**前**的材料 | 「要進 `.qy` 的內容」 |
| `.phon.surface`(**新增**) | 音變**後**的表層 | 「`.qy` 跑完的結果」 |

**不改 `.phon.ret` 的語意**,新增第二個。作者按需要選:要拼材料用前者,
要「已經唸成那樣的東西」用後者。這剛好把 `phon:` / `realization:` 的既有分工
(材料 / 適配)在投影層面再顯性化一次。

零件都在:`phon_program`、`build_phrase`、`run_program`、`surface_phrase`。
`surface_phrase` 也已經把 stem seam 印回 `+`、詞界印回空白,**所以回傳的不是扁字串,
外層仍看得到內層結構**。

### 4.2 唯讀範圍(read-only span)

> **語意**:範圍內的音段**可作環境匹配,不可作改寫目標**。

沒有這一項,4.1 不安全:外層再跑一次同一套規則,已經觸發過的規則會對內層再觸發一次。
唯讀範圍是**嚴格循環(Strict Cycle Condition)的最小實作**——不記「哪些規則跑過」
(那是一本 規則×範圍 的帳),只記「哪一段已經處理完」。

**可行性:座標維護機制已存在。** `commit.rs` 已在為 `morph` 括號做同一件事——
提交後 `for bracket in after.morph.iter_mut()` 修正座標,刪除時
`origin_morphs_for_anchor` 追蹤錨點原屬哪個形態單位。唯讀範圍是同一種東西
(骨架上的 `[lo, hi)`),直接沿用。

---

## 5. 唯讀範圍的五個裁定點

落地前必須逐條裁定,否則會鎖錯東西。

| # | 問題 | 提案傾向 |
|---|---|---|
| **1** | **粒度**:只鎖骨架,還是連 tier 關聯一起? | **分兩件事**:改寫範圍內既有的東西 → 禁;**從外面聯結到範圍內的錨點 → 允許**。不分會誤擋 Bantu 那種跨域聲調擴散 |
| **2** | **跨邊界的規則** | **必須放行**。左脈絡在唯讀內、目標在唯讀外要能跑,否則 `+` 剛換來的邊界敏感能力又被鎖掉。語意精確寫成「可作環境匹配,不可作改寫目標」正是為此 |
| **3** | **「本次操作」的範圍** | **一次跨界(一次 `run_program`)**。這樣才與 4.1 對得上:內層回來的整段標唯讀,外層動不了。若取「一條規則」的粒度,那是規則層 opt-out,用途不同(近於 Lexurgy 的 `//` 排除環境) |
| **4** | **要不要 opt-out** | **要**。英語 conditionality 的重音**必須**改寫內層;規則要能宣告「我無視唯讀」。鎖太死的話,真正的循環音韻反而寫不出來——而那正是本提案的動機 |
| **5** | **被擋下可不可觀察** | **必須可觀察**。`StepRecord` 已逐步記錄,加一個「因唯讀被擋」的狀態即可。**靜默是這個 repo 反覆踩到的坑**(見 §6),作者會誤以為規則沒匹配到 |

---

## 6. 為什麼兩項必須綁在一起

- 沒有 4.2,4.1 **不安全**(規則重複套用)。
- 沒有 4.1,4.2 **沒有消費者**——走方案 A 時單趟跑不會出現「已處理過的材料」。

單獨落地 4.2 會製造又一個「造出來沒有消費者」的東西。這個 repo 的前車之鑑已經數得出來:

| 前例 | 症狀 |
|---|---|
| `SenseEdge.opaque` | `lib.rs` 自誌「造出了表面語法卻尚無消費者」 |
| `realization:` 內的 `@name` | parse 接受、canonical dump 印出,但**無任何 selector 到得了**(《修補08》更正欄) |
| `NodeKind::RealizationBranch` 等 V1 殘留 | 型別已刪、消費端還在處理,誤導後續讀者(2026-08-17 清除) |
| `case <slot>.phon:` | 名為讀音、實為比範疇(2026-08-17 移除) |

四個裡有三個在 2026-08-17 這一輪才被發現,而發現的方式都是「有人照字面相信了它」。

**故:4.1 與 4.2 同案裁定、同案落地,或都不做。**

## 7. 相容性

- **不改 `.phon.ret`**:既有用例(`fp_v2.rs`、`identity_sidecar.rs`、`application_named_arguments.rs`)行為不變。
- **不改單趟路徑**:未使用 `.phon.surface` 的語言完全無感,`Word.readonly` 恆為空。
- **P24/P25/P26**:唯讀範圍是 `Word` 的欄位(執行期表徵),不進 `.lang` AST、不參與節點定址與 id 配發。相容。
- **可移植性(CLAUDE.md §4)**:純資料 + 座標運算,無 fs / 時間 / 執行緒。相容。
