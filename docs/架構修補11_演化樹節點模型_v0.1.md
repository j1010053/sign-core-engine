## 0. 缺陷記錄:digest 契約與 stale 傳播互相打架

### 0.1 症狀(實測)

演化鏈 `root → n1 → n2`。改動 **n1** 的 changeset 後:

```
初次求值 OK, replay_count=2
改 n1 之後求 n2 → CHANGESET_BASE_SOURCE_MISMATCH
```

失效傳播本身是對的(n1 與其所有後代都被標 stale),但**標了之後跑不起來**。

### 0.2 根源

| 立場 | 出處 | 主張 |
|---|---|---|
| digest 契約 | 步驟 14(已封板) | `.chg` 的 prelude 釘 `base_source`/`base_identities`;base 一變就**拒絕執行**——保證 replay 逐位元可重現(P26) |
| stale 傳播 | docs/06 §5【M+】 | 「parent 變動時沿依賴邊標 stale」——**言下之意是後代要重新求值** |

兩者互斥:**stale 標記在實務上用不到**,因為被標記的後代必然重算失敗。

### 0.3 這不是實作 bug

兩邊各自都正確。缺的是**中間那層語意**:base 不符時該做什麼。現行答案是「放棄」,
正確答案應是「**重新套用(rebase),成功就成立、衝突就回報**」。

## 1. git 類比

owner 指出「按照文件內容,應該是一個類似 git 的系統」。逐項對照 docs/06:

| 面向 | docs/06 | git | v0.1 是否吻合 |
|---|---|---|---|
| 拓撲 | 有向圖,預設樹,允許多親 §1 | commit DAG | ✅ |
| 邊 | **只有一種邊:縱向(descent)** §2 | parent 指標 | ✅ |
| 多親 | 融合(克里奧爾)§1 | merge commit | ✅ |
| 無環 | v0.1.1 無環約束 §2 | DAG | ✅ |
| 節點何時產生 | **只在四種情形結晶** §1 | commit 是刻意的 | ✅ |
| 使用者標記 | `pin` §1 | tag / branch | ✅ |
| **內容模型** | 存 diff,狀態是其函數 §5 | **存 snapshot** | ❌ **相反** |

**關鍵洞見**:git 之所以「改祖先」不會爆炸,是因為它**不改**——commit 不可變,
`rebase`/`amend` 是**產生新 commit**,舊的原封不動。衝突在 rebase 當下被**回報**,
不是靜默吞掉、也不是讓整棵樹壞掉。

v0.1 的模型是「**可變節點 + 只存 diff**」——最脆的組合。v0.2 把最後一項也對齊。

## 2. 節點存 snapshot、邊存 changeset【P56】

### 2.1 結構

```
Node {                              // 不可變
    parents:      Vec<Edge>,        // 主幹在 [0](docs/06 §5);多親 = 融合
    snapshot:     LanguageDocument, // **物化狀態**,不可手動更改
    nativization: Nativization,     // docs/06 §4;節點獨立屬性
    label:        Option<String>,
}

Edge {                              // 不可變;演化樹的邊
    from:      NodeId,
    changeset: Option<String>,      // `.chg` 原文;僅**主幹邊**帶,其餘為引用邊
}
```

- **節點 = 結果**(snapshot),**邊 = 過程**(changeset)。
- **兩者皆不可變**:編輯 changeset **不是**就地改邊,而是**生成一條新邊**(§2.3)。
- 多親時只有 `parents[0]` 的邊帶 changeset(承 docs/06 §5「以 parents[0] 為 replay
  主幹,其餘 parent 僅供條目引用取材」)。

### 2.2 與 docs/06 §5「不存副本」的調和

docs/06 §5 明定「狀態永遠是 ChangeSet 的函數,**不存副本**(單一資訊源)」——
存 snapshot 表面上牴觸此條。**本檔覆寫其實作面,但保留其精神**:

- **因果關係不變**:changeset 仍是**因**、snapshot 仍是**果**;snapshot **永遠**由
  「parent.snapshot × edge.changeset」產生,**不得手動編寫**。單一資訊源(誰決定內容)
  依然是 changeset。
- **改的是「果要不要留下來」**:§5 原意是避免「副本與真相不同步」。而**不可變性**
  使不同步**不可能發生**——兩者都不會在腳下改變。
- **可驗證**:不變式 `apply(parents[0].from.snapshot, edge.changeset) == snapshot`
  隨時可查(git `fsck` 的對應物),故物化不是失去單一資訊源,是**把果快取成一等資料**。

**紅利**:讀一個節點的語言狀態變成 **O(1)**——不必 replay 祖先鏈。先前量到的
「replay 一棵樹會放大成本」的技術債,對**讀取**而言直接消失;replay 只在**建立**
節點時發生一次(不可避免,且只有一次)。

### 2.3 改 changeset = 生成新邊 + rebase 判定(owner 流程)

```
        ┌─ e1 ─┐      ┌─ e2 ─┐
   root ┤      ├─ n1 ─┤      ├─ n2
        └──────┘      └──────┘

改 e1 的內容 →  ① 生成新邊 e1'(舊 e1 原封不動)
               ② 套用 e1' 於 root.snapshot → 新節點 n1'
               ③ 對 n2 做 **rebase 判定**:把 e2 重新套到 n1'.snapshot 上
                    ├─ 乾淨 → 產生 e2'、n2'
                    └─ 衝突 → 明確回報,要求人介入(不默默近似)
```

舊鏈 `root→n1→n2` **始終有效**(不可變),新鏈是**並存**的另一條。這正是 git 的
`rebase` 語意。

## 3. rebase 判定依據【P57】

> owner 提問:「rebase 判定可以依據 `.chg` 直譯器的 err 訊息嗎?」
> **答:可以,但要用「型別化的錯誤變體」,不是用訊息字串。** 而且比預期更好用——
> `ReplayError::Statement { ordinal, .. }` **已經帶了是哪一句失敗**。

### 3.1 先繞過 digest,才看得到真正的衝突

`base_source`/`base_identities` 的驗證在 `resolve` 與 `run` **兩層**都做。rebase 的
第一步必然是 digest 不符——**那正是「這是 rebase 不是重放」的信號本身**,不是衝突。
故 rebase 路徑 = 「**放寬 digest 驗證**重新 resolve,再分類其餘錯誤」。

### 3.2 錯誤變體 → rebase 結果的對映

| 變體 | rebase 意義 |
|---|---|
| `BaseSourceMismatch` / `BaseIdentitiesMismatch` | **不是衝突**——rebase 的入口信號,必須繞過 |
| `LibraryLockMismatch` | **環境變動**(套件版本),另一類,非節點衝突 |
| `Statement { ordinal, source: TargetNotFound }` | **衝突**:該筆編輯的目標在新 base 上不存在;`ordinal` 指出**哪一句** |
| `Statement { source: AnchorInvalid }` | **衝突**:位置參考已失效 |
| `Statement { source: Validation(report) }` | **衝突**:結果語意不合法;`report` 帶完整診斷 |
| `Statement { source: ParentKind / FieldMismatch / Cycle }` | **衝突**:型別/欄位/結構對不上 |
| `Selector(..)` | **衝突**:定址解不開 |
| `Parse` / `Schema` | **非衝突**:changeset 本身壞了(輸入錯誤) |
| `Ok(_)` | **乾淨 rebase** → 產生新邊與新節點 |

**成果**:先前列為「待裁」的「更細的衝突偵測(哪一句、為什麼)」**幾乎免費就有了**
——`ordinal` 給句號、`ValidationReport` 給診斷。不需要逐句試探。

**鐵律**:分類**只依變體**,不 `match` 訊息字串(訊息是給人看的,改字不該改行為)。

> ### 3.3 實作回報:上表對「目標不存在」曾經高估,已補(v0.3)
>
> 落地時發現上表第三列 `Statement { ordinal, source: TargetNotFound }` **對最常見的
> 情形不成立**。以**名字**定址(`sign("y")`)而目標不存在時,錯誤在更早的 **selector
> 解析層**就發生,產生 `ReplayError::Selector(String)` ——**不帶 `ordinal`**。
> `Statement { TargetNotFound }` 只在以穩定 id 定址、且 selector 解析成功後才走得到。
>
> 而「目標在新 base 上不存在」正是 rebase 最典型的衝突,故「哪一句」這個紅利
> **對主要路徑並未兌現**。
>
> **裁定(owner 認可)**:補上。實作採**單點包裝**——新增
> `ReplayError::StatementSelector { ordinal, message }`,在
> `UnresolvedChangeSet::resolve` 的語句迴圈把 `Selector(msg)` 重新標上句號。
>
> 選這個作法而非把 ordinal 灌進 `Selector(String)`:後者有約 20 處建構點,且**那些
> 地方都不知道自己屬於哪一句**——句號只有 resolve 的迴圈知道。故單點包裝既是最小
> churn,也是唯一資訊齊全的位置。既有 `Selector` 變體保留給非語句情境。
>
> 影響面:2 個既有測試(`clone_keyword`、`named_addressing`)改為斷言新變體,
> 並順帶取得句號斷言。判別測試 `a_missing_target_conflict_names_its_statement`
> 讓失敗落在**第 1 句**,故「句號寫死成 0」會被抓到(已突變驗證)。

## 4. 節點識別【P58】

- **內容定址**:`NodeId = sha256(snapshot.source ‖ parents ‖ nativization)`——
  與 git commit hash 同構(commit = tree + parents + metadata),且滿足 P26
  「決定性、禁隨機/時間戳」。
- **身分含出身**:雜湊納入 parents,故「內容相同但來歷不同」是**不同節點**,
  樹結構不會被意外摺疊。
- **人類可讀名字是另一層**:`label` 與外部具名指標(branch/head)不是身分——
  承 P45「標籤不取代穩定 id」。

## 5. digest 的職責重新定位【P59】

digest 不是「防止 base 改變」——不可變模型下 base 本來就不會變。真正用途:

| 用途 | 說明 |
|---|---|
| **跨系統流通** | `.chg` 單獨拿到別處時,確認基底沒被掉包(步驟 14 的原始用意) |
| **rebase 判定的入口** | 不符 = 「這是 rebase」→ 走 §3 的分類流程,而非直接失敗 |

步驟 14 的契約**語意一字不動**(直接 replay 仍驗、仍擋);只是**多一條 rebase 路徑**
供演化樹使用。

### 5.1 snapshot 的持久化:共享物件庫【P60】

**逐節點存一份完整 `.lang` 不可行**:演化每代只改少數 sign,其餘逐字相同,
空間隨節點數線性成長且 99% 是重複。採 **git 的共享物件庫**作法:

| 我們 | git 對應 | 說明 |
|---|---|---|
| **sign 物件** | blob | 一個 sign 的 canonical 文字,以其**內容雜湊**為鍵,**全庫只存一份** |
| **snapshot 清單** | tree | 節點狀態 = 「名字 → sign 雜湊」的有序清單 + dsl 宣告等區段的雜湊 |
| **節點** | commit | snapshot 清單雜湊 + parents + nativization(P58) |

改一個 sign → 只有**那一個** sign 物件是新的,其餘全部**共用同一份**;
父子兩個 snapshot 清單也只差那一行。空間從「節點數 × 語言大小」降為
「節點數 × 每代改動量」。

**選 sign 當共享單位的理由**:演化的自然改動粒度就是 sign(P2「語言知識只住
Language 的 Global/Trait/Sign」),且 canonical printer(P21)保證同內容逐字相同,
雜湊天然穩定。

> **實作注意**:`.lang` 本體共享得很好,但 **identity manifest 不然**——
> 位址是**位置式**的(`Signs(n)`/`Items(n)`),在前面插一個 sign 會讓其後所有條目
> 的位址位移,整份 manifest 幾乎全churn。manifest 又不能純由 `.lang` 導出
> (它承載跨編輯的穩定 id 繫結,正是 sidecar 的用意)。故 manifest 的共享策略
> **另議**——最簡作法是逐節點整份存,或改用非位置式定址。此點不影響 P60 的語意。

## 6. 多親融合:機械合併【P61】

### 6.1 缺陷:多親目前語意上空轉

`evolution.rs` 對 `parents` 的全部用法:

| 位置 | 用途 | 用到哪些 parent |
|---|---|---|
| `insert` L111 | 存在性檢查 | 全部 |
| `check_acyclic` L252 | 成環檢查 | 全部 |
| `invalidate` L148 | stale 傳播 | 全部 |
| **`resolve` L175** | **replay 的 base** | **只有 `parents.first()`** |
| **`ancestor_chain` L211** | **上溯主幹** | **只有 `parents.first()`** |

即:`parents[1..]` **對求值結果沒有任何貢獻**——多親宣告得出來,但語意上是空的。
docs/06 §5 v0.1.1 承諾的「其餘 parent 僅供 ChangeSet 條目引用取材」**從未實作**,
因為 `.chg` 沒有任何跨文件的引用手段(見 §7)。

本節把 MVP 的 `parents[0]` 佔位升級為 docs/06 §5 已列為【M+】的
**「完整融合 replay(多主幹混合)」**——不是繞過規格,是補上規格本來要的東西。

### 6.2 機械合併的範圍:看有沒有對齊鍵(v0.3 修訂)

> **修訂記錄**:v0.3 初稿寫「機械合併**只**作用於 `signs`」,理由是其餘四者
> 「結構上無聯集語意或不可解析」。落地時發現**該理由只對其中兩個成立**——
> `traits` 有穩定 id、`distribution` 有鍵字串,兩者都有對齊鍵。
> **owner 已裁定改為逐項合併**;下表為修訂後的版本,舊表保留在 §6.2.1 以誌其誤。

三態規則要能**逐項**套用,前提是兩邊的項目**對得起來**。真正的分界是**有沒有對齊鍵**:

| 區段 | 對齊鍵 | 作法 |
|---|---|---|
| `signs` | 穩定 id | **逐項** |
| `traits` | 穩定 id(向 identity manifest 取;`TraitDef` 不自帶 id) | **逐項** |
| `distribution` | 鍵字串 | **逐項** |
| `prosody` | **無**——單一條鏈,沒有「第幾項對第幾項」 | 整塊 |
| `dsl_decls` | **無**——不透明 verbatim(I15-a),看不進內容 | 整塊 |

逐項的三個**共用同一段泛型程式**。寫三份幾乎一樣的程式會走鐘:日後補一個角落只改到
其中一份,詞與文法的合併行為就悄悄不一致了——正是本專案一路在避免的多資訊源。

**顆粒度到「一個項目」為止**(owner 裁定):A 改了某個 sign 的發音、B 改了同一個 sign
的語意,仍算衝突。再往下降到維度/規則層要先決定 `phon`/`sem`/`syn`/`prag` 各自算不算
獨立單位,屬另一個議題,不在 P61。

仍成立的部分:`prosody` 與 `dsl_decls` 各方改成不同值時**必須由該節點的 `.chg`
明確指定**(它們會改變語言狀態,依 §9 判準一律寫在邊上,不得放 config)。
這也與真實克里奧爾的形狀一致——**詞彙來自上層語、語法音韻來自底層語**:
量大的部分機械化,量小而判斷重的部分交給人。

### 6.2.1 誌誤:初稿的舊表與它錯在哪

初稿的表(**已作廢**):

| 區塊 | 初稿判定 | 初稿理由 |
|---|---|---|
| `signs` | ✅ 可合併 | 純命名(handle 撞號) |
| `traits` | ❌ 不可 | 「兩邊的 `Noun` 是同一個範疇嗎」= 語言學判斷 |
| `dsl_decls` | ❌ 不可 | 不透明 verbatim(I15-a) |
| `prosody` | ❌ 不可 | 單一條鏈,無聯集語意 |
| `distribution` | ❌ 不可 | 同鍵異值 = 語言學判斷 |

**錯在哪**:`traits` 與 `distribution` 的理由不成立。初稿擔心的
「兩邊的 `Noun` 是同一個範疇嗎」,**在 id 對齊之下已經有答案**:

| id 狀況 | 意義 | 處理 |
|---|---|---|
| 同一個 id | 同一個 trait,兩邊都繼承自共同祖先 | 三態規則,與 sign 相同 |
| 不同 id、同名 | 兩個不相干的 trait 撞名 | **命名碰撞**,與 sign 相同 |

那個語言學判斷**根本不會發生**——id 已經分好了。舊表的實際代價:兩支只要都碰過文法
就整塊衝突,而「兩支都碰過文法」在演化裡幾乎必然,等於**每次合併都要人工**。

### 6.3 signs 的合併規則:3-way,以穩定 id 對齊

**基準 = 諸 parent 的最近共同祖先;無共同祖先時基準為空。**
空基準使規則退化為純聯集(對應「兩個無關語言融合」),故**同一套邏輯涵蓋兩種情形**,
不需要兩條程式路徑(同 git `--allow-unrelated-histories`)。

**必須 3-way 而非兩兩比對**:2-way 只看得到「兩邊不同」,分不出「一邊改過」與
「兩邊都改過」,會把前者誤報為衝突。共同祖先場景下絕大多數 sign 是「僅一邊改過」,
2-way 將產生數量級的假衝突,**機制不可用**。

**對齊鍵 = 穩定 id,不是名字**(承 docs/06 §6.1:「兩狀態的 sign 以 `SignId` 對齊
——同 id = 同一 sign 的兩個演化階段」)。合併與 diff 因此共用同一套對齊,不是兩套;
且能正確處理「一邊改了名」(用名字對齊會誤判為一生一滅)。

| 情況 | 結果 |
|---|---|
| 僅一邊相對基準改過 | **自動取該邊** |
| 兩邊改成相同值 | **自動,取該值** |
| 兩邊改成不同值 | **衝突,明確回報**(不得以 `parents[0]` 優先靜默帶過——那會默默丟棄另一支的演化) |

**命名碰撞是另一類衝突**:無共同祖先時,兩個 id 不同的 sign 可能同名。
這在 `.lang` 是硬性錯誤(名字唯一)。裁定:**合併時附帶「來源 → 前綴」改名規則**,
而非逐個報錯或永久命名空間化——克里奧爾本就是大量重命名的場合,一次給規則比逐個處理實際,
且不需回頭改動祖先(符合節點不可變,P56)。改名規則寫在該節點的 `.chg`(§9 判準)。

### 6.4 時機:建節點時,在該節點 changeset 之前

```
parent A snapshot ─┐
                   ├─►【機械合併】─► 本節點 base ─► 套用本節點 changeset ─► snapshot
parent B snapshot ─┘        ↑ 衝突在此處爆
```

節點的 `.chg` 拿到的是**已合併的乾淨語言**,與單親節點無異;合併過程對它不可見。

P56 之下此時機是硬的:合併**只在建節點時跑一次**,結果即該節點的 snapshot。
故 **有衝突就建不出節點**,不存在「先建起來之後再解」的中間狀態。

**比對單位是結構節點(sign/trait/item),不是文字**——即四原語定址的單位;
不比 `.lang` 原文,也不比正規形逐行。

### 6.5 前置:多 root【已實作】

§6.3 的「無共同祖先 → 空基準」在單 root 之下**永遠走不到**——任兩個節點往上追必定
相遇。這不是「做得出來但用不到」,是**造不出輸入去測**,寫了也是改成什麼樣測試都不會
紅的死碼(違反本專案的突變測試紀律)。故多 root 是 P61 的硬前置,已先行落地:

| | |
|---|---|
| `new(libraries)` | 建**空**圖,不再吃 root |
| `add_root(document) -> Result<NodeId>` | 加起點語言,可多次 |
| `roots()` | 全部起點(彼此無血緣) |

**兩道守門(皆為靜默毀損的防線)**:

1. **root namespace 必須唯一**。namespace 決定穩定 id(`<ns>:<n>`),而 §6.3 的合併
   **以穩定 id 對齊**。兩個 root 共用 namespace ⇒ 法語的 `evo:root:5`(水)與沃洛夫語的
   `evo:root:5`(樹)會被合併器當成**同一個 sign 的兩個演化階段而默默併掉**
   ——不報錯、無跡象。
2. **同原文、異 namespace 必須擋下**。`NodeId` 雜湊的是 `snapshot.source()`,
   而 **namespace 不在 `.lang` 文字裡**(身分是 sidecar),故兩者 id 相同、會走冪等
   路徑,**呼叫端指定的 namespace 被默默忽略**;錯誤要到之後 `base_identities` 不符
   才爆,離成因很遠。

> **誠實界線**:守門 1 只保證兩個 root **自身**的 id 不撞。後代 fork 的 namespace 由
> `.chg` 的 `changeset <ns>:` 自由指定,跨家族仍可能撞。**不能改成全圖 namespace 唯一**
> ——`rebase` 刻意沿用原 changeset 的 namespace(同 changeset 同 namespace ⇒ 同 id ⇒
> 結果可比對),全域唯一會讓 rebase 永遠失敗。
>
> **完整防線在合併當下**:**兩側都有、但共同基底沒有的 id 即為碰撞**
> (空基底時任何共有 id 都是碰撞)——因為合法共有的 id 只可能來自共同祖先。
> 此檢查屬 P61 本體,隨合併一起實作。

### 6.6 落地狀態(v0.3):**P61 已完整落地**

`changeset/src/merge.rs` + `EvolutionGraph::{merge_base, merge_plan}`
(14 整合 + 6 單元測試)。已有:最近共同祖先(唯一/空/多候選報錯)、
以 `SignId` 對齊的三態規則、生滅與刪改衝突、id 碰撞、命名碰撞、無鍵區段三態。

**物化(⑤b)已實作**:`merge::materialize(plan, base, sides, namespace)`。

> **更正**:先前記「需要 `language` 側新 API」是**過度悲觀**。
> `LanguageDocument::from_edit_parts(language, manifest)` 早已存在(當時無人使用),
> 且自帶完整驗證。故 `language` crate **一行未改**。

難處全在 **identity manifest**:位址是**位置式**的(`Signs(3)`、`Signs(3)/Items(0)`…)。
合併後 sign 按名字重排,每一個的「第幾個」都變,整份清單要重算——但**編號必須原封
不動**(編號變了等於換了一個 sign),且一個 sign 是**一整棵子樹**,每層都要跟著挪。

**作法:先 import 再換 id**,不自己重算位址——

1. 把挑好的內容組成 `Language`,`dump()` 後 `import_new_root` ⇒ **正確形狀免費拿到**,
   只是 id 全新;
2. 依位址把每個節點的新 id **換回它繼承來的 id**;
3. `from_edit_parts` 驗證清單與 `.lang` **逐位址相符**,不符當場爆。

自己重算位址等於複製 `language` 內部的節點列舉規則,兩份規則必然走鐘;走這條路則
位址算錯**不可能靜默通過**。

**兩個不在該驗證範圍內、會靜默毀損的點**(各有守門與測試):

| 風險 | 後果 | 守門 |
|---|---|---|
| 配號器只取一方 | 日後新增節點會發出**已用過的號碼**,兩節點共用一個 id,不報錯 | 取各方**最大值** |
| `namespace` 與 parent 重用 | 新配的 id 撞上繼承的 id | 比對**全部配號器**的命名空間而非 `root_namespace`——後代文件的 `root_namespace` 仍是祖先的,只看它會漏掉各次 fork 的命名空間 |

**已接進 `commit`(⑤c)**:`EvolutionGraph::merged_base(parents)` ——
單親回該 parent 的 snapshot(含借詞,§6.8),多親回全 parent 的機械合併結果。

`commit` 與 `verify`(fsck)**必須走同一條路**:fsck 原本拿 `parents[0]` 的 snapshot
重放,接線後多親節點的 base 是合併結果,不一起改的話**合法節點會驗不過**。

呼叫端寫 `.chg` 時也以 `merged_base` 為 base(prelude 的 digest 綁的是它);
該函式是純的、決定性的,故 `commit` 內部重算會得到逐位元相同的結果。

**§6.1 記錄的「`parents[1..]` 對求值無貢獻、多親語意空轉」至此消除。**

**對齊鍵確認**:`SignDef.id` 與 identity manifest 的 `ref_for_sign` 一致、
且 replay 後不變,即 docs/06 §6.1 所稱的 `SignId`。`Ephemeral` 命名空間的 id
跨文件無意義,遇到即硬錯(不略過——略過等於默默漏掉一個 sign)。

**逐項的三個區段共用同一段泛型程式**(`merge_keyed`)。突變測試佐證共用是真的:
把該函式從 3-way 改成 2-way,**sign 與 trait 的測試同時轉紅**(6 個)。

### 6.7 合併 base 的命名空間【owner 裁定】

> **命名空間是什麼**:穩定 id 長成 `<命名空間>:<流水號>`(`evo:root:7`),
> 命名空間即**「是誰發的這個號碼」**。合併時絕大多數項目是**繼承**的(帶著原本的
> 命名空間過來),但仍有三樣需要新號碼:文件根節點、清單的出身欄位,以及
> **這個節點之後才新增的東西**。第三項才是重點——若沿用某個 parent 的命名空間,
> 新發的號碼會撞上從該 parent 繼承來的 id,**而且不報錯**。

**規則:各 parent 的命名空間以 `-` 連接。**

```
parent A: fr        ┐
parent B: wo        ├─►  合併 base: fr-wo
```

由 parent 導出而非由 changeset 指定,理由:

- 它描述的是這個 base **本身是什麼**(這幾個 parent 的融合),與 changeset 叫什麼無關;
- `materialize` 因此**不需要知道 changeset**,職責乾淨;
- 同一組 parent 永遠得到同一個字首(決定性,P26)。

> #### 被否決的作法:沿用該節點 `.chg` 的命名空間
>
> 曾提議直接用 `changeset <ns>:` 那一行(不必加語法)。**落地時發現行不通**:
> `LanguageDocument::fork`(`identity.rs:388`)**拒絕已存在於配號器裡的命名空間**。
> 流程會是 ① `materialize(…, ns)` 讓 `ns` 進入 base 的配號器 → ② 跑 `.chg` 時
> `fork(ns)` 撞上該檢查而失敗——同一個命名空間在一個節點裡被用兩次。

**命名慣例:root 的命名空間直接用語言代號,不加前綴。**

現行測試用的 `evo:` 只是**測試裡的字首**(evolution 的縮寫),**程式完全不看它**
(`validate_namespace` 只檢查字元合法性)。但連接規則會把慣例的醜放大:

| 慣例 | 融合後 | 再融合一次 |
|---|---|---|
| `evo:fr` + `evo:wo` | `evo:fr-evo:wo` | `evo:fr-evo:wo-evo:xx` |
| **`fr` + `wo`** | **`fr-wo`** | `fr-wo-xx` |

故定為**不加前綴**。

> **既有隱患(記錄,非本刀處理)**:`fork` 只擋**同一條鏈**上的命名空間重複,
> **不同分支之間可以撞**——兩支都從 root 分出來時,各自只看得到 root 的配號器。
> 兩支若都叫 `n1` 並各自發號,合併時就會撞。目前唯一的防線是合併當下的
> `IdCollision`(§6.3),那已足夠(撞了必然在合併時被抓),但值得知道它是**唯一**的防線。

### 6.8 融合保 id、借詞發新 id

兩者常被混為一談,但在身分上是相反的:

| | **融合**(多親) | **借詞**(單親 + `ContactInjection`) |
|---|---|---|
| 走什麼路 | 合併多個 parent 產生新 base | **不合併**;base 就是那唯一的 parent |
| 來的項目 | **保留原本的 id** | **拿到全新的 id** |
| 原語 | 由合併計畫直接組成 base | `Adopt` → `insert_sign`,就是一個 **Insert** |
| 語言學意義 | 同一個詞**繼續活下去** | **造了一個新詞** |

承 docs/06 §2:「接觸不生特殊邊——**借用 = 拉一個新節點,其 ChangeSet 含引用來源 X
的條目**」。故借詞節點是單親的,**完全不碰合併路徑**。

這個差別是對的:英語的 `beef` 借自法語 `bœuf`,但它是英語的一個**新詞**,不是法語那個
詞跑到英語繼續演化;兩者之後各走各的。推論:

- **融合**:diff 與合併會把兩支的「水」對在一起——同一個 id,同一個詞的兩個階段;
- **借詞**:借來的詞與 donor 那個詞**永遠不會被對在一起**——不同 id。provenance
  記著它從哪來(§3.2 由引用結構派生),但身分是新的。

**實作影響**:`materialize` **只在多親時被呼叫**;單親(含借詞、含一般演化)走原本的
路徑,一行不動。

### 6.9 合併後必跑引用完整性檢查

signs 會引用 traits(`belongs`、slot filler 的範疇約束)。詞庫機械聯集、
而 traits 由人擇定時,將出現**懸空引用**。合併後必須跑一次引用完整性檢查並明確回報,
**不得默默丟棄該 `belongs`**(承 §0.3「不默默近似」)。此檢查沿用既有 validation。

## 7. 跨語言引用:`ContactInjection`【P62】

### 7.1 規格早有、實作沒有

docs/06 §3.2:

> 某條目的「來源」= 它實際引用了哪個 parent 的 ChangeSet:自身創新 = 不引用;
> contact-from-X = 引用 X 的子集並變換;fusion = 引用多個 parent。
> MVP 以 **`ContactInjection(NodeId, …)`** 顯式記錄引用

docs/06 §2(無環約束 v0.1.1):

> ContactInjection 只能引用「時間上**已 materialize**」的節點狀態;引用圖必須無環

實作面兩個證據顯示此機制**從未落地**:

1. `rewrite.rs:158` 的註解自白:`Adopt { sign: SignDef, source }` ——
   「**呼叫端先從 donor Language 取出 `SignDef`**,展開才能維持 `(rewrite, Language)`
   的純函數簽名」。即「怎麼選」被推到引擎外。
2. `Selector`(`changeset/src/lib.rs:1770`)五個變體
   `Stable/Language/Sign/Trait/Path` **全部是單一目標、單一文件**;
   既無集合選擇,也無法指名另一個語言。

### 7.2 三個機制是同一個洞

| 機制 | 來源 | 量 | 現況 |
|---|---|---|---|
| `adopt` 借詞 | 1 個 donor | 少數 | 呼叫端手遞 `SignDef`(自白的洞) |
| 語言接觸 / 擴散 | 1 個鄰居,反覆 | 一批 | 不存在 |
| 克里奧爾融合(§6) | N 個 parent | 大量 | 不存在 |

三者只差在**量**,缺的是同一個東西:**跨語言的集合選擇器**。
補上 `ContactInjection` 三個機制一起有;不補則三者各自作弊。

**不得改用「接觸邊」表達**:docs/06 §2 明文
「**只有一種邊:縱向(descent)。接觸不生特殊邊**……此為與早期三種邊模型的**關鍵簡化**」。
引用寫在 ChangeSet 內,圖拓撲不變。

### 7.3 宣告面:`.chg` prelude 的 `donor` 行

`change_set_prelude`(`changeset/src/lib.rs:3354`)現已釘三類外部依賴;
donor 是**形狀完全相同的第四類**:

```
changeset evo:n2:
    schema = v1
    base_source     = sha256:…      ← 從哪個狀態出發
    base_identities = sha256:…      ← 那些 id 是什麼
    library std@1.0 sha256:…        ← 用了哪些外部套件
    donor fr <node-id>              ← 還讀了哪些語言   ★ 新增
```

body 的條目按**別名**引用已宣告的 donor。

> **v0.3 細化:形狀是 `donor <別名> <node-id>`,不是只有 node-id。**
> 本節原本寫「body 的條目**按名**引用」卻沒給名字。P58 之下 node-id 是 64 字元的
> 內容雜湊,直接寫進每一個條目沒法用。加別名的形狀與既有的
> `library <package>@<version> sha256:<digest>` **同構**(名字 + 摘要),不是新慣例。
>
> 別名在**檔案內必須唯一**:同名宣告兩次會讓 body 的引用「指向哪一個」變成任意的
> ——而那是**靜默**的,結果照樣算得出來,只是從錯的語言取材。故解析當下就硬錯。

**P58 之下不需另算 digest**:`NodeId` 即內容雜湊,故 `donor <node-id>` 本身就是 digest
——donor 內容變動 ⇒ 它是另一個 `NodeId` ⇒ 引用自然失效。

**驗證沿用既有機制,不新寫**:`verify_base_and_locks`(`lib.rs:3374`)增一項檢查即可。
三道硬錯(皆不得回空、不得默默略過):

1. body 引用未宣告的 donor(比照未知 rewrite 名的處理);
2. 宣告的 donor 未 materialize(docs/06 §2 無環約束);
3. donor id 解析不到。

### 7.4 來源由引用派生,**不加欄位**

docs/06 §3.1 明寫「`source` **不是獨立欄位**:見 §3.2,由引用結構派生
(Adopt 的 Reference 即來源)」。故**不得**為 `SignProvenance` 增設「來源節點」欄位——
`ContactInjection` 條目本身即帶 `NodeId`,加欄位會製造第二個資訊源。

### 7.5 篩選條件複用既有欄位,不新增本體

| 條件 | 現況 | 語言學意義 |
|---|---|---|
| `belongs X` | 已有(registry 走閉包,P40) | 按語法範疇取 |
| `entrenchment` 閾值 | 已有 | **基本詞彙抗借用**——最貼近真實的判準 |
| `provenance` | 已有 | 例:不重複借入已是借詞者 |
| sem / gloss | 已有 | 按語意場取 |
| 帶 slot(construction,P42) | 已有 | 借構式 vs 借詞 |

即:**既有 sign 欄位上的過濾式**,不是新本體。

## 8. `ServiceContext` 的範圍【P63】

### 8.1 障礙

`expand(rewrite, document) → Vec<PrimitiveEdit>`(P16)是**只讀單一 document 的純函數**。
跨語言引用需要讀到圖上另一個節點,簽名擋著。直接加參數需改 12 個 rewrite 的簽名
與全部呼叫端(含已寫好的 recipe),且每多一類外部來源就再改一次——
P53 `ServiceContext` 正是為此開的接縫。

### 8.2 裁定:併入 `ServiceContext`,定位放寬

**donor 查詢併入 `ServiceContext`**,其定位由「外部服務接點」放寬為
**「當前 document 以外的唯讀來源」**。

不另開平行 context:兩者形狀相同(皆為注入的唯讀解析器),分開只在命名上乾淨,
實際使每個 rewrite 多背一個參數;且切分標準(「服務」vs「資料」)本身不穩固
——History 亦是資料。

### 8.3 範圍限制(owner 裁定)

> **`ServiceContext` 可解析的節點 = ① 本節點的 `parents` ∪ ② 本節點 ChangeSet 中
> `donor` 宣告的節點。其餘一律硬錯。**

兩者皆為**節點自身內容**,故「範圍受節點內容限制」字面成立。此限制是承重的:

| | 無限制 | 有限制 |
|---|---|---|
| P58 內容定址 | 讀取來源不進雜湊 ⇒ **同雜湊可對應不同結果** | 雜湊蓋得住讀取來源 |
| replay 可重現 | 結果取決於圖上別處狀態 | 節點內容決定結果 |
| 失效傳播 | 依賴關係不可知 | **依賴邊可由內容推導** |
| docs/06 §2 單一種邊 | 傾向新增接觸邊(違反關鍵簡化) | 引用在 ChangeSet 內,拓撲不變 |
| docs/06 §2 無環約束 | 引用集合不明,無從檢查 | 引用集合是明的,可檢 |

### 8.4 實作順序

**P56 必須先於 `ContactInjection`。** 理由:節點 C 引用非祖先節點 X 後,
X 變動則 C 的結果變動,而現行 `invalidate`(`evolution.rs:148`)只沿 `parents` 走,
追不到此依賴。P56 落地後節點不可變(改動 = 生新節點),該問題自然消失;
先做 `ContactInjection` 則需額外實作一套引用依賴的失效傳播,做完即廢棄。

## 9. 節點 folder 儲存與雜湊邊界【P64】

### 9.1 節點以 folder 儲存

docs/07 §5c 的**旁註層**(文化說明、隱喻傾向、生成軟提示)規定
「**是 C 節點的一部分(隨節點存續)**,但與四維正交」,卻**至今沒有存放位置**。
節點改以 folder 儲存正好給它一個家:

```
nodes/<id>/
    manifest        ← snapshot 清單(名 → 物件雜湊;P60)
    edges           ← 入邊(from + changeset)
    annotation/     ← 旁註層(docs/07 §5c)
    config          ← 節點層設定
objects/            ← 共享物件庫(P60),跨節點共用
```

### 9.2 雜湊邊界

docs/07 §5c 要求旁註「**不參與 replay、不被 diff、不約束本體**」。
若旁註進入內容雜湊,改一句註解即產生新節點、分岔整棵樹——顯然錯誤。故:

> **雜湊內(parents + snapshot + nativization,P58)不可變;
> 雜湊外(annotation、config)可變。**

節點的不可變性因此要精確表述為「**內容**不可變」,而非「整個 folder 不可變」;
加註解不弄髒演化史。

### 9.3 判準:會改變語言狀態的一律在邊上

| 放哪 | 進雜湊 | 放什麼 |
|---|---|---|
| **edge(`.chg`)** | ✅ | `donor` 宣告、引用條目、**§6.2 四個非-sign 區塊的人工指定**、§6.3 改名規則 |
| **folder / `config`** | ❌ | 顯示偏好、編輯器狀態 |
| **folder / `annotation/`** | ❌ | 旁註層(docs/07 §5c) |

**`ContactInjection` 不得放 `config`**(曾考慮,已否決):它決定 replay 讀得到什麼,
放在雜湊外將使 ① P58 內容定址失效(同雜湊對應不同結果)、
② 改 config 可悄悄換掉借用來源而不生新節點、③ P63 的範圍限制淪為空話
——恰好拆掉立此界線的理由。§6.2 的四區塊人工指定同理。

## 10. P 系列決策

| # | 決策 |
|---|---|
| **P56** | **節點存 snapshot、邊存 changeset,兩者皆不可變**。`Node { parents: Vec<Edge>, snapshot, nativization, label }`、`Edge { from, changeset }`(僅主幹邊帶 changeset)。snapshot **不可手動編寫**,永遠由 `apply(parent.snapshot, edge.changeset)` 產生——因果不變(changeset 是因),改的只是「果物化保存」。**覆寫 docs/06 §5 的「不存副本」實作面**,但保留其精神:不可變性使「副本與真相不同步」不可能發生,且不變式可驗(fsck)。紅利:**讀節點狀態 O(1)**,replay 只在建立節點時發生一次 |
| **P57** | **rebase 判定依「型別化錯誤變體」而非訊息字串**:先**放寬 digest 驗證**重新 resolve(digest 不符正是 rebase 的入口信號),再依變體分類——`TargetNotFound`/`AnchorInvalid`/`Validation`/`ParentKind`/`Selector` = 衝突;`Parse`/`Schema` = 輸入錯;`LibraryLockMismatch` = 環境變動;`Ok` = 乾淨。`Statement { ordinal }` 免費提供**哪一句**衝突,`ValidationReport` 提供診斷 |
| **P58** | **節點內容定址**:`sha256(snapshot.source ‖ parents ‖ nativization)`,同構 git commit hash、滿足 P26;雜湊納入 parents 故「內容同、來歷異」是不同節點;`label` 是另一層不是身分(承 P45) |
| **P60** | **snapshot 持久化採共享物件庫**(git 作法):sign = blob(內容雜湊為鍵,全庫一份)、snapshot 清單 = tree、節點 = commit;空間由「節點數×語言大小」降為「節點數×每代改動量」。選 sign 為共享單位因其為演化的自然改動粒度(P2)且 canonical printer(P21)保證同內容逐字相同。**注意**:identity manifest 因位址位置式(`Signs(n)`)而不易共享,策略另議 |
| **P59** | **digest 職責重新定位**:①跨系統流通防掉包 ②rebase 判定入口。步驟 14 契約語意不變,只多一條 rebase 路徑 |
| **P61** | **多親融合 = 全 parent 機械合併**(§6),取代 `parents[0]` 佔位(現行 `parents[1..]` 對求值無貢獻,語意空轉);即 docs/06 §5【M+】的「完整融合 replay」。**合併範圍以「有沒有對齊鍵」劃分**(v0.3 修訂,§6.2):`signs`/`traits`(穩定 id)/`distribution`(鍵字串)**逐項**合併且共用同一段泛型程式;`prosody`(單一條鏈)/`dsl_decls`(不透明 verbatim,I15-a)無鍵,只能整塊比,不一致時由該節點 `.chg` 人工指定。顆粒度到「一個項目」為止,不降到維度/規則層。**合併 base 的命名空間 = 各 parent 的命名空間以 `-` 連接**(§6.7;由 parent 導出而非 changeset 指定,故 `materialize` 不需知道 changeset;沿用 `.chg` 命名空間的作法已否決——`fork` 拒絕重複的配號器命名空間);root 命名空間慣例為**語言代號不加前綴**。**融合保 id、借詞發新 id**(§6.8):融合是「同一個詞繼續活下去」,借詞是「造了一個新詞」(`Adopt` = 一個 Insert 原語),故借詞走單親路徑、完全不碰合併。signs 採 **3-way**(基準 = 最近共同祖先;**無共同祖先則基準為空**,退化為聯集,同一套邏輯涵蓋兩種情形),**以穩定 id 對齊**(承 docs/06 §6.1,與 diff 共用);僅一邊改過或兩邊同值 → 自動,兩邊異值 → **明確衝突**。命名碰撞以**「來源 → 前綴」改名規則**處理(寫在 `.chg`)。合併發生在**建節點時、該節點 changeset 之前**,比對單位是結構節點而非文字;**有衝突則節點建不出來**。合併後必跑**引用完整性檢查**(懸空 `belongs`) |

| **P63** | **`ServiceContext`(P53)定位放寬**為「當前 document 以外的**唯讀來源**」,donor 查詢併入,**不另開平行 context**(形狀相同;分開只使 12 個簽名各多一參,且「服務 vs 資料」切分不穩固)。**範圍受節點內容限制**:可解析節點 = 本節點 `parents` ∪ 本節點 `donor` 宣告,其餘硬錯。此限制承重——否則 P58 內容定址失效(同雜湊可對應不同結果)、replay 取決於圖上別處狀態、依賴邊不可推導、docs/06 §2 無環約束無從檢查。**實作順序:P56 必須先於 P62**(否則需為引用依賴另寫一套失效傳播,P56 落地後即廢棄) |
| **P64** | **節點以 folder 儲存**,給 docs/07 §5c **旁註層**(規定「是 C 節點的一部分」卻無存放位置)一個家:`nodes/<id>/{manifest, edges, annotation/, config}` + 共享 `objects/`(P60)。**雜湊邊界**:因 §5c 要求旁註「不參與 replay、不被 diff」,**雜湊內(parents+snapshot+nativization)不可變、雜湊外(annotation/config)可變**——節點的不可變性是「**內容**不可變」而非「folder 不可變」,加註解不分岔演化史。**判準:會改變語言狀態的一律寫在邊上**;`ContactInjection` 與 P61 的四區塊人工指定**不得放 `config`**(已否決),否則恰好拆掉 P63 範圍限制的理由 |
