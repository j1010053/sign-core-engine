## 0. 缺陷記錄:digest 契約與 stale 傳播互相打架

### 0.1 症狀(實測)

演化鏈 `root → n1 → n2`。改動 **n1** 的 changeset 後:

```
初次求值 OK, replay_count=2
改 n1 之後求 n2 → CHANGESET_BASE_SOURCE_MISMATCH
```

失效傳播本身是對的(n1 與其所有後代都被標 stale),但**標了之後跑不起來**。

### 0.2 根源

| 立場 | 出處 | 主張 |
|---|---|---|
| digest 契約 | 步驟 14(已封板) | `.chg` 的 prelude 釘 `base_source`/`base_identities`;base 一變就**拒絕執行**——保證 replay 逐位元可重現(P26) |
| stale 傳播 | docs/06 §5【M+】 | 「parent 變動時沿依賴邊標 stale」——**言下之意是後代要重新求值** |

兩者現在互斥:**stale 標記在實務上用不到**,因為被標記的後代必然重算失敗。
使用者要編輯任何非葉節點,就得手動重編其下所有後代的 changeset。

### 0.3 這不是實作 bug

兩邊各自都正確:
- digest **應該**擋——一份對著舊 base 寫的 changeset,盲目套到新 base 上可能默默產生錯的結果(例如它要改的節點已經不存在)。
- stale **應該**傳——不然快取會端出過時的值。

缺的是**中間那一層語意**:base 不符時該做什麼。現行答案是「放棄」,正確答案應是
「**重新套用(rebase),成功就更新、衝突就回報**」。

## 1. git 類比:哪些對、哪些不對

owner 指出「按照文件內容,應該是一個類似 git 的系統」。逐項對照 docs/06:

| 面向 | docs/06 | git | 是否吻合 |
|---|---|---|---|
| 拓撲 | 有向圖,預設樹,允許多親 §1 | commit DAG | ✅ |
| 邊 | **只有一種邊:縱向(descent)** §2 | parent 指標 | ✅ |
| 多親 | 融合(克里奧爾)§1 | merge commit | ✅ |
| 無環 | v0.1.1 無環約束 §2 | DAG | ✅ |
| 節點何時產生 | **只在四種情形結晶** §1 | commit 是刻意的,不是每次存檔 | ✅ |
| 使用者標記 | `pin: Option<UserLabel>` §1 | tag / branch | ✅ |
| **內容模型** | **存 diff**(ChangeSet),狀態是其函數 §5 | **存 snapshot**(tree),diff 是算出來的 | ❌ **相反** |

前六項高度吻合,**只有內容模型相反**——而缺陷正好長在這一項上。

### 1.1 關鍵洞見

git 之所以「改祖先」不會爆炸,是因為它**不改**:commit 不可變,`rebase`/`amend`
是**產生新 commit**,舊的原封不動仍可 checkout。衝突在 rebase 當下被**回報並要求解決**,
不是被靜默吞掉、也不是讓整棵樹壞掉。

我們現在的模型是「**可變節點 + 存 diff**」——這是最脆的組合:節點一改,所有後代的
diff 立刻全部失效,而且沒有 rebase 機制可以救。

## 2. 節點的存儲資料方式【P56】

### 2.1 節點不可變;編輯 = 產生新節點

```
LanguageNode {                  // ← 不可變(immutable)
    parents:      Vec<NodeId>,  // 預設 1;多親 = 融合(docs/06 §1)
    changeset:    String,       // 相對 parents[0] 的 `.chg` **原文**
    nativization: Nativization, // docs/06 §4;節點的獨立屬性,非由 parents 導出
    label:        Option<String>,
}
```

- **不提供 `set_changeset`**——編輯一個節點 = 用新內容**建一個新節點**,舊節點保持有效。
  (現行 API 的 `set_changeset` 是缺陷的來源,移除。)
- 可變的只有**指標**(branch/head 之類的具名引用),節點本身永遠不動。
  → digest 永遠不會失配,因為沒有任何節點的內容會在腳下改變。

**這一步就消滅了 §0 的缺陷**:stale 不再是「標記後跑不起來」,而是根本不會發生
——沒有東西變 stale,因為沒有東西被就地修改。

### 2.2 「改祖先」= 顯式 rebase,不是就地編輯

使用者想改 n1 → 系統做的是:

```
root → n1 → n2 → n3         (原鏈,保持有效)
     ↘ n1'                  (新內容)
        ↘ n2' ← 把 n2 的 changeset 重新套到 n1' 上
           ↘ n3'
```

每一步重新套用有三種結果,**必須明確回報**(不默默近似):
1. **乾淨套用** → 新節點產生,digest 重新蓋章;
2. **衝突**(目標節點已不存在、值已被別的改動佔用…)→ 回報衝突,要求人介入;
3. **語意驗證失敗**(`check_document`)→ 同上。

這正是 git rebase 的語意,也是 §0.2 缺的那層。

### 2.3 快取:衍生物,永不權威

docs/06 §5 定「狀態永遠是 ChangeSet 的函數,**不存副本**(單一資訊源)」。
故 memoize 的求值結果:

- **是衍生物**,任何時候可丟棄重算;
- **不屬於節點的儲存資料**(不進 §2.1 的結構);
- 因節點不可變,快取**永不失效**——這是不可變模型的直接紅利
  (現行的 stale 傳播機制連同 `set_changeset` 一併移除)。

### 2.4 節點識別【P57】

- **內容定址**(content-addressed):`NodeId = sha256(parents ‖ changeset ‖ nativization)`,
  與 git commit hash 同構,且滿足 P26「決定性、禁隨機/時間戳」。
- **人類可讀名字是另一層**(`label` / 外部的具名指標),**不是身分**——
  承 P45「標籤不取代穩定 id」的既有精神。
- 內容定址順帶給到:相同內容自動去重、完整性可驗、跨機器同一節點同一 id。

## 3. 三道 digest 的重新定位【P58】

digest 不是「防止 base 改變」——不可變模型下 base 本來就不會變。它的真正用途是:

| 用途 | 說明 |
|---|---|
| **跨系統流通** | 一份 `.chg` 檔單獨拿到別處時,確認基底沒被掉包(步驟 14 的原始用意) |
| **rebase 判定** | 重新套用時,digest 不符 = 「這是 rebase,不是重放」——**觸發 §2.2 的三分結果**,而非直接失敗 |

所以步驟 14 的契約**語意不變**(digest 仍然驗、仍然擋),只是**多了一條 rebase 路徑**
供演化樹使用;直接 replay 的行為一字不動。

## 4. P 系列決策

| # | 決策 |
|---|---|
| **P56** | **演化樹節點不可變**:`LanguageNode { parents, changeset, nativization, label }` 為儲存全部;**不提供就地編輯**——「改一個節點」= 建新節點。可變的只有具名指標。此舉消滅「digest 契約 vs stale 傳播」的結構衝突(§0),並使 memoize 快取**永不失效** |
| **P57** | **節點內容定址**:`NodeId = sha256(parents ‖ changeset ‖ nativization)`,與 git commit hash 同構、滿足 P26 決定性;人類可讀 `label` 是另一層,不是身分(承 P45) |
| **P58** | **digest 的職責重新定位**:不是「防止 base 改變」(不可變模型下不會變),而是①跨系統流通的防掉包 ②**rebase 判定**——不符時走「重新套用」三分結果(乾淨/衝突/驗證失敗),**明確回報不默默近似**。步驟 14 契約語意不變,只多一條 rebase 路徑 |

## 5. 對現行實作的影響

`changeset/src/evolution.rs`(步驟 16 ①②)需要調整:

| 現況 | 調整 |
|---|---|
| `set_changeset` 就地改節點 | **移除**(P56);改以「建新節點」表達 |
| `invalidate` 沿後代標 stale | **移除**(不可變 ⇒ 快取永不失效) |
| `NodeId(String)` 使用者給名 | 改為內容雜湊(P57);`label` 另存 |
| base 不符 → 直接 err | 保留為 replay 路徑的行為;**另加** rebase 路徑(P58) |
| 缺 `nativization` 欄位 | 補上(docs/06 §4) |

已寫的 14 個測試中,memoize / replay 正確性 / 圖不變式的部分可留;
`set_changeset` 與 stale 傳播的 4 個測試隨機制移除而改寫為 rebase 情境。

## 6. 界線 / 待裁

1. **rebase 的衝突偵測有多細**?最小可行 = 「重新 resolve,失敗即衝突」;
   更細的「哪一句衝突、為什麼」需要逐句嘗試——建議 MVP 先做前者。
2. **具名指標(branch/head)的形式**——本檔只定「可變的是指標不是節點」,
   指標本身的 API 與持久化形式待定。
3. **快取要不要持久化**?§2.3 定它是衍生物;持久化純屬選配優化,不影響正確性。
4. **docs/06 §5 的 memoize/stale 段落**應隨 P56 更新措辭(stale 傳播在不可變模型下
   不再需要)——待本檔核准後回寫。
