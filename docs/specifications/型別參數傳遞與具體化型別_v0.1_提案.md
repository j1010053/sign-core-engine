> **狀態：原提案，2026-10-17；2026-10-18 已實作使用者要求的巢狀宣告與型別傳遞子集。**
> 現行契約及明確邊界見 [I32](../implementation/nested-types-and-specialization.md)，可執行範例見 [XP 教學](../../tutorials/nested-types/README.md)。`NP.member` 別名與 Sign 成員作用域另由 [I33](../implementation/trait-template-consistency.md) 實作；builder 等延伸仍未實作。

> 後續需求：使用 `XP<Noun>` 時，不再手寫 `NBarComp`／`NBarAdjunct`；第 11 節提出巢狀構式與外層參數捕捉方案。
> 本文保留規劃當時對 [P76](參數化trait宣告_v0.1.md) 的修訂理由與舊現況；實際覆寫範圍以 I32／I33 為準。

## 1. 設計方向與引擎現況

採用 **明確宣告、明確傳遞、遞迴型別引用、保留型別實參**。
沿用 `.lang` 的縮排區塊、`trait`、`belongs`、`Name[0]`、`[Constraint]` 與 `export`。
每一個頂層 trait 都宣告自己的參數，不因參數同名而共用綁定，也不自動補出漏寫的參數。

引擎輪廓：

| 面向 | 現況與本提案邊界 |
|---|---|
| 表示 | Rust Language AST；trait 是可掛載模板／分類契約，Sign 是詞彙或帶槽構式，Paradigm 選取 Sign |
| 修改單位 | identity-addressed Primitive Edit、ChangeSet、evolution graph；具體化不得另造來源 Sign |
| 作用域 | 套件／文件與 trait 型別參數；現有 `export` 控制套件邊界，沒有 trait 私有作用域 |
| 執行 | 解析、作用域綁定、trait 展開、ontology／契約驗證、填槽、完整 derive；需在契約比較前完成參數替換 |
| 時間與隨機性 | 本提案只有編譯期型別處理，不新增歷時事件或時間軸，不改既有 seeded sampling |
| 身分與追蹤 | 保留來源宣告／Sign 身分；編譯型別引用由宣告及實參識別，不能靠顯示字串或發現順序識別 |
| 對外表面 | canonical source、identity sidecar、package resolver、checker/compiler、query、CLI、ChangeSet／存檔重開 |
| 已知缺口 | 複合 slot 型別不能 parse；generic marker 被禁止；簡單泛型 slot 實際掛載可報 `SLOT_CONFLICT` |
| 驗證入口 | `cargo test --workspace --locked --offline`；具體案例必須走 `derive` 與 replay／reopen，而非只驗展開 helper |

對目前程式的核對入口：
[parser](../../crates/language/src/parser.rs)、[參數替換](../../crates/language/src/compile.rs)、
[ontology](../../crates/language/src/ontology.rs)、[package scope](../../crates/language/src/package_scope.rs)、
[P76 測試](../../crates/language/tests/p76_parameterized_trait.rs)。
本次規劃不宣稱這些缺口已修復。

## 2. 程式語言參考與取捨

以下資料於 2026-10-17 查閱。只採用有助於 `.lang` 的規則；這些語言的整套型別系統不是本提案的契約。

| 參考 | 可借用的規則 | `.lang` 的選擇 |
|---|---|---|
| [Rust Reference：generic parameters](https://doc.rust-lang.org/reference/items/generics.html) | 宣告使用 `<T>`，參數有明確作用域；不同宣告不靠同名自動共用參數 | 保留現有 `<T>`；每個頂層 trait 自行宣告 |
| [C#：generic interfaces](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/generics/generic-interfaces) | 泛型介面可無成員；父介面的實參可由本地參數與固定型別組成 | 允許 `marker trait X-bar<T>`，以及 `belongs Pair<Fixed, T>` |
| [TypeScript Handbook：generics](https://www.typescriptlang.org/docs/handbook/2/generics.html) | 宣告層級的參數可供該宣告的成員共同使用 | 同一 trait 的所有 blocks／維度共用其參數；不採用結構相似即相容的分類模型 |
| [C# 規格：constructed types](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/types#84-constructed-types) | 已套入實參的型別由泛型宣告與對應實參決定 | `X-bar<Noun>` 和 `X-bar<Verb>` 保留不同的分類身分 |
| [.NET：variance](https://learn.microsoft.com/en-us/dotnet/standard/generics/covariance-and-contravariance) | 泛型型別的子型別關係需要獨立規則，不能只由實參繼承關係推斷 | 第一版採不變性，不新增 `in`／`out` 語法 |

特別保留 `.lang` 的分工：`belongs` 聲明分類，block mount 安排模板內容，slot 接受
Sign／token；不增加 Rust 的 `impl`、C# 的 `new` 或 TypeScript 的 `extends` 關鍵字。

## 3. 建議的 phrase 模板

本節展示頂層模板明確傳遞參數的基礎方案，仍需具體 Sign 包裝。
若要省去每種詞類的包裝宣告，改採第 11 節的巢狀構式方案；兩者不是要同時貼入同一份來源。

```lang
export marker trait X-bar<T>:

export trait XP<T>:
    syn:
        slots:
            spec [*]?
            head [X-bar<T>]

trait bar-adjunct<T>:
    belongs X-bar<T>
    syn:
        slots:
            adjunct [*]?
            head [X-bar<T>]

trait bar-comp<T>:
    belongs X-bar<T>
    syn:
        slots:
            head [T]
            comp [*]?
```

`T` 可以命名為 `X`；採用 `T` 只是避免與詞彙層名稱混淆。不需要另宣告 `marker trait T`。
`X-bar<T>` 的參數即使不出現在任何內容欄位，也用來區分類別，因此 marker 仍有保留它的理由。

這份範例只定義槽位與分類。`?` 是可省略，不是零到多個；遞迴出現在 head 的型別限制。
語序、音形、語義與特徵傳遞由具體構式另寫，不能從槽位列出順序推導。

同套件可定義具體分類與消費端，以下只展示型別／掛載部分：

```lang
marker trait Noun:
marker trait Verb:

sign NBarComp:
    belongs bar-comp<Noun>
    bar-comp[0]

sign NBarAdjunct:
    belongs bar-adjunct<Noun>
    bar-adjunct[0]

sign NP:
    belongs XP<Noun>
    XP[0]

sign VP:
    belongs XP<Verb>
    XP[0]
```

展開與填槽時必須成立：

| 層次 | 已確定的契約 |
|---|---|
| `NP` 使用 `XP<Noun>` | head 必須滿足 `X-bar<Noun>` |
| `NBarAdjunct` 使用 `bar-adjunct<Noun>` | 本身屬於 `X-bar<Noun>`；其 head 仍要求 `X-bar<Noun>` |
| `NBarComp` 使用 `bar-comp<Noun>` | 本身屬於 `X-bar<Noun>`；最底層 head 要求 `Noun` |
| `VP` 使用 `XP<Verb>` | head 要求 `X-bar<Verb>`，不能接受上述名詞投射 |

這是編譯期的型別傳遞。`head [X-bar<T>]` 不會自行挑選、建立或呼叫 `bar-comp<T>`；
使用者仍須提供已建立的構式／token。型別檢查保證各層實參一致，不在填槽時把名詞型別
重新賦予原本屬於動詞投射的 filler。

## 4. 第一版的語法與語義規則

### 4.1 參數宣告、綁定及完整實參

- `trait Name<T, U>:` 宣告依序排列的型別參數。marker trait 同樣可宣告；global trait、
  Sign 與 Paradigm 暫不新增型別參數。
- 參數作用域是自己的整個 trait，包括所有 blocks／維度。頂層的其他 trait 不在其中。
- 每個參數是獨立綁定：`Outer<T>` 可以傳給 `Inner<U>`，透過 `Inner<T>` 建立 `U := T`。
  同名的參數不會自動互相綁定，重新命名本地參數不改語義。
- 實參依位置傳遞，而且必須全數提供。`Inner<Fixed, T>` 合法；若 Inner 要兩個參數，
  `Inner<Fixed>` 是錯誤，不自動增加 Outer 的參數。
- 本地參數優先於同名套件類別；在其作用域外，同名詞若存在則仍指那個獨立類別。
  不存在的名字必須報錯，不自動視作參數。套件限定名稱仍明確指向套件宣告。
- Sign 是具體消費端，展開完成後不得留下自由型別參數。

例如參數名稱不同仍能傳遞：

```lang
trait inner<H>:
    syn:
        slots:
            head [H]

trait outer<T>:
    belongs inner<T>
    inner[0]
```

`outer<Noun>` 的綁定是 `T := Noun`，接著 `H := Noun`，最後為 `head [Noun]`。
這種「固定一部分、其餘用本地參數傳入」足以支援模板組合，不需要省略位置的實參列表。

### 4.2 統一的型別引用

在 slot／role constraint、`belongs` 的實參、型別 bound、分類 guard 及泛型 mount
中，使用同一種可遞迴的型別引用：

```text
Noun
English.Noun
T
X-bar<T>
Phrase.XP<English.Noun>
Holder<X-bar<English.Noun>>
```

原提案僅接受範疇型別。現行 [I35](../implementation/sign-instance-types.md) 已擴充接受 Sign 實例型別；仍不能填字串、enum 值或省略必要實參的泛型模板。
`T` 是型別，不是型別建構子；`T<Noun>` 不在第一版範圍。

`belongs` 的外層目標仍須為具名 trait，例如 `belongs X-bar<T>`；不開放 `belongs T`
動態改換繼承目標。slot 可以寫 `[T]`，因為這是 filler 的限制，不是模板本身的繼承關係。

`[*]` 維持 AnySign，只出現在允許 wildcard 的 constraint 位置；`X-bar<*>` 不表示
「任意一種 X-bar」。若要跨所有實參的共同分類，應另外設計具名的非泛型上位分類。
一般 feature 值、`case [syn.number]` 的 bundle 欄位、phon 字面值都不解讀成型別引用。

### 4.3 Bound

沿用 `T: Bound`，bound 可為具名或已套入實參的型別：

```lang
trait Projection<T: Word>:
    syn:
        slots:
            head [T]

trait WithBar<T, B: X-bar<T>>:
    syn:
        slots:
            head [B]
```

bound 可引用同列表中較早的參數；第一版不接受自我／向後參數引用的 bound，也不引入
聯集、交集或 `where`。跨 trait 傳入尚未具體化的參數時，外層 bound 必須足以保證
內層 bound；不能等到某次偶然填入相容實參才把錯誤的泛型宣告放行。

### 4.4 掛載保持 `.lang` 的風格

標準寫法繼續是：

```lang
sign NP:
    belongs Phrase.XP<English.Noun>
    Phrase.XP[0]
```

`belongs` 綁定實參並建立分類；`Phrase.XP[0]` 從同容器中唯一相符的 `belongs` 取得實參。
型別參數不寫在普通 Sign 呼叫的 `()` 裡。

擬增加的明確掛載形式如下，供多個實例需要區分時使用：

```lang
sign NP:
    belongs Phrase.XP<English.Noun>
    Phrase.XP<English.Noun>[0]
```

- `Name<T>[n]`：指定實例的第 n 塊；`Name<T>`／`Name<T>[]`：指定實例的全部塊。
- 泛型的明確掛載須有同容器中相符的 `belongs Name<T>`，避免分類與展開使用不同實參。
- `Name[n]`／`Name`／`Name[]` 作泛型簡寫時，必須能找出唯一的實例；找不到或有多個
  就報錯，不依宣告順序猜測。非泛型既有寫法不變。
- P5 的全部 blocks 必須放置規則，改為逐個具體實例檢查。
- 能定位多個實例不代表其內容一定相容；同名 slot／feature 的既有衝突規則仍適用。

### 4.5 型別身分、匹配與不變性

具體化型別由「解析後的宣告身分＋依序排列的實參型別」決定；別名只影響名稱寫法。
來源中只有一個 `X-bar<T>` 宣告，`X-bar<Noun>`／`X-bar<Verb>` 是其編譯期型別，
不是新的來源宣告，也不是新增的 lexical Sign。

```text
X-bar<Noun> != X-bar<Verb>
bar-comp<Noun> <: X-bar<Noun>        # 來自明確的 belongs
```

第一版泛型參數採不變性。即使 `Noun <: Nominal`，也不能自動推得
`X-bar<Noun> <: X-bar<Nominal>`；普通分類的既有子類匹配仍然有效。
套件限定名稱解析後若指同一宣告與實參，就必須得到相同型別。

不得把所有實例退化成裸名 `X-bar` 進行填槽／guard／query 匹配。未填實參的泛型名稱
不是可用的 runtime 分類；source 編輯 selector 可繼續以宣告名稱定位模板本身。

### 4.6 遞迴與終止

`head [X-bar<T>]` 是型別引用，可用來建立任意有限深度的投射；不因這個引用就展開一份
head，也不能預先遞迴產生所有可能的 filler。

內容掛載與分類繼承的循環仍是錯誤。診斷要同時記錄宣告鏈與實參；不能只靠重複的
具體型別名稱偵測，否則 `Loop<T> -> Loop<Wrap<T>> -> ...` 可能無限產生不同實例。
同一宣告在內容展開／繼承鏈上形成循環時應拒絕；單純 slot 型別的遞迴不納入這條循環。

## 5. export 與「只有 XP 能引用」

參數傳遞本身不提供存取控制。第一階段沿用 [I31](../implementation/package-exports-and-qualified-names.md)：

- `T` 是局部參數，不是可由套件匯出的獨立宣告。
- 無 `export` 的頂層 helper，整個套件都可用；套件外不能直接命名它。
- 公開 XP 可在自己的實作中使用私有型別；每一層實參的名稱也必須遵守來源作用域。

第 3 節的兩個 `bar-*` 是私有的，所以具體消費端示例放在同一套件。若要讓另一個套件
自己掛載 `bar-comp<English.Noun>`，必須公開該模板，或另外提供可使用的公開建構入口。
只公開 XP、隱藏所有建立合法 head 的入口，會得到無法由外部組裝的 API；這要在套件
介面設計時驗證，不能靠繞過私有型別檢查解決。

「同套件其他定義也不能引用，只限 XP 及其內部 helper」在第 11 節提出下一階段的詞法作用域方案。
它需要巢狀宣告、外層參數捕捉、成員可見性與可用的建構入口；不能把頂層 helper
因為寫在 XP 下方，就暗中當成 XP 的成員。第一階段不加入 `private`／`protected` 關鍵字。

## 6. 最小文法骨架

以下是新增部分的 EBNF 摘要，其他現行語法保留；QualifiedName 沿用 `.` 限定名稱。
Identifier 沿用既有字元規則，包含 `X-bar` 這類名稱。

```text
TypeParameters = "<" Parameter { "," Parameter } ">" ;
Parameter      = Identifier [ ":" TypeRef ] ;
TypeArguments  = "<" TypeRef { "," TypeRef } ">" ;
TypeRef        = QualifiedName [ TypeArguments ] ;
Constraint     = "[" ( "*" | TypeRef ) "]" ;
Slot           = Identifier Constraint [ "?" ] ;
Belongs        = "belongs" QualifiedName [ TypeArguments ] ;
Mount          = QualifiedName [ TypeArguments ] [ "[" [ Integer ] "]" ] ;
TraitHeader    = [ "export" ] [ "marker" ] "trait"
                 QualifiedName [ TypeParameters ] ":" ;
```

語義解析將裸名的 TypeRef 區分為本地參數或具名範疇。`<>`、實參不足／過多、未綁定參數、
把參數當建構子、私有跨包引用都要給出明確錯誤。第一版不新增尾逗號、預設實參、具名實參、
推斷佔位符或 `Name<T>.Nested`；點號仍只有已支援的套件限定意義。
套件自身的宣告仍使用裸名；caller 使用限定宣告名稱建立公開定義的本地覆寫時，
沿用 I31 的檢查。上述 TraitHeader 的 QualifiedName 不開放額外的巢狀宣告命名空間。

## 7. 與現有契約的差異

| P76／目前實作 | 提案中的處理 |
|---|---|
| `<T>`、`<T: Bound>`、`belongs Name<Args>` | 保留表面形式，補完整驗證與具體化 |
| 型別參數主要替換 slot／role 的單一字串類別 | 擴為遞迴 TypeRef，所有型別位置使用同一套綁定 |
| marker 不允許參數，理由是沒有內容可替換 | 擬修訂：參數同時決定分類身分，允許空內容的 generic marker |
| P76 部分段落允許省略實參並自動向外傳播 | 擬收斂為完整位置列表：外層明確宣告，再以 `Inner<Fixed, T>` 傳遞 |
| 以裸 trait 名建 ontology／索引 | 需保留完整實參的編譯型別身分；來源 selector 與 runtime 型別名稱分開 |
| `Name[0]` 取得同容器的實參 | 保留唯一綁定簡寫，新增明確的 `Name<Args>[0]` |
| export 只到 package 層 | 基礎型別傳遞階段保留；第 11 節另提 XP 專用 helper 作用域 |

已重現的實作問題也要作為回歸案例：簡單 `XP<B>` 的 `head [B]` 在掛載為具體 Sign
時可能產生 `SLOT_CONFLICT`；未掛載的 `belongs X-bar<X>` 即使目標零參數，部分入口
仍會放行。新實作須檢查所有宣告中的 arity，而不是只在內容展開時驗證。

未實作並驗收前，不修改 P76 的「已裁定」狀態、不把本提案編為新的已裁定 P／I 號，
也不把提案範例加入宣稱可執行的教學。

## 8. 可執行的實作順序

1. **統一型別表示與綁定。** 引入遞迴 TypeRef／具作用域的參數身分，接 parser、printer、
   package 限定名稱與完整 arity／bound 驗證。每個泛型宣告建立獨立環境；替換按節點進行，
   不對名稱／phon／feature 字串做全域文字替換。
2. **完成具體化與契約合併。** 在 Sign 的 slot／role 契約比較前替換完所有參數；同一
   實例的內容不能同時以「未替換模板」與「已替換內容」參與合併。讓先前的 `SLOT_CONFLICT`
   最小反例通過，再加入 generic marker 及不同實參的隔離。
3. **串完整執行與查詢。** 類別閉包、slot／role matching、guards、candidate selection、
   semantic types、query filters 與診斷使用同一型別身分。API 接收的外部型別字串經同一
   TypeRef parser／作用域解析；不要只替 slot parser 加尖括號。
4. **保留修改與歷史。** source／identity、rename/reference traversal、ChangeSet insert/update、
   reconstruct、replay、package alias／內容鎖、compile cache 一起更新。cache 必須區分實參；
   語義版本須變更。若公開 DTO 需要新 schema，明確遷移，不把舊裸名靜默解讀成 wildcard。
5. **封閉端到端缺口。** 先跑下方最小正反例，再跑完整 workspace；editor 高亮、CLI、
   project reopen 與相關教學同步。只有通過這些出口後才宣稱通用模板可用。

具體化是 compiled projection：不改寫來源模板，不複製來源 Sign ID，不在歷時 graph
新增未由使用者宣告的節點。trace 可以記錄「來源模板＋實參＋被掛載的 block」。
編譯索引應按需建立、以宣告和完整實參去重，slot 遞迴不觸發無限實例列舉。

## 9. 驗收矩陣

這是待實作的驗收要求，不是已通過的測試報告。

| 行為 | 最小正例與反例／可觀測斷言 |
|---|---|
| 多層傳遞 | `Outer<T> -> Middle<T> -> Inner<T>`；改變各層參數名字仍得到同一底層約束 |
| phrase 各層一致 | Noun 路徑接受名詞詞彙 head；把任一層換成 Verb，明確拒絕 |
| 多個實例獨立 | 同一系統同時編譯 NP／VP；宣告／編譯順序互換後，彼此的 slot 與分類不污染 |
| generic marker | 空內容的 `X-bar<Noun>`／`X-bar<Verb>` 仍是不同型別；來源 marker 只有一個身分 |
| 複合 TypeRef | 巢狀型別實參、套件限定實參、role／guard 與 slot 使用相同解析／替換結果 |
| 作用域 | 外層參數不自動滲入頂層 helper；同名局部參數不捕獲其他宣告的參數 |
| arity／bound | 未使用的錯誤宣告也被拒絕；錯誤數量、未知型別、外層 bound 不足皆報錯 |
| 掛載 | 唯一綁定簡寫等同明確掛載；多實例簡寫拒絕；逐個實例檢查缺少 blocks |
| 契約合併 | 泛型 head 替換後成功；真正不相容的同名 slot 仍須失敗，不能為修泛型而放寬所有衝突 |
| 遞迴 | 兩層 adjunct 接一層 comp 的有限結構成功；內容／繼承循環及成長型實參循環拒絕 |
| 封裝 | 公開模板內部引用私有型別可用；外部直接命名私有型別／實參仍拒絕；公開 API 有可達的合法 filler |
| 完整 derive | 補上 phon／sem 後走 `derive`；同音形 N/V filler 必須由型別區分，不能只斷言表層字串 |
| 保留身分與歷史 | canonical round trip、source／identity reopen、ChangeSet replay 後，類別實參、來源 ID 與結果一致 |
| cache／別名 | 同來源使用不同實參或 alias 目標不得誤用舊結果；同一宣告的不同合法別名解析為同一型別 |

## 10. 明確延後的功能

獨立宣告型別參數的 generic Sign／Paradigm、具名或預設實參、由 filler 推斷參數、
higher-kinded types、聯集／交集、variance annotation、自我參照 bound，
都不作為第一版型別傳遞的前置條件。
XP 專用的巢狀 helper／外層參數捕捉改於下一節具體規劃；要達到「不手寫各詞類包裝」，
就必須完成這層擴充，不能只完成基礎 TypeRef 傳遞便宣稱需求完成。

## 11. 巢狀構式隨 XP 一起具體化（後續提案）

### 11.1 參考與適用範圍

2026-10-17 補充需求：`belongs XP<Noun>` 應足以綁定內部構式，不要求再宣告
`NBarComp`／`NBarAdjunct`。沿用 `<Noun>` 作型別實參；`XP[0]` 仍是 block 掛載。

[C# 規格 §15.3.9.7](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#15397-nested-types-in-generic-classes)
允許巢狀型別直接使用外層的型別參數，內層引用也可省略外層限定；
[C# 巢狀型別指南](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/nested-types)
則提供預設私有成員的參考。這裡借用的是詞法作用域與參數捕捉，並非引入 C# 的物件繼承或配置物件語義。

### 11.2 建議寫法

```lang
export trait XP<T>:
    marker trait X-bar:

    sign bar-comp:
        belongs X-bar
        syn:
            slots:
                head [T]
                comp [*]?

    sign bar-adjunct:
        belongs X-bar
        syn:
            slots:
                adjunct [*]?
                head [X-bar]

    syn:
        slots:
            spec [*]?
            head [X-bar]

sign NP:
    belongs XP<Noun>
    XP[0]

sign VP:
    belongs XP<Verb>
    XP[0]
```

假設 `Noun`／`Verb` 已定義。以上仍是型別／作用域示例，省略音形、語序、語義及實際組裝入口。
內部的 `bar-comp`／`bar-adjunct` 改為 `sign`，因為它們要成為可填槽、可呼叫的構式。
只把它們改成巢狀 `trait`，仍然只有模板，不會因此自動得到可呼叫的 Sign。

### 11.3 捕捉、具體化與掛載

- 巢狀宣告可引用外層 `T`，不必再寫 `<T>`。先完成詞法綁定，再替換實參；不能只按字串同名替換。
  頂層 helper 仍不捕捉 XP 的參數。此擴充先不給巢狀 Sign 自己增加參數列表。
- `XP<Noun>` 綁定整組內部宣告：`bar-comp` 的 head 要求 `Noun`，`bar-adjunct` 的 head
  要求同一 XP 實例的 `X-bar`。`XP<Verb>` 得到獨立的對應型別與構式實例。
- 巢狀 marker 即使沒有顯式參數列表，其型別身分也包含外層實例。
  診斷可顯示 `XP<Noun>.X-bar`／`XP<Verb>.X-bar`；兩者不能互相填槽。
  這種診斷名稱不代表外部有權引用它。
- 具體化的成員以「來源成員身分＋外層宣告及完整實參」識別，按需建立並去重。
  兩個 Sign 同樣使用 `XP<Noun>` 時，共享這組編譯實例，不因消費者名稱不同再造一組類別。
- `belongs XP<Noun>` 建立綁定，`XP[0]` 掛載 XP 自己的內容。巢狀宣告不算 XP 的內容 block，
  內部 `head`／`comp` 不會被攤平合併進 NP 的 slots。
- 不把編譯實例寫成新的頂層來源 Sign，也不製造新的歷時節點。
  來源成員仍各有穩定身分；trace 與 runtime handle 另帶外層實參，以免不同實例混用。

### 11.4 可見性與可用的建構入口

本擴充的最低範圍是：未加 `export` 的巢狀成員只在 XP 的詞法作用域及其內部宣告中可見。
同套件的其他宣告也不能直接命名；`NP belongs XP<Noun>` 不會讓 NP 本地內容取得私有權限。
掛入 NP 的 XP 內容則保留定義時的引用綁定，能繼續使用 XP 的私有成員。
XP 的 `export` 不會遞迴公開內部名稱，裸名也不提升到套件層。

若內部構式全部私有，XP 就需要在自己的作用域內定義可從外部使用的組裝流程，例如以
已明確指定的 Sign application／autofill 組裝 head，或提供公開建構入口。
單有上面的分類與 slots 範例，不足以讓外部直接建立私有的 X-bar filler。
型別限制不會自動選 comp／adjunct，也不會自動挑詞或展開遞迴。

巢狀公開成員若採 `export`，須另擴充 `XP<Noun>.member` 的成員路徑、可見性與呼叫規則，
並檢查整條路徑的存取權；這不是第 6 節基礎文法已支援的套件限定名稱。
本節未把 `NP.member` 當成自動轉送到 XP 的別名，也未把公開建構入口的完整語法視為已裁定。

### 11.5 追加實作與驗收要求

先完成第 8 節的型別傳遞，再加入巢狀宣告 AST、詞法 scope、成員具體化與私有存取檢查，
並串接 source／identity、ChangeSet、reopen、query 與編輯器。驗收至少包括：

| 要求 | 可觀測證據 |
|---|---|
| 無手寫包裝 | NP／VP 來源不含 NBarComp 等宣告，仍可透過合法建構入口完成有限短語 derive |
| 實參捕捉 | XP<Noun> 最底層只接受 Noun；外層參數改名後結果相同 |
| 型別隔離／去重 | NP／VP 不混用 X-bar；兩個 XP<Noun> 消費者共享同一成員實例 |
| 詞法私有 | 套件外、同套件兄弟宣告與 NP 本地內容直接引用皆失敗；XP 定義內的引用成功 |
| block 分離 | 增加巢狀宣告不改 XP[0] 的內容編號，也不在 NP 增加 comp／adjunct slots |
| 來源與歷史 | dump／replay／reopen 保留巢狀成員身分及實參；不生成 NBarComp 等來源節點 |
| 遞迴與選擇 | 只具體化有限成員，不預先生成無限 adjunct 鏈；實際選擇由明確的建構流程處理 |
