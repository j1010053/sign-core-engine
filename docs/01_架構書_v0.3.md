## 1. 專案概述

本專案是一套桌面端的人工語言(conlang)設計工作台。核心賣點是「可調式人為干涉程度」:使用者可以在每個模組獨立選擇手動、輔助或自動模式,只投入自己在意的決策,其餘交由系統依語言類型學規律生成。第一階段以完全離線、可重現的規則+統計引擎為基礎;第二階段再引入 LLM 作為選配外掛。

優先開發的核心模組為**音系與音變演化**、**造詞與詞典管理**;由上而下的語法化演化與型態句法列為緊接其後的重點擴充。Phase 2 涵蓋四項:LLM 外掛、文字系統、語音模擬、多主體(multiagent)演化模擬(見 §4.6)。

## 2. 核心設計原則

**干涉光譜(Intervention Spectrum)。** 每個模組提供三檔:手動(使用者定義一切)、輔助(使用者只設定關鍵約束與規則,系統補完其餘)、自動(系統依類型學統計分佈生成,事後可修改)。三檔可在同一專案中混用,例如音系全手動、造詞用輔助。

**來源標記與鎖定。** 每一筆資料(音素、規則、詞條、構式)都記錄來源:`manual` / `generated` / `generated-then-edited`。生成內容可單獨「鎖定」後重骰(reroll)其餘部分,避免重新生成時破壞已滿意的成果。

**可重現性。** 所有隨機生成都基於專案層級的種子(seed)加上模組內遞增序號,同一 seed 必得同一結果。這是離線引擎的關鍵優勢,也讓「重骰」行為可以被復原(undo)。

**分層結構檔(Linguistic Strata)。**另設唯讀旁註層**(docs/07 §5c)掛載非形式化知識——文化說明、隱喻傾向、使用者語料;不參與演化,是「手動」創作內容的家。** 一個語言不是一個扁平檔案,而是一疊互相連結的層:語用/篇章、語意、句法、型態、音系、辭典、正字法。每一層有自己的編輯器與資料結構,但彼此以參照連結(例如型態層的一個詞綴指向它在辭典層的條目與音系層的實際音形)。這讓「保留不同層級的設計細節」成為資料模型的基本性質,而非附註;也讓演化可以按層計算差異(見 §6)。

**演化的雙向軸(Two Axes of Change)。** 本工具把語言演化拆成兩條互相交會的軸:

- **音變軸(由音系向上)**:音素/特徵層的規則性變化,重塑音位配列與詞形。這是 §4.2 的音變引擎。
- **語法化軸(由上而下)**:材料沿著語法化斜坡(cline)從語用/篇章向句法、再向型態下沉,最終沉澱進辭典,成為新的功能語素。這是 §4.3 的語法化引擎,對應 Givón 的名言「今天的型態是昨天的句法」。

兩軸並非獨立:語法化產生的新黏著語素會進入音變引擎接受「語音磨損(erosion)」,磨損又促成進一步的融合。**erosion 就是兩個引擎在時間軸上交會的地方**,實作上讓語法化引擎的輸出可以直接排入音變規則鏈。

**演化即分支。** 歷時演化採用類似 git 的樹狀模型:祖語是根節點,每個子節點記錄「相對於父節點、跨各層的變化集」(音變規則序列 + 語法化事件 + 手動編修),天然支援語言家族與姊妹語言。

```
┌──────────────────────────────────────────────┐
│ UI 層(桌面前端)                                │
│  儀表板 / 各層編輯器(語用…音系) / 規則編輯器    │
│  詞典表格 / 演化樹視圖 / 造詞面板 / 文法檔勾選盤 │
├──────────────────────────────────────────────┤
│ 應用層                                         │
│  專案管理、undo/redo、匯入匯出、跨層一致性檢查  │
├──────────────────────────────────────────────┤
│ 引擎層(純函式核心,無 UI 依賴)                  │
│  ├ 音節/詞形生成器(規則+加權統計)               │
│  ├ 音變引擎(autosegmental DSL 直譯器 + 選配 FST) │
│  ├ 語法化引擎(斜坡路徑 + 重新分析 + erosion)    │
│  ├ 借詞改造引擎(donor→recipient 修復規則)       │
│  ├ 文法檔約束器(勾選 → 限制自動演化候選)         │
│  ├ 類型學/斜坡先驗資料庫(內建靜態資料)           │
│  └ [Phase 2] LLM 外掛介面                       │
├──────────────────────────────────────────────┤
│ 資料層                                         │
│  SQLite(專案檔,分層 schema).json 匯入匯出     │
└──────────────────────────────────────────────┘
```

引擎層與 UI 完全解耦,方便未來加 CLI、批次演化或測試。借詞改造引擎與音變引擎共用同一套 DSL 機制,只是語意不同(修復規則 vs 歷時規則)。

## 4. 核心模組設計

### 4.1 音系模組(Phonology)

負責定義單一語言節點的共時音系,包含四個子系統。

**音素庫。** 以 IPA 表格選取器呈現(輔音表、元音圖),每個音素附帶語音特徵(feature bundle,如 [+voice, +coronal]),特徵是後續音變規則以自然類(natural class)書寫的基礎。輔助模式下,使用者選定少數核心音素後,系統依共現統計(implicational universals,例如有送氣塞音系列傾向成套出現)提出補齊建議,使用者逐項接受或拒絕。

**音位配列(Phonotactics)。** 使用音節模板語法定義,如 `(C)(G)V(N|S)`,其中 C、G、V 等為使用者自訂的音素類別。額外支援禁用序列(filter,如 `*ji`, `*wu`)與位置限制(某音素僅限詞首)。

**超音段。** 重音系統(固定位置/重量敏感)與聲調系統(聲調庫、tone-bearing unit 設定)。第一版可先做固定重音與簡單字調;超音段在資料模型中直接以獨立 tier 表徵(見下段),不以音段上的變音符模擬——後者是既有工具的公認痛點(見 §8)。

**多層表徵(Autosegmental Tiers)—— 核心差異化。** 詞的表徵不是單一音段串,而是骨架 + 多條平行 tier + 連結線。完整設計見另附《Tier 音變 DSL 語法規格 v0.3》,此處摘要其定案本體論。tier 分兩類、用兩套不與彼此混淆的語彙,分野的第一性原理是**是否與時間軸綁定**:

- **韻律層(prosodic tiers)= 時間軌道**:mora、syllable、foot、pword,向上延伸至 φ(音韻短語)、ι(語調短語)、U(發語)七層(《架構修補01》P1:`Word` 是由 sign 組合按需建構的**臨時韻律域**,預設 ω,sandhi 擴至 φ/ι/U;非儲存單位)。由剖析(parse)從骨架切出,層間以**支配(domination)**相連,嚴格分層、相鄰、全覆蓋,因而**內在有序**。動詞是結構性的(parse / reparse / dominate / release)。
- **旋律層(melody tiers)= 時間乘客**:tone、nasal、ATR/和諧。不綁時間,只有**聯結(association)**到韻律錨點後才獲得時間位置,允許多對多、浮游、無內在序。動詞全是聯結圖的加減邊,以 `associate` / `delink` 為唯一原語,`spread` / `dock` / `shift` / `merge` 皆其具名特例。

關鍵設計是**任何特徵都能提升為一條旋律層**——鼻化、母音和諧名義上是音段特徵,行為上是詞層現象(autosegmental 的核心洞見),不該只有重音/聲調享有。旋律層自帶**穩定性(stability)**:音段被刪時掛在其上的自體段不消失,改為浮游並留在序列原位,等 `dock` 重掛或末端拼讀處理——這正確產生聲調轉移與連調,線性模型(含 Lexurgy)在此會丟失。旋律的預設狀態是 **Ø(未指定/零特徵)**,使 H / L / 無調(Ø)三分與私有特徵(有 `+nasal`、無則 Ø)自然成立。每條 tier 另有一個可宣告的**可見性(visibility)**屬性,控制其自體段對規則的預設能見度(MVP 用於「浮游 vs 已聯結」——預設 `linked-only`,浮游者須顯式選取);這個屬性刻意設計成通用機制,未來可擴展為邊緣不可見性(extraprosodicity,如令詞末成分對某規則隱形),屆時是擴充而非改造。

三條互不重疊的存取能力,對應三種計算本質:

1. **tier 內規則**——內容定址,沿連結線唯讀跨層(受**局部可達上界**:可達閉包止於 `locality` 韻律成分、預設 syllable,並向該旋律層錨定層前後各延伸相鄰一格,兩者取聯集;衡量可達性而非路徑長度),寫只寫自己這層。近似正則,可編譯進 FST 後端。
2. **Scan 塊**——唯一允許位置定址(「第幾個」)的建構,以三道鎖(along 軌道 / within 疆界 / from 方向)把違反局部性的全域存取關進盒子。非正則,永久直譯器。
3. **spell-out**——唯一的跨層整合點,置於全流程末端把多層圖壓平交給 romanizer。

宣告與規則示例(v0.3 記法):

```
Melody tone {H, L} anchor mora            # 乘客,預設停靠莫拉;Ø 為未指定
tonogenesis:  insert H floating near mora / onset&[-voice] _   # 沿支配鏈唯讀讀骨架
dock-tone:    dock tone&floating strategy nearest prefer-left  # 浮游調著陸,tie-break 向左
tone-shift:   shift 1 mora rightward                           # 整層平移(聲調右移一莫拉)
Scan tone along syllable within pword from right:              # 全域位置存取隔離於此
    associate H -> <syl>[2]                                    # 倒數第二音節指派
```

早期的 interface(跨層寫)類別已取消:跨層**讀**由可達性承擔、跨層**寫**不存在(改為末端 spell-out)、全域位置存取由 Scan 承擔。特徵幾何(feature geometry,同宿主特徵互動與類節點 spread)列為 MVP 後的進階選項。**FST 邊界**:tier 內規則(局部性內)候選編譯;Scan 與 spell-out 為標記的非正則點,留直譯器——影響含聲調語言的批次演化與反向重構覆蓋率,列 §10 開放問題。

**音素頻率分佈。** 每個音素與音節結構帶有權重(預設參考自然語言的 Zipf 式分佈,可手動調整),供造詞器抽樣使用,讓生成的詞「聽起來像同一個語言」。

### 4.2 音變演化模組(Diachronics — 音變軸)

**DSL 採用 strata 模型。** 明確採用 Lexurgy 式的分層規則檔,把一個詞從輸入到輸出拆成幾個已命名的層,規則寫在哪一層是分開宣告的:

1. **Deromanizer**:輸入正字法 → 音位/語音記法(IPA);
2. **音位/語音層**:真正的歷時音變都發生在此;
3. **中間 romanizer**:可在演化任一階段插入,把該階段以可讀轉寫 dump 出來 —— 這正是「保留不同演化階段」的機制;
4. **Romanizer**:語音 → 輸出正字法。

這樣可避免把「轉寫慣例」和「真正的音變」混為一談,是既有工具踩過坑後的成熟設計,建議直接沿用而非自創分層方式。規則本體形如:

```
k > tʃ / _ [+front]        # 前元音前顎化
V > ∅ / _ #  (unstressed)   # 詞尾弱化元音脫落
{p,t,k} > {b,d,g} / V_V     # 元音間濁化
```

引擎需支援:特徵化自然類、環境條件(前後文、詞界 #、音節與重音/聲調狀態)、規則排序與 feeding/bleeding 互動、複合規則(`Then:` 串接)、例外詞標記。執行策略採前一輪討論的混合式:直譯器為「編輯模式」引擎(逐條追蹤、易除錯、貼近使用者習慣),FST 為「定稿後」後端(整本詞典即時批次演化、祖語反向重構)。

**輔助模式的「補全演化」。** 這是實現「只設定重要演化規則」的關鍵。內建一份**音變自然度資料庫**:常見演化路徑的有向圖(lenition 鏈 p→f→h→∅、元音鏈移、鼻音同化、詞尾清化等),每條路徑附觸發條件與典型機率。使用者寫下 2–3 條關鍵音變後,系統:分析套用後的音系狀態(例如某音變造成不平衡的元音空間);從資料庫抽樣提出 5–10 條「後續自然演變」建議(附解釋:為什麼這條演變常見);使用者勾選採納,系統自動排序插入規則鏈。

**雙軌:共時導出 × 歷時編輯(《架構修補01》)。** 語言 = sign store(底層形 UR,有限)+ **Grammar Store**(按韻律層級索引的共時規則,有限);表層形按需導出、**永不儲存**。歷時音變不是「對詞表套規則鏈」,而是 **ChangeSet 對兩個有限儲存的編輯**(AddRule / LoseRule / ReorderRules / InvertRule + UR restructuring);Lexurgy 式「套規則改詞表」= AddRule + 立即 Lexicalization 的相容模式。詳見《架構修補01_共時規則系統與臨時韻律域》。

**演化樹與時間軸。** 每個語言節點記錄「相對於父節點的 ChangeSet」。對 Grammar Store/UR 的編輯經重導出即得子語言詞典,詞條自動保留詞源鏈(proto-form → 各階段中間形 → 現代形)。視圖上以家族樹 + 每條枝上的規則清單呈現,點任一詞可回放它的完整演變歷程。

### 4.3 語法化演化模組(Grammaticalization — 由上而下的演化軸)

這是 v0.2 的主要新增,是音變引擎在「語法側」的對稱物,實現使用者要的「語用→句法、句法→型態與辭典」的下沉機制。

**語法化斜坡(cline)。** 引擎的核心是這條公認路徑:

```
篇章/語用策略 → 句法構式 → 功能詞 → 依附詞(clitic) → 屈折詞綴 → 融合/零形
(內容詞) ───────────────────────────────────────────────────────►(語法素)
```

材料只往右(下)走,方向性是語法化的實證通則,這正是讓系統能「自動建議」的基礎——就像音變有自然度資料庫,語法化也有可查的典型路徑。

**語法化路徑資料庫。** 對應音變自然度資料庫,內建一份 source→target 的斜坡路徑表(可整理自 Heine & Kuteva 的《世界語法化辭典》這類彙編),每條附觸發構式與條件。範例路徑:

- 動詞 GO / WANT → 未來時標記
- 動詞 FINISH / 副詞「已經」→ 完成貌 / 完結貌
- 指示詞 → 定冠詞 →(進一步)關係詞 / 一致標記
- 數詞 ONE → 不定冠詞
- 身體部位名詞(BACK、HEAD、FACE)→ 方位後置詞 / 空間格
- 動詞 SAY → 補語連詞 / 引述標記
- 伴隨介詞 WITH → 工具格
- 領有動詞 HAVE / GET → 義務情態

**四個伴隨機制(引擎每套一步都同步觸發)。** 重新分析(reanalysis,結構重新劃界:句法構式被解讀為型態結構)、類推擴展(analogical extension,新用法擴散到更多語境)、語意漂白(desemanticization,實義流失)、語音磨損(erosion)。其中 erosion 直接把新生的黏著形丟進 §4.2 的音變引擎處理——這是兩軸交會點。

**輔助模式運作流程。** 給定辭典(內容詞)與句法層的若干構式,引擎在輔助模式下掃描並提出建議,例如「你表『完成』的動詞可循 FINISH→完成貌路徑,語法化為一個完成貌詞綴」。使用者採納後,系統自動:(a) 在辭典層新增一個功能語素條目,標記 `grammaticalized-from: X`,並保留來源內容詞(divergence/layering,母詞與語法素並存);(b) 在句法層與型態層記錄這次重新分析;(c) 視需要把新黏著形排入音變引擎接受磨損。整個過程進入與其他生成內容相同的「建議→採納」流程,可鎖定、可重骰、可 undo。

**與文法檔約束器聯動。** 引擎只會提出「目標範疇已被使用者勾選」的路徑,且輸出形式受勾選的形態型限制(見 §4.5)。

### 4.4 造詞與辭典模組(Word Generation & Lexicon)

**候選詞生成器。** 依音位配列 + 頻率權重抽樣生成詞形,一次呈現 10–20 個候選讓使用者挑選(即「自動預選」)。支援約束條件過濾:音節數範圍、必含/禁含某音、押韻或頭韻要求、與某詞相似/相異。生成與手動輸入時即時做**避撞檢查**:完全同音、與既有詞編輯距離過近(可調閾值)、違反 phonotactics。

**內建 Swadesh 與核心詞列表。** 一等公民功能。內建 Swadesh 100 / 207、Leipzig-Jakarta 100、Dolgopolsky 等清單,並附分類語意場(親屬、身體、自然、基本動作)。以「填空進度」呈現,可依清單或語意場批次造詞;清單也作為概念空間的覆蓋率追蹤器,快速看出辭典還缺哪些基礎概念。清單可自訂與擴充。

**借詞子模組(Loanword)。** 模擬語言接觸。指定一個 donor(專案內的另一個 conlang 節點,或內建的自然語言音系側寫),引擎對 donor 詞形套用 recipient 的**修復規則**:插音(epenthesis)、刪音、對缺失音素做特徵最近似替換,把外來詞「本土化」。修復規則本身就是一套小型規則引擎,重用 §4.2 的 DSL 機制。借詞條目標記 `origin: loan`,記錄 donor、借入時間與**借詞層(stratum)**——早期借詞會跟著經歷後續音變,晚期借詞不會,這個時間差直接掛上演化時間軸,是很有表現力的功能。反向找同源/借源可參考 loanpy 這類既有工具的作法。

**辭典管理。** 詞條資料結構:詞形(音位/正字兩層)、詞性、多義項釋義、例句、語意標籤、詞源鏈(指向祖語詞條或 donor)、來源標記、備註。介面為可篩選排序的表格 + 詞條詳情頁,含全文搜尋(含 IPA 搜尋)、反查(由釋義找詞)、批次編輯、統計面板(音素使用率、音節型分佈,可檢查詞典是否偏離設定頻率)。匯出:CSV、JSON、Markdown 詞典、LaTeX、以及 MDF(SIL Toolbox / Lexique Pro 相容格式,便於與既有工具互通)。

### 4.5 文法檔:範疇與形式勾選(演化限制器)

每個語言節點帶一份**文法檔(grammar profile)**,是一組勾選盤,分兩類:

**範疇(Categories)—— 這語言「在乎」哪些區別。** 時制、體貌、情態、示證(evidentiality)、格、數、性/類別(gender / noun-class)、定指、人稱一致等,逐項勾選是否發展。

**形式/實現(Exponence)—— 這語言「怎麼表現」語法。** 形態型(孤立 / 黏著 / 屈折)、詞綴位置偏好(前綴 / 後綴,與語序和諧相關)、是否容許融合、詞幹交替、以聲調承載語法等。

這份檔以兩種方式約束自動演化,是語法側對應「音位配列約束造詞」的機制:

1. **範疇過濾**:語法化引擎只提出目標範疇已勾選的路徑——未勾示證,就不會憑空長出示證系統。
2. **形式約束**:語法化輸出的形態要符合勾選的實現方式——在「僅後綴」的檔案下,一個後置詞語法化時只能變成格**後綴**而非前綴,與語言的語序和諧一致。

勾選可隨時間軸調整(某節點才開始發展格系統),也可設為「自動」讓系統依類型學和諧律自行推薦一組自洽的範疇/形式組合。

### 4.6 Phase 2 模組(四項)

**LLM 外掛。** 語意漂移建議、例句生成、自然語翻譯練習、語法化來源構式的自動偵測輔助。一律為選配、可完全停用,輸出進入相同的「建議→採納」流程,不改變離線核心的可重現性。

**文字系統。** 字符編輯與正字法映射,直接接上 §4.2 的 romanizer 層;支援演化(字符隨語言分化而變體)與音節/字母/表意等類型。

**語音模擬。** 讓 conlang 可被「聽見」。分兩層:音位→語音的實現層(允音變體、協同發音等次於音位的細節),與 IPA→音訊的合成層(可先接現成 TTS/共振峰合成,長期可做關節式合成)。實現層的規則重用 §4.2 的 DSL,但作用在語音而非音位表徵。

**多主體演化模擬(Multiagent)。** 以能動者為基礎(agent-based)模擬語言變化如何在說話者群體中觸發與擴散:社會網路上的創新傳播、詞彙擴散(lexical diffusion,接上前述加權 FST 抽樣)、迭代學習(iterated learning)產生規則化與組合性。與 §4.3 的語法化引擎互補——語法化給「路徑」,多主體模擬給「哪些成員、多快採納」。抽樣同樣走 seeded PRNG 以維持可重現。

## 5. 統計引擎與內建資料

> 本節的完整本體論已細化為《docs/10 統計先驗與抽樣引擎》:E = 唯讀先驗庫 + 無狀態抽樣函數;有效分佈 = 手動 > 導入 provider > 統計投影 > E1 先驗;語言特定頻率不獨立儲存(是 sign 集合的投影,覆寫住節點)。以下為原始概述。

離線引擎的「像自然語言」效果來自數份內建靜態資料,隨軟體打包、不需連網:

1. **類型學先驗表**:音素庫大小分佈、常見音素共現(可自 PHOIBLE 整理)、音節結構與語序/對齊類型頻率(可參考 WALS);
2. **音變路徑資料庫**:常見歷時音變(可參考 Index Diachronica 的整理),含條件與權重;
3. **語法化斜坡資料庫**:source→target 路徑(可參考 Heine & Kuteva 的彙編),含觸發構式與條件;
4. **頻率模板**:數種自然語言風格的音素/音節權重預設檔(可另存自訂風格);
5. **Swadesh / 借詞用自然語言音系側寫**:供覆蓋率追蹤與借詞 donor 使用。

抽樣一律走 seeded PRNG,保證可重現。這幾份資料庫的人工整理是全案最花語言學功夫處,建議都採「先做 30–50 條高頻項起步、之後增補」的策略。

## 6. 資料模型(概要)

語言節點改為承載一疊分層,而非扁平欄位:

```
Project ─┬─ LanguageNode(樹狀,parent_id)
         │     ├─ PragmaticsStratum   (資訊結構、言語行為、敬語、篇章助詞)
         │     ├─ SemanticsStratum    (語意地圖、語意場、TAM/空間本體)
         │     ├─ SyntaxStratum       (語序、對齊、構式、論元結構)
         │     ├─ MorphologyStratum   (語素庫、形態型、範式/模板、詞綴序)
         │     ├─ PhonologyStratum    (音素+特徵、phonotactics、超音段 tier)
         │     ├─ Lexicon ─ Lexeme    (form, gloss, tags, origin, etymology_ref)
         │     ├─ Orthography         (字符、正字法映射)
         │     ├─ GrammarProfile      (範疇/形式勾選,演化限制)
         │     └─ ChangeSet           (到子節點的變化:音變規則序列
         │                             + 語法化事件 + 手動編修)
         └─ Settings(seed, 各模組干涉檔位, 頻率模板)
```

各層以參照互連(型態層語素 → 辭典條目 + 音系音形)。父子節點的差異可**按層計算**(「從祖語到女兒語,句法層改了什麼」),這是演化樹視圖與詞源回放的資料基礎。專案檔為單一 SQLite 檔(利於大詞典效能與搜尋),另提供 JSON 完整匯出作為交換與版本控管格式。

## 7. 技術選型建議

**框架:Tauri 2(Rust 後端 + Web 前端)**,理由:安裝包小、跨平台、Rust 適合實作高效能的批次演化引擎(對上萬詞條套用數十條規則需即時完成);替代方案為 Electron。前端:React + TypeScript;IPA 輸入採內建虛擬鍵盤 + X-SAMPA 快捷。引擎核心以 Rust crate 實作並附完整單元測試(演化引擎正確性是全案地基);實作遵循《執行語意規格》§9 四原則:優先套用開源模組、原語先行其餘組合、每 identity 單一資訊源、功能完整下精簡。資料庫:SQLite(rusqlite / tauri-plugin-sql)。

## 8. DSL 與既有工具參照(供實作對照)

- **Lexurgy(目前 v1.7.x,活躍維護)**:採用其 strata 模型(deromanizer / 音位 / 中間 romanizer / romanizer)作為 DSL 骨架;特徵(需明確定義)、變音符、類別、複合規則(`Then:`)、逐步追蹤皆成熟,且有社群規則庫。長距離現象靠 `propagate`(反覆套用至收斂,含方向變體)+ `filter`(投影出子集,如只看母音)處理母音和諧、鼻化、重音。音節結構在 v1.7.0 改用 `onset :: nucleus :: coda` 明確標界。**但這是線性模型 + 投影,非真正的多 tier**:沒有獨立浮動的聲調 tier,故「聲調右移一音節」「音段刪除後特徵浮動重掛」這類做不到。本案的多 tier 表徵(§4.1)即針對此點超越之。是本案 DSL 的主要參照。
- **Brassica**:取捨方向不同,原生把重音/聲調當一等超音段、原生多字母(把詞看成字位序列)、規則套用方式彈性(迭代/偶發/由右至左/跨詞)、內建 MDF 與範式產生器。處理正字法層與超音段時值得借鏡其模型。
- **ASCA**:以 Rust 撰寫的新音變引擎(網站 + CLI)。既然本案選 Rust,值得先評估能否直接作為音變後端地基,省下 replace/FST 相關的底層工程。
- **loanpy**:專門透過歷時規則反推同源/借源,對應本案的 FST 反向重構與借詞子模組。
- **已知天花板與本案對策**:現有 SCA 幾乎都在相鄰音段上操作,長距離/超音段規則(如「每個聲調右移一音節」)普遍難寫,各家多以 filter 或跳字位機制變通,無法直接表達「詞內任一處有鼻音則…」或自主音段浮動。本案以 §4.1 的 autosegmental 多層表徵正面處理:韻律軌道與旋律乘客兩分,以 association 為唯一原語、內建 stability 與 Ø 零特徵,並把違反局部性的全域存取隔離進 Scan。這是本案相對 Lexurgy / Brassica 最主要的差異化。

## 9. 開發路線圖

- **M0 — 引擎原型(無 UI)**:分層資料模型、音素/特徵模型、autosegmental 詞表徵(骨架 + 韻律軌道 + 旋律乘客 + 連結圖 + stability + Ø)、phonotactics 驗證器、seeded 詞形生成器、音變 DSL 直譯器(strata + tier 內規則 + Scan + 末端 spell-out)。CLI + 測試驗證。
- **M1 — MVP**:專案管理、音素庫編輯器、造詞面板(候選預選 + 避撞 + Swadesh 覆蓋)、辭典表格、單層音變套用。可完成「設計一個語言並造詞」的完整流程。
- **M2 — 音變演化完整版**:演化樹視圖、音變自然度資料庫與「補全演化」、詞源回放、FST 批次/反向後端、借詞子模組。
- **M3 — 語法化與文法檔**:語法化引擎與斜坡資料庫、文法檔勾選盤與約束器、erosion 兩軸交會、句法/型態層編輯器。
- **M4 — 擴充**:型態範式自動展開、LaTeX / MDF 匯出、跨層一致性檢查面板。
- **Phase 2**:LLM 外掛、文字系統、語音模擬(實現層 + IPA 合成)、多主體演化模擬。

## 10. 風險與開放問題

DSL 表達力與易學性的平衡——建議相容 Lexurgy 語法子集以借用社群資源。三份規則/路徑資料庫(音變、語法化、修復)的人工整理是最重的語言學工作量,採高頻優先增量策略。語法化引擎的難點在「重新分析」如何自動偵測觸發構式,建議 M3 先做「使用者指定來源詞 + 選定路徑」的半自動版,再逐步加入自動掃描建議。另需決定:是否支援匯入既有工具(PolyGlot、ConWorkShop、Lexurgy、Brassica)的專案或規則格式,這會顯著影響早期採用意願。新增兩個開放問題:(1) autosegmental 規則與 FST 後端的相容邊界——tier 內規則(局部性內)候選編譯,Scan 與 spell-out 為標記的非正則點永久留直譯器,影響批次演化與反向重構對含聲調語言的覆蓋率;(2) 多主體模擬的範圍界定——社會網路參數要開放到什麼程度才有趣而不失控,建議先以「少數可調參數 + 預設情境(方言分裂、接觸、聲望借詞)」起步。
